# T0 · VM 생성 직후 ~ `kubeadm init` 전 ★ 가장 중요

**전 노드 6대 모두**에 해야 합니다. 여기를 놓치면 클러스터를 다시 만들어야 합니다.

## T0-1. 클론 VM의 고유값 확인 🔴 Proxmox 클론에서 가장 잘 걸림

공식 문서가 **노드마다 고유해야 한다**고 명시하는 값이 3개입니다.

| 값 | 확인 명령 |
| --- | --- |
| hostname | `hostnamectl` |
| MAC 주소 | `ip link` |
| **product_uuid** | `sudo cat /sys/class/dmi/id/product_uuid` |

> ⚠️ **템플릿에서 클론하면 이 값들이 같아질 수 있습니다.**
> 겹치면 kubelet이 노드를 구분하지 못해 **join이 실패하거나, 더 나쁘게는 join은 되는데 노드가 서로 덮어씁니다.**
>
> 우리 팀은 이미 같은 계열의 문제를 겪었습니다 — harbor-template 만들 때 `machine-id`를 초기화하지 않아
> 4번 재작업했습니다(VMID 104→105→107→108). **같은 실수를 K8s에서 반복하면 비용이 훨씬 큽니다.**

**6대 전부 다른지 한 번에 확인:**
```bash
for h in master w1 w2 w3 w4 w5; do
  echo -n "$h: "; ssh $h 'sudo cat /sys/class/dmi/id/product_uuid'
done | sort -k2 | uniq -f1 -d    # 출력이 있으면 중복 있음
```

**중복이면**: `sudo systemd-machine-id-setup --commit` 후 재부팅. Proxmox 쪽에서 UUID 재생성이 필요할 수도 있습니다.

## T0-2. swap 비활성화

**v1.36에서도 kubelet의 기본 동작은 "swap이 감지되면 실패"** 입니다.

```bash
sudo swapoff -a
sudo sed -i '/ swap / s/^/#/' /etc/fstab     # 재부팅 후에도 유지
free -h | grep -i swap                        # 0B 이어야 함
```

> `failSwapOn: false`로 허용할 수도 있지만, **워크로드는 기본적으로 swap에 접근하지 못합니다.**
> 그리고 swap이 켜져 있으면 메모리 limit·OOM 판정이 흐려져서 **자원 산정이 무의미해집니다.**
> 관측 담당 입장에서 특히 반대할 이유입니다.

## T0-3. 커널 모듈 · sysctl

```bash
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay && sudo modprobe br_netfilter

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system
```

## T0-4. 컨테이너 런타임 — cgroup 드라이버 일치 🔴

공식 문서가 **런타임과 kubelet의 cgroup 드라이버가 일치해야 한다**고 요구합니다.

```bash
# containerd
sudo containerd config default | sudo tee /etc/containerd/config.toml
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd
```

> ⚠️ **안 맞으면 어떻게 되나**: 파드가 뜨긴 하는데 **자원 제한이 제대로 안 걸리고 노드가 불안정**해집니다.
> 에러가 안 나서 발견이 늦습니다. 관측 지표(cAdvisor)도 어긋납니다.

## T0-5. 시각 동기화 ★ 보안 담당 필수

```bash
timedatectl status          # System clock synchronized: yes 확인
timedatectl                 # Time zone: UTC 유지 (아래 이유)
```

**왜 보안 항목인가:**
- **인증서 검증**이 시각에 의존합니다. 노드 시각이 어긋나면 TLS 핸드셰이크가 실패합니다
- **감사 로그 타임스탬프**가 어긋나면 사고 조사 시 순서를 재구성할 수 없습니다
- **토큰 만료** 판정이 틀어집니다

**타임존은 UTC로 유지합니다.** 노드 TZ를 KST로 바꾸면 로그·메트릭 타임스탬프가 전부 이동해
**기존 Prometheus 데이터와 대조가 꼬입니다.** 사람이 읽을 스케줄만 `CronJob.spec.timeZone: "Asia/Seoul"`로 지정합니다.

## T0-6. 보안 설정 파일 3종 배치 ★★ 마스터 노드

**이 세 개가 T0의 존재 이유입니다.** 전부 kube-apiserver 기동 옵션이라 `init` 이후에는 재시작이 필요합니다.

```bash
sudo mkdir -p /etc/kubernetes/enc /etc/kubernetes/admission \
              /etc/kubernetes/audit /var/log/kubernetes/audit

sudo cp admission-config.yaml /etc/kubernetes/admission/
sudo cp audit-policy.yaml     /etc/kubernetes/audit/
# encryption-config.yaml 은 키를 포함하므로 마스터에서 직접 생성 (README 3단계)
```

| 파일 | 지금 넣으면 | 나중에 넣으면 |
| --- | --- | --- |
| `encryption-config.yaml` | 파일 배치 | API 재시작 + **기존 Secret 전량 재작성** |
| `admission-config.yaml` | 파일 배치 | API 재시작 |
| `audit-policy.yaml` | 파일 배치 | API 재시작 |

> **etcd 암호화는 소급 적용이 안 됩니다.** 켜기 전 저장된 Secret은 계속 평문입니다.
> Secret이 아직 0개인 지금이 유일하게 공짜인 시점입니다.

**③ etcd 암호화가 실제로 걸렸는가** — 가장 확실한 검증

```bash
  --cert=/etc/kubernetes/pki/etcd/server.crt \

  get /registry/secrets/default/enc-test | hexdump -C | head -5

# ✅ k8s:enc:aescbc:v1:key1 로 시작 → 암호화됨
# ❌ hello 가 그대로 보임      → 경로·볼륨 마운트 확인
kubectl -n default delete secret enc-test
```

## T1 부산물 — join 토큰 관리 ★ 보안

`kubeadm init` 출력의 join 명령에는 **부트스트랩 토큰**이 들어 있습니다.

- **기본 수명 24시간**입니다
- **이 토큰이 있으면 누구나 클러스터에 노드를 추가할 수 있습니다** → 슬랙·메신저에 붙여넣지 마세요
- join 시 **`--discovery-token-ca-cert-hash`를 반드시 포함**하세요.
  공식 문서: 이걸 생략하고 `--discovery-token-unsafe-skip-ca-verification`을 쓰면
  **다른 노드가 컨트롤플레인을 사칭할 수 있어 kubeadm 보안 모델이 약화**됩니다

```bash
kubeadm token list                       # 남은 토큰 확인
sudo kubeadm token delete <토큰>          # 워커 join 끝나면 즉시 삭제
```

# T2 · CNI(Cilium) 설치 🔴 되돌리기 매우 비쌈

**시점**: `kubeadm init` 직후, **CoreDNS가 Pending인 상태**에서 설치합니다.
CNI가 없으면 파드 네트워크가 없어서 CoreDNS가 뜨지 못합니다. 정상입니다.

## Pod CIDR을 반드시 명시

```bash
helm install cilium cilium/cilium -n kube-system \
  --set ipam.operator.clusterPoolIPv4PodCIDRList=10.244.0.0/16 \
  --set ipam.operator.clusterPoolIPv4MaskSize=24 \
  --set k8sServiceHost=<마스터IP> --set k8sServicePort=6443
```

> 🔴 **Cilium 기본 Pod CIDR은 `10.0.0.0/8`** 입니다.
> Cilium 공식 문서 경고: *"If your node network is in the same range as 10.0.0.0/8, you will lose connectivity to other nodes."*
> 그리고 공식 문서는 `clusterPoolIPv4PodCIDRList`의 **기존 항목을 나중에 바꾸지 말라**고 명시합니다
> (예기치 못한 동작). **설치 시점에 정해야 합니다.**
>
> `kubeadm-config.yaml`의 `podSubnet`과 **같은 값**이어야 합니다. 다르면 파드 네트워크가 동작하지 않습니다.

## ★ 보안·모니터링 담당이 여기서 확인할 것

**① NetworkPolicy가 실제로 작동하는지**
```bash
cilium status
kubectl -n kube-system exec ds/cilium -- cilium-dbg status | grep -i policy
```
> Cilium은 NetworkPolicy를 지원합니다. 하지만 **"지원한다"와 "작동한다"는 다릅니다.**
> T5에서 실제 연결 테스트로 확인합니다.

**② Hubble을 켤지 결정** ← 모니터링 담당 관심사
```bash
--set hubble.enabled=true --set hubble.relay.enabled=true
```
> Hubble은 Cilium의 관측 기능으로, **어떤 파드가 어떤 파드와 통신했고 정책에 막혔는지**를 보여줍니다.
> **NetworkPolicy 시연과 검증에 직접적으로 유용**합니다. 켜려면 설치 시점이 가장 쉽습니다.
> 자원을 더 쓰므로 워커 사양을 보고 판단합니다.

**③ kube-proxy 대체 모드를 쓸지**
Cilium은 kube-proxy를 대체할 수 있습니다. 쓴다면 `kubeadm init` 시
`skipPhases: [addon/kube-proxy]`가 필요하므로 **T1 전에 결정**해야 합니다.

# T3 · 워커 5대 join

```bash
sudo kubeadm join <마스터IP>:6443 \
  --token <토큰> \
  --discovery-token-ca-cert-hash sha256:<해시>
```

**★ 담당 확인사항**
- [ ] 6대 전부 `Ready`인가 — `kubectl get nodes -o wide`
- [ ] **join 토큰 삭제** — `sudo kubeadm token delete <토큰>`
- [ ] 마스터 노드의 taint 정책 결정 (아래)

## 마스터 taint — 관측 관점에서 중요한 결정

기본적으로 마스터에는 `node-role.kubernetes.io/control-plane:NoSchedule` taint가 붙어
일반 워크로드가 뜨지 않습니다.

**관측 DaemonSet(node-exporter)을 마스터에도 띄울 것인가?**

| 선택 | 결과 |
| --- | --- |
| **띄운다** (toleration 추가) | 마스터 노드 지표를 볼 수 있음 ✅ **권장** |
| 안 띄운다 | **마스터가 관측 사각지대**가 됨 |

> **마스터 1대 구성이라 더 중요합니다.** 그 한 대가 죽으면 클러스터 조작이 불가능해지는데,
> 지표가 없으면 죽어가는 것도 모릅니다. **반드시 toleration을 넣습니다.**

## T4-1. 네임스페이스 + PSA 라벨 (첫 번째)

> 먼저 만들고 나중에 라벨을 붙이면, 그 사이에 들어온 워크로드는 검사를 받지 않습니다.
> `namespaces.yaml`은 이미 라벨이 포함된 형태입니다.

**적용 전 dry-run으로 미리 보기** (공식 권장 방법):

## T4-2. etcd 스냅샷 CronJob ★★ 마스터 1대의 생명줄

> 공식 문서: *"컨트롤플레인 노드가 고장나면 클러스터가 데이터를 잃고 처음부터 재생성해야 할 수 있다."*
>
> 마스터가 1대이므로 **etcd 백업이 유일한 복구 수단**입니다. **미루지 않습니다.**

- etcd 데이터 위치: `/var/lib/etcd`
- 스냅샷은 `etcdctl snapshot save`
- 스냅샷 파일 자체가 **전 Secret을 담고 있으므로** 저장 위치의 권한을 제한해야 합니다
  (etcd 암호화를 켰으므로 스냅샷 안의 Secret도 암호문입니다 — T0-6을 한 이유)
- 오프사이트 복사까지 해야 마스터가 통째로 죽었을 때 의미가 있습니다

## T4-3. default ServiceAccount 토큰 자동마운트 차단

```bash
for ns in $(kubectl get ns -o name | cut -d/ -f2); do
  kubectl patch sa default -n $ns -p '{"automountServiceAccountToken":false}'
done
```

> **왜**: SA를 지정하지 않은 파드는 `default` SA를 받고 **토큰이 자동으로 마운트**됩니다.
> 권한은 없지만, 파드가 탈취되면 **API 서버에 붙을 발판**이 되고
> 여러 워크로드가 같은 SA를 쓰면 **감사 로그에서 누가 한 일인지 구분되지 않습니다.**

---

# T5 · 워크로드 배포 전

| 순서 | 작업 | 왜 이 순서인가 |
| --- | --- | --- |
| 1 | **ResourceQuota / LimitRange** | Quota가 걸리면 이후 모든 파드가 requests/limits를 명시해야 함. 워크로드보다 먼저 |
| 2 | **ServiceAccount + RBAC** | 워크로드가 SA를 참조하므로 먼저 존재해야 함 |
| 3 | **NetworkPolicy default-deny** | 나중에 걸면 이미 도는 통신이 끊겨 장애로 보임 |
| 4 | **연결 테스트로 차단 검증** | ⚠️ 정책이 있는 것과 작동하는 것은 다름 |
| 5 | metrics-server | HPA의 전제조건 |

## NetworkPolicy에서 반드시 빠뜨리지 말 것

- **DNS egress(53/UDP·TCP)** — kube-system CoreDNS로. **default-deny egress 도입 시 가장 흔한 장애 원인**
- **Prometheus scrape ingress** — 안 열면 지표 수집이 통째로 멈춤
- **API 서버 egress** — cert-manager·Kyverno 등이 API를 호출함

# T6 · 관측 스택 배포

| 순서 | 무엇 | 비고 |
| --- | --- | --- |
| 1 | Prometheus (StatefulSet + PVC) | |
| 2 | kube-state-metrics, node-exporter | node-exporter는 **privileged ns + 마스터 toleration** |
| 3 | ServiceMonitor / PodMonitor | 라벨 매칭 확인 |
| 4 | OTel Collector (Agent + Gateway) | Agent는 privileged ns |
| 5 | Loki, Tempo | |
| 6 | Grafana, Alertmanager | |
| 7 | PrometheusRule | 알람을 코드로 |

> 🔴 **도커 단계의 교훈을 반복하지 않기**: 관측 스택 전체가 무인증으로 `0.0.0.0`에 노출돼 있었습니다.
> 특히 **Loki는 애플리케이션 로그 전체가 조회**됩니다.
> K8s에서는 **NetworkPolicy로 관측 네임스페이스 ingress를 Grafana·Prometheus로만 제한**합니다.
