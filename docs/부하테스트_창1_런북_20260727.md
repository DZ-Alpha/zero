## 4. 실행 명령

```bash
# ④ Smoke — setup 로그(token=yes, recipeIds/gamIds 개수)와 체크 전부 통과 확인
k6run -e MODE=smoke -e SERVICE=all --tag testid=w1-smoke /scripts/k6-loadtest.js

# ⑤ ramp (6분) — knee 탐색
k6run -e MODE=ramp -e SERVICE=product     -e MAX=200  --tag testid=w1-product-ramp     /scripts/k6-loadtest.js
k6run -e MODE=ramp -e SERVICE=recipe      -e MAX=200  --tag testid=w1-recipe-ramp      /scripts/k6-loadtest.js
k6run -e MODE=ramp -e SERVICE=ingredients -e MAX=200  --tag testid=w1-ingredients-ramp /scripts/k6-loadtest.js
k6run -e MODE=ramp -e SERVICE=main        -e MAX=1000 --tag testid=w1-main-ramp        /scripts/k6-loadtest.js

# knee 판독 후 — steady 3회 반복 (같은 RATE, testid만 r1/r2/r3)
# 각 run이 끝나면 곧바로 harvest (window 기본 2m30s = steady 3m − 워밍업 30s)
k6run -e MODE=steady -e SERVICE=product -e RATE=<knee> --tag testid=w1-product-steady-r1 /scripts/k6-loadtest.js
~/loadtest/harvest.sh w1-product-steady-r1 product-service
k6run -e MODE=steady -e SERVICE=product -e RATE=<knee> --tag testid=w1-product-steady-r2 /scripts/k6-loadtest.js
~/loadtest/harvest.sh w1-product-steady-r2 product-service
k6run -e MODE=steady -e SERVICE=product -e RATE=<knee> --tag testid=w1-product-steady-r3 /scripts/k6-loadtest.js
~/loadtest/harvest.sh w1-product-steady-r3 product-service
# (community 시간 남으면) k6run -e MODE=ramp -e SERVICE=community -e MAX=150 --tag testid=w1-community-ramp ...
```

**harvest는 run 직후에 실행할 것** — window가 "지금부터 과거"라서 시간이 지나면 창이 어긋난다.
ramp 직후 전체 구간을 보려면 `harvest.sh w1-product-ramp product-service 6m`.

판독 규칙:
- ramp가 끝까지 SLO 안 → knee 미도달, MAX 올려 1회 재실행
- steady가 SLO 위반 → RATE = 0.9×knee로 3회 다시
- **steady 첫 30초는 워밍업으로 버리고** 평균/피크를 읽는다
- **3회 p95 편차(CV) > 10% → 그 서비스는 원인 확인 후 재측정** (관행적 기준 — 공식 표준 아님.
  배포·다른 부하와 겹쳤는지, cadvisor 재시작 여부부터 확인)

## 6. 관측 쿼리 카드 (Grafana Explore)

⚠️ **단위·시리즈 함정 (2026-07-27 실측 확인)**: k6 remote-write는 지연을 **초 단위**로 저장한다
(0.0523 = 52.3ms). Grafana에서 그래프 축이 0.05로 보이면 50ms다 — SLO 500ms는 **0.5**와 비교할 것.
또 시리즈가 **엔드포인트별로 쪼개져** 있어서 그냥 조회하면 여러 줄이 나온다. 보수적으로 보려면
`max(...)`로 최악 엔드포인트를 보고, **전체 집계 p95는 k6 콘솔의 THRESHOLDS 블록이 정답**이다.

```promql
# ① SLO (k6 클라이언트 측) — testid는 해당 run으로. ×1000 해서 ms로 본다
max(k6_http_req_duration_p95{testid="w1-product-ramp"}) * 1000
max(k6_http_req_failed_rate{testid="w1-product-ramp"})
# ② 실제 RPS
rate(k6_http_reqs_total{testid="w1-product-ramp"}[30s])
# ③ 대상 컨테이너 자원 (시방서 값의 원천)
rate(container_cpu_usage_seconds_total{job="cadvisor-production-vm",name="<svc>"}[1m])
container_memory_working_set_bytes{job="cadvisor-production-vm",name="<svc>"}
# ④ 경로 병목 — b-gateway도 0.5 CPU (0.4↑ 지속이면 게이트웨이 한계를 재는 중)
rate(container_cpu_usage_seconds_total{job="cadvisor-production-vm",name="b-gateway"}[1m])
# ⑤ 생성기 포화 (R4) — 70%↑면 생성기 한계 의심
100 - avg(rate(node_cpu_seconds_total{job="harbor-vm",mode="idle"}[1m]))*100
# ⑥ cadvisor 생존 (R9) + DB VM (R6)
up{job="cadvisor-production-vm"}
topk(5, sum by (name)(rate(container_cpu_usage_seconds_total{job="cadvisor-db-vm"}[1m])))
```

판독: ①의 p95가 500ms를 넘는 시각 → 그 시각의 ② 값 = knee RPS.

⚠️ **사후 분석 함정**: 위 instant 쿼리들은 **테스트가 도는 동안**만 값이 나온다.
Prometheus instant 쿼리는 최근 5분(lookback delta 기본값) 샘플만 보므로, 끝난 run을
나중에 조회하면 빈 결과가 나온다(staleness — 공식 문서 querying basics). 사후 분석은
range 함수로: `max_over_time(k6_http_req_duration_p95{testid="..."}[3h])` 또는
Grafana 시간범위를 run 시각으로 맞춰 그래프로 볼 것.

### 병목 귀속 판정 (이 열이 비면 R을 replicas 계산에 쓰면 안 된다)

knee에서 무엇이 먼저 한계에 닿았는지 harvest 출력으로 분류한다. **replicas 공식은
"컨테이너가 병목"일 때만 성립**한다 — DB나 게이트웨이가 병목이면 파드를 늘려도 처리량이
안 늘기 때문이다(공유 자원이 상한).

| 관측 | 귀속 | 시방서에 쓰는 법 |
| --- | --- | --- |
| 대상 컨테이너 CPU가 0.5(=limit)에 근접 | **컨테이너 CPU** ✅ | R을 그대로 사용 |
| MEM이 한도 90%↑, 재시작 발생 | **컨테이너 MEM** ✅ | 상향 후 재측정해야 진짜 필요량 |
| b-gateway CPU ≥0.45 | 게이트웨이 ⚠️ | R은 하한값. 게이트웨이 replicas도 별도 산정 |
| DB VM top이 급등 | DB ⚠️ | R은 하한값. DB 증설/캐시가 선결 — 성애님 소관 |
| 셋 다 여유인데 p95만 상승 | 앱 내부(직렬화/외부호출) | 코드 이슈로 이관, 값은 참고용 |

환산 (창 밖에서):
```
replicas = ceil(목표RPS / R) × 1.3
requests.cpu/mem = steady 평균 | limits.cpu = 피크×1.5~2.0 | limits.mem = 피크×1.3~1.5
HPA target 60~70%, CPU 기준만
```

- 사용자 접점(192.168.0.56:3001)이 실제로 안 열림 — 즉시 중단

**복구 (부하 제거 후에도 서비스가 안 돌아올 때)**
```bash
# 1) 부하 완전 정지 확인 (harbor)
docker ps --filter ancestor=grafana/k6:1.3.0 -q | xargs -r docker stop

# 2) 상태 확인 (production — ssh bruce@10.10.10.30)
sudo docker ps -a --format '{{.Names}}\t{{.Status}}'
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/b/search?page=1

# 3) 죽은 컨테이너만 재기동 (compose 정의 그대로 — 설정 변경 아님)
cd ~/backend && sudo docker compose -p backend up -d <서비스명>

# 4) 사용자 접점 확인
curl -s -o /dev/null -w '%{http_code}\n' http://10.10.10.30:3001/
```

  안 될 때만. 이미지·설정을 바꾸지 않으므로 CI 배포 상태와 충돌하지 않는다.
- 복구가 안 되면 silence 해제 + 팀 공지 후 성애님/재헌님과 함께 판단(혼자 롤백 시도 금지).

5. (권장) 야간 soak 1회 — login이 무트래픽에도 256Mi의 97.6%까지 기어오른 건 누수 의심.
   soak가 누수 여부를 판정해줌 (k6 공식 test types의 soak)
6. spike/soak 모드는 스크립트에 이미 내장 (`MODE=spike -e MAX=…` / `MODE=soak -e RATE=… -e DURATION=3h`)
   — soak RATE는 knee의 50~80%, spike 판정은 급등 구간 에러율 + 급락 후 p95 회복 시간

## 9-b. 사진 업로드 부하 (★ 우리 서비스 고유 워크로드 — 창2 핵심)

표준 읽기 부하만으로는 당당의 실제 부담을 못 잰다. **식단 사진 업로드가 유일한 대용량 요청
경로이고, 메모리를 가장 많이 쓰는 코드 경로**다. login/ai/diet가 무트래픽에도 메모리 90%+인
현상과 직결될 가능성이 높다.

### 경로와 부하 특성 (코드 실측)

| 구간 | 코드 | 부하 특성 |
| --- | --- | --- |
| b-gateway | [nginx.conf:121](../infra/b-gateway/nginx.conf#L121) `client_max_body_size 12m` | 큰 본문을 `/tmp`에 버퍼링 → **그 /tmp가 tmpfs(=RAM)** 라 게이트웨이 256m 한도에 얹힌다 |
| diet-service | [uploads.py:24](../backend/diet-service/app/routers/uploads.py#L24) `data = await file.read()` | **파일 전체를 메모리에 적재** → 동시 업로드 N개 × 사진 크기가 그대로 메모리 피크 |
| MinIO (DB VM) | [storage.py:51](../backend/diet-service/app/services/storage.py#L51) `put_object` | 객체가 실제로 쌓인다 → 사후 정리 필요 |
| AI 분석 | `POST /diet/upload`(별도 API) → meal_log + Kafka | **호출하지 않으면 트리거 안 됨** → Bedrock 과금 없음 |

즉 `POST /b/uploads/diet-photo`만 때리면 **저장 경로의 진짜 메모리 필요량을 Bedrock 비용 없이**
잴 수 있다. 이 값이 diet-service `limits.memory`의 실측 근거가 된다.

### 실행 (창2, 승인 후)

```bash
# smoke — 1건 업로드가 200인지 (object_key 반환 확인)
k6run -e MODE=smoke -e SERVICE=upload -e PHOTO_KB=2048 -e PRE_VUS=5 -e MAX_VUS=10 \
  --tag testid=w2-upload-smoke /scripts/k6-loadtest.js

# ramp — 업로드는 RPS를 훨씬 낮게. 전송시간 포함이라 SLO도 별도
k6run -e MODE=ramp -e SERVICE=upload -e MAX=20 -e SLO_MS=3000 \
  -e PHOTO_KB=2048 -e PRE_VUS=20 -e MAX_VUS=60 \
  --tag testid=w2-upload-ramp /scripts/k6-loadtest.js
~/loadtest/harvest.sh w2-upload-ramp diet-service 6m
~/loadtest/harvest.sh w2-upload-ramp b-gateway 6m      # 게이트웨이도 반드시 함께
```

- `PHOTO_KB`: 2048(폰 사진 압축 후 통상) 기본. 10MB 상한 근처(예: 9000)로 한 번 더 재면
  최악 케이스 메모리를 알 수 있다.
- **VU 수를 낮추는 이유**: 사진 버퍼가 VU마다 복사된다(60 VU × 2MB ≈ 120MB, 생성기 메모리).
- **게이트웨이를 같이 재는 이유**: tmpfs 버퍼링 때문에 백엔드보다 게이트웨이가 먼저 OOM될 수 있다.

### 업로드 전용 리스크

| # | 리스크 | 대응 |
| --- | --- | --- |
| U1 | **MinIO에 테스트 객체 누적** (2MB × 수천 건 = GB급) | 사전 승인(성애님) + 사후 삭제. 키가 `diet-photos/<TEST_USER_ID>/`로 격리되므로 프리픽스 단위 삭제 가능 |
| U2 | b-gateway가 tmpfs 버퍼로 먼저 OOM | 게이트웨이 메모리를 동시 관측. 죽으면 **전 API가 멈춘다** — 중단 기준에 포함 |
| U3 | 네트워크 포화 (2MB × 20 RPS = 40MB/s) | harvest의 `net rx` 확인. 80MB/s↑면 네트워크를 재는 중 |
| U4 | DB VM(MinIO) 디스크·CPU 압박 | 성애님 소관. DB VM top + 디스크 알람 유지 |

**사후 정리** (테스트 종료 직후, MinIO 자격증명 필요 — 성애님):
```bash
# 예시: mc(MinIO Client) 사용 시 — 테스트 사용자 프리픽스만 삭제
mc rm --recursive --force <alias>/<bucket>/diet-photos/<TEST_USER_ID>/
```
정리 전에 `mc ls --summarize`로 삭제 대상 건수·용량을 먼저 확인할 것.

## 10. 남은 갭 — 측정으로 못 메우는 것 (팀 결정 필요)

부하테스트가 아무리 정확해도 아래는 "결정"이라 측정으로 나오지 않는다. 창1 결과를 들고
정하면 시방서가 완성된다.

| # | 갭 | 없으면 생기는 일 | 누구/언제 |
| --- | --- | --- | --- |
| G1 | **목표 RPS(T) 미정** — replicas 공식의 분자 | R을 구해도 replicas를 못 정함 | 팀 결정. 창1 직후. 근거 예: 시연 동시접속 N명 × 인당 0.3~0.5 req/s |
| G2 | **frontend(Next.js) 미측정** — 512Mi 한도, k8s Deployment 대상 | frontend requests/limits만 근거 없음 | 창2에 `BASE_URL=http://10.10.10.30:3001` ramp 1회 추가 여부 결정 |
| G3 | **쓰기 경로** — 사진 업로드는 9-b로 해소(스크립트 준비 완료), 나머지 POST(글쓰기·식단기록)는 미측정 | 쓰기 많은 서비스 limits 과소 산정 가능 | 업로드=성애님 승인 후 창2. 그 외 POST는 DB 오염이라 별도 협의 |
| G4 | **admin-service 경로 없음** (인증 GET뿐) | admin 값은 유사 서비스 준용 | 창2에서 admin 토큰(role=admin)으로 `/b/admin/me` 측정 가능 |
| G5 | **DB VM은 단일 인스턴스** — 모든 서비스가 공유 | 병목 귀속이 DB면 replicas 증설이 무효 | 7번 판정표로 매 회차 기록. DB 증설은 성애님 소관 |
| G6 | **K8s 재측정 미실시** | 도커 값은 "시작 근거"일 뿐 | 7/31 통합검증에서 동일 스크립트 재실행(k6-operator 또는 동일 harbor 실행) |

### 측정 정확도의 알려진 한계 (해석 시 감안)

- **scrape 15s + 1m rate 평활** → CPU 피크는 실제보다 낮게 잡힌다. limits에 ×1.5~2.0을
  두는 이유이며, 이 여유를 줄이지 말 것.
- **cAdvisor 자체가 무겁다**(7/24 OOMKill 2회) — 측정 중 죽으면 그 구간 공백. harvest의
  `cadvisor up`이 1인지 매번 확인.
- **k6는 클라이언트 측 지표** — 네트워크 왕복이 포함된다. 같은 LAN이라 영향은 작지만,
  서버 처리시간과 동일하지 않다(앱 OTel이 붙으면 교차검증 가능 — 재헌님 담당).
