# K8s 오브젝트 이해도 검증 — 예상 질의응답 35문항 (모범답안 포함)

## A. 기본 개념 (10문항) — 2~3문장으로 답하기

**A1. PSA(Pod Security Admission)가 뭐예요?**
- **A**: 파드가 생성될 때 보안 설정을 네임스페이스 라벨 기준으로 검사해 통과·거부·경고를 결정하는 쿠버네티스 기본 내장 어드미션 컨트롤러입니다. privileged/baseline/restricted 3개 레벨과 enforce/audit/warn 3개 모드를 조합해 쓰며, v1.25에서 제거된 PSP의 후계입니다. 저희는 원칙적으로 enforce=restricted를 걸고, DB 네임스페이스만 baseline으로 완화했으며 관측 DaemonSet은 공식문서 재검증 결과 privileged가 필요해 별도 분리로 재조정 중입니다.

**A2. SecurityContext는 뭐예요?**
- **A**: 파드나 컨테이너가 어떤 사용자(UID)·권한·커널 능력으로 실행될지를 매니페스트에 지정하는 필드입니다. PSA가 검사하는 관문(gate)이라면 SecurityContext는 그 관문을 통과할 실제 값을 채우는 쪽입니다. 저희 팀 표준은 runAsNonRoot, allowPrivilegeEscalation=false, capabilities drop ALL, seccomp RuntimeDefault의 하드닝 4종 세트입니다.

**A3. NetworkPolicy는 뭐고, 기본 동작은 어떻게 되나요?**
- **A**: 어떤 파드가 어떤 대상과 통신할 수 있는지를 IP·포트(L3/L4) 수준에서 선언하는 쿠버네티스 방화벽 규칙입니다. 기본 상태의 파드는 비격리, 즉 전부 허용이고, 어떤 정책이 그 파드를 선택하는 순간 격리되어 명시적으로 허용된 트래픽만 통과하는 화이트리스트 모델입니다. 적용에는 Calico·Cilium 같은 정책 지원 CNI가 필수입니다.

**A4. ServiceAccount는 뭐예요?**
- **A**: 파드(워크로드)가 쿠버네티스 API 서버에 자기 신원을 증명할 때 쓰는 기계용 신분증입니다. 쿠버네티스에는 사람용 User 오브젝트가 아예 없고, 사람은 인증서나 OIDC 같은 외부 수단으로 인증합니다. SA는 인증(누구인가)만 담당하며, 권한(무엇을 할 수 있는가)은 RoleBinding으로 따로 연결해야 하고 연결 전에는 권한이 0입니다.

**A5. Secret에 값을 넣으면 암호화되나요?**
- **A**: 아닙니다. Secret의 data는 base64 인코딩일 뿐이라 누구나 디코드할 수 있고, 기본 설정에서는 etcd에도 평문으로 저장됩니다(공식 문서 명시). 실제 보호는 RBAC 최소권한과 etcd Encryption at Rest를 명시적으로 켜야 완성됩니다.

**A6. StatefulSet은 뭐고 언제 쓰나요?**
- **A**: 파드마다 바뀌지 않는 고유 이름(신원)과 파드 전용 영속 볼륨을 보장하는 상태 저장 워크로드 컨트롤러입니다. 공식 문서 기준으로 ①안정적 네트워크 식별자 ②안정적 영속 스토리지 ③순서 보장 배포·스케일링 ④순서 보장 롤링 업데이트 — 이 4가지 중 하나라도 필요하면 StatefulSet, 아니면 Deployment입니다. 저희는 Prometheus·Alertmanager·Vault가 여기 해당합니다.

**A7. DaemonSet은 뭐예요?**
- **A**: 클러스터의 모든(또는 조건에 맞는) 노드마다 똑같은 파드를 정확히 1개씩 돌게 보장하는 워크로드 컨트롤러입니다. replica 필드가 없고 노드 수가 곧 파드 수이며, 노드가 늘거나 줄면 자동으로 따라갑니다. 노드 자체의 지표·로그를 걷어야 하는 node-exporter, OTel Collector Agent에 씁니다.

**A8. HPA는 어떻게 동작하나요?**
- **A**: CPU 같은 지표를 보고 파드 개수(replica)를 자동으로 늘리고 줄이는 컨트롤러입니다. 기본 지표는 "사용량 ÷ requests"의 사용률(%)이고, 이 숫자는 cAdvisor→kubelet→metrics-server→Metrics API 파이프라인이 공급합니다. 그래서 requests 미지정이거나 metrics-server가 없으면 HPA는 동작하지 못합니다.

**A9. Namespace는 보안 경계인가요?**
- **A**: 아닙니다, 소프트 격리입니다. 네임스페이스 자체는 네트워크·커널·자원을 차단하지 않으며, 공식 문서도 "네임스페이스 간 보안을 강제하지 않는다"고 명시합니다. 대신 RBAC·NetworkPolicy·PSA·Quota 같은 정책을 걸 수 있는 경계를 제공하므로, 저희는 그 위에 default-deny 등 정책을 얹어 실질 격리를 만들었습니다.

**A10. PDB(PodDisruptionBudget)는 뭐예요?**
- **A**: 노드 드레인 같은 "자발적 중단" 상황에서 한 애플리케이션의 파드가 동시에 몇 개까지 내려갈 수 있는지(또는 최소 몇 개는 살아있어야 하는지)를 보장하는 오브젝트입니다. minAvailable 또는 maxUnavailable 중 하나로 지정하고, Eviction API를 거치는 축출에만 작동합니다. 하드웨어 고장 같은 비자발적 중단은 막지 못합니다.

## B. 비교·구분 (11문항)

**B1. Role과 ClusterRole의 차이는?**
- **A**: 범위가 다릅니다. Role은 특정 네임스페이스 안의 리소스에만 권한을 주고, ClusterRole은 네임스페이스 경계 없이 Node·PV 같은 non-namespaced 리소스와 /metrics 같은 nonResourceURLs까지 다룹니다. 규칙 문법(apiGroups·resources·verbs)은 완전히 같고 차이는 범위뿐입니다. 저희는 "네임스페이스 안에서 끝나는 일에 전역 권한 금지" 원칙으로 Role이 기본, ClusterRole은 Prometheus 등 소수만 씁니다.

**B2. RoleBinding과 ClusterRoleBinding의 4가지 조합을 설명해보세요.**
- **A**: RoleBinding+Role은 그 네임스페이스 권한, RoleBinding+ClusterRole은 전역 정의를 그 네임스페이스로 축소하는 재사용 패턴, ClusterRoleBinding+ClusterRole은 클러스터 전역 부여 — 이 3개는 가능합니다. ClusterRoleBinding+Role만 불가능한데, 전역 바인딩이 네임스페이스 스코프 역할을 가리키는 스코프 모순이라 API가 막습니다. 즉 "ClusterRole=무조건 전역"이 아니라, 전역 여부는 어떤 바인딩으로 붙이느냐가 결정합니다.

**B3. Deployment와 StatefulSet은 뭐가 다른가요?**
- **A**: 파드가 서로 대체 가능(무상태)하면 Deployment, 고유 신원·순서·전용 스토리지가 필요하면 StatefulSet입니다. 결정적 차이는 스토리지인데, Deployment는 기존 PVC를 참조(공유)만 하는 반면 StatefulSet은 volumeClaimTemplates로 파드마다 전용 PVC를 자동 생성해 재스케줄돼도 같은 볼륨에 다시 붙습니다. 웹/API는 Deployment, DB나 Prometheus처럼 데이터를 파드 곁에 남겨야 하면 StatefulSet입니다.

**B4. Deployment replica를 노드 수만큼 주면 DaemonSet과 같지 않나요?**
- **A**: 다릅니다. Deployment는 파드가 같은 노드에 몰릴 수 있고, 노드가 늘어나도 자동으로 따라 뜨지 않습니다. DaemonSet은 "노드당 정확히 1개 + 노드 증감 자동 추종"을 보장하므로, 노드마다 재야 의미가 있는 node-exporter 같은 워크로드는 반드시 DaemonSet이어야 관측 사각지대가 안 생깁니다.

**B5. Secret, SealedSecret, etcd 암호화는 각각 뭘 보호하나요?**
- **A**: 보호 구간이 다릅니다. SealedSecret은 Git에 올리는 이동·저장 구간을 공개키 암호로 보호하고, etcd Encryption at Rest는 클러스터 디스크·백업(at-rest) 구간을 보호하며, Secret 자체는 보호 장치가 아니라 파드로 값을 전달하는 통로입니다. SealedSecret이 컨트롤러에서 언실되면 결국 평범한 Secret으로 etcd에 남기 때문에 서로 대체가 안 되고 직렬로 겹쳐야 합니다.

**B6. PSA가 있는데 Kyverno는 왜 또 필요한가요?**
- **A**: PSA는 내장 어드미션의 3레벨 고정 프로파일이라 단순하고 예측 가능하지만 세밀한 조정이 안 됩니다. Kyverno는 "Harbor 레지스트리만 허용", "latest 태그 금지" 같은 임의 조건을 검사(validate)할 수 있고 수정(mutate)·생성(generate)까지 됩니다. 배타 관계가 아니라 PSA가 넓은 벽, Kyverno가 세밀 보완으로 병용하며, 저희는 PSA를 완화한 네임스페이스를 Kyverno로 다시 조입니다.

**B7. PV, PVC, StorageClass의 관계를 설명해보세요.**
- **A**: PVC는 "이만큼 이런 방식으로 쓰겠다"는 요청서, PV는 클러스터에 실존하는 스토리지 자원, StorageClass는 PVC 요청에 맞춰 PV를 자동으로 찍어내는 공장 설정입니다. 파드는 PV가 아니라 PVC를 마운트하고, PVC와 PV는 배타적 1:1로 바인딩됩니다. 스코프도 달라서 PVC만 네임스페이스 소속이고 PV·StorageClass는 클러스터 스코프입니다.

**B8. liveness, readiness, startup 프로브의 차이는?**
- **A**: 실패했을 때의 행동이 다릅니다. liveness 실패는 컨테이너 재시작(데드락·행 복구), readiness 실패는 재시작 없이 Service Endpoints에서 빼서 트래픽만 차단(회복 시 자동 복귀), startup은 성공하기 전까지 나머지 두 프로브를 정지시켜 느리게 시작하는 앱을 조기 킬에서 보호합니다. 운영 원칙은 "liveness는 자기 생존만 검사, DB 같은 외부 의존성은 readiness로"입니다.

**B9. ClusterIP와 Headless Service의 차이는?**
- **A**: ClusterIP는 대표 가상 IP(VIP) 하나를 만들고 kube-proxy가 뒤의 파드들로 로드밸런싱합니다. Headless(clusterIP: None)는 VIP도 로드밸런싱도 없이 DNS가 파드 IP 명단을 직접 반환합니다. "하나의 대표 vs 명단 전체"의 차이라서, 각 파드를 개별 지목해야 하는 StatefulSet에는 Headless가 필수입니다.

**B10. ResourceQuota와 LimitRange의 차이는?**
- **A**: ResourceQuota는 네임스페이스 전체 합계의 상한("requests 합 최대 16Gi"), LimitRange는 개별 컨테이너·파드·PVC 하나의 기본값·최소·최대("한 파드 최대 2Gi")입니다. CPU/메모리 Quota가 걸리는 순간 모든 새 파드는 requests/limits를 명시해야 하는데, 이때 LimitRange의 기본값 자동 주입이 누락 파드를 구제합니다. 그래서 둘은 항상 짝으로 배포합니다.

**B11. ServiceMonitor와 PodMonitor의 차이는?**
- **A**: ServiceMonitor는 Service를 라벨로 골라 그 뒤의 파드들을 긁고(Service 존재 + Service의 named port 필수), PodMonitor는 Service 없이 파드를 직접 라벨로 긁습니다. 기본은 ServiceMonitor, Service를 안 두는 DaemonSet 계열에는 PodMonitor가 자연스럽습니다. 주의할 점은 실제로 긁는 주체는 CRD가 아니라 Prometheus이고, CRD는 "대상 선언"일 뿐이라는 것입니다.

## C. 프로젝트 결정 근거 (8문항) — 가장 중요

**C1. 관측 네임스페이스는 PSA를 어떻게 잡았나요? (정정 반영 — 92 통합본 참조)**
- **A**: node-exporter가 /proc·/sys를, OTel Agent가 /var/log를 hostPath로 읽고 hostNetwork·hostPID도 쓰는데, 공식 Pod Security Standards상 이것들은 **baseline에서도 금지**라 이 DaemonSet들에는 사실상 privileged 레벨이 필요합니다. 당초 baseline으로 잡았다가 공식문서 재검증에서 이를 확인했고, privileged 범위를 최소화하려고 해당 DaemonSet만 별도 네임스페이스로 분리하는 방향으로 재조정 중입니다. dang-db-ns는 다릅니다 — DB 공식 이미지가 root로 도는 것은 restricted 전용 요구(runAsNonRoot) 위반일 뿐이라 baseline으로 충분합니다. 어느 경우든 SecurityContext 하드닝·Kyverno validate·NetworkPolicy 격리는 동일하게 유지합니다.
- **꼬리질문 대비**: "baseline이면 뭐까지 허용되나요?" → baseline은 privileged 컨테이너·host 네임스페이스·hostPath 같은 명백한 권한 상승 경로를 차단하되, runAsNonRoot·drop ALL·seccomp 명시는 요구하지 않습니다(restricted 전용) — 그 빈틈은 SecurityContext+Kyverno로 자발적으로 메웁니다.

**C2. 왜 Vault는 replica 1인데 Alertmanager는 3이죠?**
- **A**: 두 시스템의 합의 방식이 다르기 때문입니다. Vault의 Raft는 정족수(3노드) 기반이라 물리 호스트가 2대뿐인 우리 환경에서는 replica 3을 띄워도 호스트 하나가 죽으면 정족수가 깨지는 가짜 HA가 됩니다. 반면 Alertmanager는 gossip 프로토콜이라 정족수가 필요 없어 물리 2호스트에서도 HA가 유효합니다. 그래서 Vault는 StatefulSet 구조만 올바로 잡고 replica 1 PoC로 명시했고, Alertmanager는 3 replica + PDB minAvailable 2로 운영합니다.
- **꼬리질문 대비**: "그럼 Vault가 죽으면 어떻게 되나요?" → 런타임 동적 발급만 멈추고 정적 시크릿은 SealedSecret 계층이 담당하므로 부트스트랩은 무사 — `vault sealed` PrometheusRule 알람으로 조기 감지합니다.

**C3. Prometheus는 왜 StatefulSet이죠?**
- **A**: TSDB와 WAL을 로컬 디스크에 쓰는 상태 저장 워크로드이기 때문입니다. StatefulSet의 volumeClaimTemplates로 prometheus-0 전용 PVC가 자동 생성·고정되고, 파드가 재시작해도 같은 PVC에 다시 붙어 WAL을 이어받으므로 수집 공백과 데이터 유실을 막습니다. 공식 4조건 중 "안정적 영속 스토리지 + 안정적 신원"에 해당하는 전형적 사례입니다.
- **꼬리질문 대비**: "StatefulSet을 지우면 데이터도 날아가나요?" → 아니요, PVC/PV는 자동 삭제되지 않고 남아서 재배포하면 다시 붙습니다 — 완전 삭제는 PVC를 수동으로 지워야 합니다.

**C4. Grafana는 왜 Deployment죠? 대시보드는 어디 저장돼요?**
- **A**: Grafana를 의도적으로 무상태로 설계했기 때문입니다. 지표·로그 데이터 자체는 Prometheus·Loki 같은 각 수집기에 있고, 대시보드·데이터소스 설정은 provisioning 파일로 Git에 코드로 두었습니다. 그래서 파드가 죽어도 GitOps 재프로비저닝으로 동일하게 복원되며, 전용 PVC가 필요 없어 StatefulSet이 아닌 Deployment가 맞습니다.
- **꼬리질문 대비**: "UI에서 수정한 대시보드는요?" → provisioning이 원본이므로 UI 수정은 휘발 전제입니다 — 변경은 Git을 거치는 게 운영 원칙이고, 알람도 인프라 알람은 PrometheusRule(GitOps)로 표준화하는 방향입니다.

**C5. requests/limits 값은 어떻게 정했나요?**
- **A**: 도커 환경에서 실측한 관측치를 기반으로 하고, 워커 노드 용량(8Gi/2CPU)을 상한으로 잡았습니다. 임의 수치는 과소면 OOMKill, 과대면 스케줄 불가·자원 낭비라 양쪽 다 위험해서 실측이 유일한 근거라고 판단했습니다. LimitRange의 max가 이 상한을 admission에서 강제하고 defaultRequest가 누락을 자동으로 메웁니다. 최종 확정치는 K8s 이관 후 부하테스트로 재검증하는 전제입니다.
- **꼬리질문 대비**: "부하테스트는 왜 아직인가요?" → 도커 수치는 이미 있고 K8s 환경은 특성이 달라, 이관 완료 후 실환경에서 해야 의미가 있어 일정상 이월했습니다.

**C6. 시크릿 관리는 어떻게 설계했어요?**
- **A**: 3계층 직렬 방어입니다. ① SealedSecret이 Git 부트스트랩 구간(DB 초기 비밀번호, Harbor 자격증명)을 공개키 봉인으로 지키고, ② Vault가 런타임 동적 발급을 담당하며(물리 한계로 replica 1 PoC), ③ etcd Encryption at Rest가 최종 저장 구간을 지킵니다. 어느 계층을 거치든 최종 형태는 K8s Secret으로 etcd에 남기 때문에, ③이 없으면 etcd 스냅샷 하나가 곧 전체 유출이 됩니다.
- **꼬리질문 대비**: "SealedSecret이 있는데 etcd 암호화가 왜 또 필요하죠?" → SealedSecret은 Git 구간만 보호하고 언실 후엔 평문 Secret이 etcd에 남습니다 — 보호 구간이 달라 서로 대체 불가입니다.

**C7. CNI를 왜 Calico/Cilium으로 전제했나요?**
- **A**: NetworkPolicy가 우리 보안 설계의 축인데, 정책 지원 CNI가 없으면(flannel 단독 등) NetworkPolicy 리소스가 저장은 되지만 오류 없이 조용히 무시되기 때문입니다. 그러면 default-deny 3계층(fe→be→db)이 통째로 무효가 되는 치명적 리스크라 CNI 선정을 이관 전제조건으로 못박았습니다. 그래서 체크리스트에 "default-deny 적용 후 파드 간 연결 테스트로 실제 차단 확인"을 포함했습니다.
- **꼬리질문 대비**: "적용됐는지 어떻게 검증해요?" → 리소스 존재 ≠ 동작이므로, 정책 적용 후 실제 연결 테스트(수동 워크스루)로 차단 여부를 확인합니다.

**C8. 알람 규칙은 왜 PrometheusRule CRD로 관리하나요?**
- **A**: 알람을 UI 수기 설정이 아니라 Git(ArgoCD) 코드로 두면 리뷰·버전 관리·롤백이 가능해지기 때문입니다. Operator가 재시작 없이 반영해 주고, 잘못된 PromQL은 어드미션 웹훅이 생성 시점에 차단합니다. 대상은 up==0, 메모리 limit 90%, TLS 만료 임박, Vault sealed 같은 인프라·플랫폼 알람이고, 대시보드 밀착 알람만 Grafana Alerting에 남기는 소유권 구분이 진행 중입니다.
- **꼬리질문 대비**: "PrometheusRule만 만들면 슬랙 알람이 오나요?" → 아니요, CRD는 발화까지만 책임입니다 — 발송은 Alertmanager 라우팅/리시버 + default-deny 위 슬랙 egress 허용 + webhook 시크릿까지 갖춰져야 합니다.

## D. 실무 함정 (6문항)

**D1. enforce=restricted 네임스페이스에 위반 Deployment를 apply하면 어떻게 되나요?**
- **A**: apply 자체는 성공합니다. PSA의 enforce는 최종 파드에만 적용되기 때문에 Deployment 오브젝트는 저장되고, 그 밑에서 만들어지는 파드만 거부되어 replica 0으로 조용히 실패합니다. 공식 문서에 명시된 동작이고 가장 잘 걸리는 함정입니다. 그래서 저희는 warn·audit 모드를 같은 레벨로 함께 걸어 apply 시점에 경고가 보이게 했습니다.
- **꼬리질문 대비**: "그 조용한 실패는 어떻게 탐지해요?" → kube-state-metrics의 spec replica 대비 available replica 불일치 지표와 ReplicaSet의 FailedCreate 이벤트로 잡습니다.

**D2. 메모리 limit 초과와 CPU limit 초과는 어떻게 다르게 동작하나요?**
- **A**: 메모리는 비압축성 자원이라 limit을 초과하면 컨테이너가 OOMKill로 죽습니다. CPU는 압축성 자원이라 초과분이 throttle(속도 제한)될 뿐 죽지 않습니다. 그래서 메모리 limit은 실측 대비 여유를 두어야 하고, CPU limit은 상대적으로 관대해도 됩니다.
- **꼬리질문 대비**: "그럼 메모리 기반 HPA는 왜 잘 안 써요?" → JVM·캐시 계열은 부하가 빠져도 메모리를 반납하지 않아 스케일 다운이 안 됩니다 — 1차 지표는 CPU, 메모리는 limits로 OOM 방어만 합니다.

**D3. RWO PVC를 쓰는 파드가 여러 개 뜨면 어떻게 되나요?**
- **A**: RWO는 파드 단위가 아니라 노드 단위 제약입니다. 같은 노드에 스케줄된 파드들은 하나의 RWO PVC에 동시 접근할 수 있고, 다른 노드의 파드만 못 붙습니다. 단일 파드로 강제하려면 RWOP(ReadWriteOncePod)를 써야 합니다. 그래서 Deployment가 RWO PVC를 참조하면 replica가 다른 노드로 갈리는 순간 깨지므로 사실상 replica 1로 봐야 합니다.
- **꼬리질문 대비**: "PVC를 지우면 데이터도 지워지나요?" → reclaimPolicy에 달렸습니다 — Retain이면 PV가 Released로 남아 수동 정리가 필요하고, Delete(동적 프로비저닝 기본값)일 때만 실제 볼륨까지 삭제됩니다.

**D4. NetworkPolicy를 잘 짰는데 트래픽이 안 막힙니다. 원인이 뭘까요?**
- **A**: 십중팔구 CNI가 NetworkPolicy를 지원하지 않는 경우입니다. flannel 단독 같은 미지원 CNI에서는 정책 리소스가 저장은 되지만 오류 없이 조용히 무시됩니다. 그다음 후보는 policyTypes 누락입니다 — Egress를 명시하지 않으면 egress 규칙이 없는 한 나가는 트래픽은 그대로 열려 있습니다. 그래서 저희는 CNI를 전제조건으로 두고 적용 후 실제 연결 테스트로 검증합니다.
- **꼬리질문 대비**: "default-deny egress를 걸었더니 전부 장애가 났어요. 왜죠?" → DNS(kube-system CoreDNS, UDP/TCP 53) egress 허용을 빠뜨린 것 — default-deny egress 도입 시 가장 흔한 장애 원인이라 예외 1순위입니다.

**D5. kubectl drain이 끝나지 않고 무한 대기합니다. 왜죠?**
- **A**: PDB의 축출 여유가 0인 경우가 대표적입니다. 예를 들어 replica 3에 minAvailable: 3이면 어떤 파드도 축출할 수 없어 drain이 영원히 블록됩니다. minAvailable은 정족수 유지에 필요한 수까지만 잡고 축출 여유를 최소 1개는 남겨야 합니다 — 저희 Alertmanager가 replica 3 + minAvailable 2인 이유입니다.
- **꼬리질문 대비**: "그럼 kubectl delete pod로 지우면 되지 않나요?" → 지워지긴 하지만 Eviction API를 우회해 PDB 보호가 무력화됩니다 — 유지보수는 반드시 축출 경로(drain)로 하는 게 원칙입니다.

**D6. ServiceMonitor를 만들었는데 Prometheus targets에 안 뜹니다. 어디부터 보나요?**
- **A**: 90%는 라벨 매칭 문제라 순서대로 봅니다. ① Prometheus의 serviceMonitorSelector와 CRD 라벨 불일치, ② NamespaceSelector가 대상 네임스페이스 미포함, ③ ServiceMonitor의 selector와 Service 라벨 불일치, ④ port에 숫자를 적은 경우(Service의 named port여야 함). 그래도 안 되면 NetworkPolicy가 scrape 트래픽을 막는지 확인합니다 — default-deny 환경에서는 메트릭 포트 ingress 허용이 있어야 실제로 긁힙니다.
- **꼬리질문 대비**: "셀렉터를 빈 값({})으로 두면요?" → 빈 셀렉터는 전부 매치, null은 아무것도 매치 안 함 — 정반대 동작이라 주의해야 합니다.
