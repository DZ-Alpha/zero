## 🚨 먼저 읽기 — 재검증에서 바로잡은 것 1건

**기존 문서에 "obsv-ns는 hostPath 때문에 baseline"이라고 썼는데, 이건 틀렸습니다.**

무엇이 틀렸나:
- `hostPath`(노드의 디렉터리를 파드에 직접 붙이는 것)는 **baseline에서도 금지**입니다.
- `hostNetwork`·`hostPID`·`hostIPC`(노드의 네트워크·프로세스 공간을 그대로 쓰는 것)도 **baseline에서 금지**입니다.
- 공식 문서 원문: *"HostPath volumes must be forbidden"*, *"Sharing the host namespaces must be disallowed"*

그래서 어떻게 되나:
- node-exporter와 OTel Agent는 hostPath가 꼭 필요합니다. → **baseline 네임스페이스에서도 거부됩니다.**
- 이 둘에는 **privileged 레벨이 필요**합니다.
- 대신 privileged 범위를 최소로 줄이려고, **이 DaemonSet 2개만 별도 네임스페이스로 분리**하는 방향으로 재조정 중입니다.

반면 **`dang-db-ns`의 baseline은 그대로 맞습니다**:
- DB 공식 이미지가 root로 도는 것이 문제인데, "root 금지(runAsNonRoot)"는 **restricted에서만** 요구합니다.
- baseline은 root 실행을 허용하므로 baseline으로 충분합니다.

한 가지 더 — **"PVC를 쓰니까 완화해야 한다"는 논리는 틀렸습니다.** restricted가 허용하는 볼륨 목록에 **PVC는 포함**되어 있습니다. Prometheus가 PVC를 쓰는 것 자체는 restricted에서도 가능합니다.

**질문 받으면 이렇게 답하세요**
> "처음엔 baseline으로 잡았습니다. 그런데 공식문서를 재검증하다가 hostPath와 hostNetwork가 baseline에서도 금지라는 걸 확인했습니다. 그래서 hostPath를 쓰는 DaemonSet만 별도 네임스페이스로 분리해서, privileged가 필요한 범위를 최소로 줄이는 방향으로 재조정하고 있습니다."

→ 틀린 걸 숨기는 것보다 **검증해서 바로잡은 과정을 보여주는 것**이 훨씬 낫습니다.

### 그 밖에 반영한 세부 정정
- cert-manager의 `renewBefore`는 **기본값이 없습니다.** 기본 동작은 "인증서 수명의 2/3 지점에 갱신"입니다. 수명이 90일이면 결과적으로 만료 30일 전입니다.
- StatefulSet의 PVC는 기본적으로 **안 지워집니다.** v1.32에서 정식 기능이 된 `persistentVolumeClaimRetentionPolicy`로 자동 삭제를 켤 수는 있지만, 기본값은 보존입니다.
- Kyverno의 `failureAction`은 v1.13부터 생긴 **rule 단위 필드**입니다. 예전 `validationFailureAction`은 폐기 예정입니다.
- Service의 공식 타입은 **4개**(ClusterIP·NodePort·LoadBalancer·ExternalName)입니다. **Headless는 타입이 아니라 `clusterIP: None` 설정**입니다.

# 1부. 오브젝트 정리

## 1-1. 전체 지도 — 무엇이 무엇을 지키고, 무엇을 재는가

파드 하나가 뜨기까지 어떤 관문을 지나는지 순서대로 보면 전체가 잡힙니다.

```
[1] 파드를 만들어 달라고 요청하면 — 관문을 차례로 지납니다
    ① 인증: 너 누구야?           → SA(04)
    ② 인가: 그걸 할 권한 있어?    → Role(05)·ClusterRole(06)
                                    ⟵ RoleBinding·CRB(07)가 둘을 연결
    ③ 수정(Mutating): 값을 바꿔줌  → Kyverno mutate, Vault Injector
    ④ 검사(Validating): 규칙 위반? → PSA(01), Kyverno validate(12)
       ※ ③④의 동작 원리 = Admission Webhook(13). 수정이 항상 먼저.
    ⑤ 자원 검사: 예산 안에 들어와? → ResourceQuota(26)·LimitRange(27)
    ⑥ etcd에 저장 (암호화 10)
    → 이 모든 과정을 기록 = Audit Policy(14)

[2] 이미 떠 있는 파드를 지키는 것
    Namespace(23)   = 정책을 걸 자리
    NetworkPolicy(03) = 누구와 통신할 수 있나 (L3/L4)
    SecurityContext(02) = 어떤 권한으로 실행되나
    시크릿: SealedSecret(09) → Secret(08) → etcd 암호화(10)
    TLS: Certificate·Issuer(11)

[3] 파드를 실제로 돌리는 것
    Deployment(25)  = 무상태, 롤링 업데이트
    StatefulSet(15) = 고유 이름 + 파드 전용 볼륨
    DaemonSet(16)   = 노드마다 1개
    + Probes(19) 상태 점검 · HPA(20) 개수 자동조절
    + PDB(28) 동시 다운 제한 · Service(24) 고정 주소

[4] 재고 담는 것
    ServiceMonitor(17) 무엇을 긁을까 → PrometheusRule(18) 언제 울릴까 → Alertmanager 발송
    StorageClass(22) 공장 ─만듦→ PV(21) 실물 ⟵1:1─ PVC(21) 요청서 ⟵마운트─ 파드
```

## 1-2. 오브젝트 28종 상세

> 각 항목은 **한 줄 정의 → 무슨 문제를 푸나 → 어떻게 동작하나 → 자주 틀리는 것** 순서입니다.

### 🔴 Tier 1 · 보안 (01~14)

#### 01 PSA (Pod Security Admission)

**한 줄로** — 파드가 만들어질 때 보안 설정을 검사해서 통과·거부·경고를 결정하는 검문소입니다.

**무슨 문제를 푸나**
누구나 파드를 만들 수 있으면 root로 돌거나 노드 파일을 마음대로 읽는 파드도 뜹니다. PSA는 그런 파드를 **아예 만들어지지 못하게** 막습니다. 쿠버네티스에 **기본으로 들어있어서 따로 설치할 게 없습니다**(v1.25부터 정식). 예전에 쓰던 PSP를 대체했습니다.

**어떻게 동작하나**
- 검사 기준은 **네임스페이스에 붙인 라벨**입니다. 파드마다 설정하는 게 아닙니다.
- 라벨 형식: `pod-security.kubernetes.io/<모드>: <레벨>`
- **레벨 3개** — 위로 갈수록 엄격하고, 위 레벨은 아래를 포함합니다.
  - `privileged` : 아무 제한 없음
  - `baseline` : 명백히 위험한 것만 차단 (privileged 컨테이너, hostNetwork/hostPID/hostIPC, **hostPath**)
  - `restricted` : baseline + 하드닝 강제 (root 금지, 권한상승 금지, capability 전부 제거, seccomp 명시, 볼륨 타입 제한)
- **모드 3개** — 서로 독립적이라 동시에 걸 수 있습니다.
  - `enforce` : 위반하면 파드 거부
  - `audit` : 감사 로그에만 기록
  - `warn` : 경고만 표시
  - 활용 예: `enforce=baseline` + `warn=restricted` → 지금은 baseline만 막지만, restricted로 올릴 준비가 됐는지 미리 봅니다.

**⚠️ 가장 자주 틀리는 것**
`enforce`는 **최종 파드에만** 적용됩니다. Deployment 같은 워크로드 오브젝트에는 적용되지 않습니다.
> 공식 문언: *"enforce mode is not applied to workload resources, only to the resulting pod objects"*

그래서 이런 일이 벌어집니다:
1. 규칙을 위반한 Deployment를 apply 한다 → **성공합니다.**
2. 그런데 그 밑에서 만들어지는 파드는 거부된다.
3. 결과적으로 **replica가 0인 채로 조용히 실패**합니다. 에러 메시지도 안 보입니다.

→ 그래서 `warn`·`audit`을 같은 레벨로 함께 겁니다. 이 둘은 워크로드 오브젝트에도 적용돼서 **apply 시점에 경고가 보입니다.**

**그 외**
- `pod-security.kubernetes.io/<모드>-version` 라벨로 기준 버전을 고정할 수 있습니다. 클러스터를 업그레이드했는데 기준이 몰래 강화돼서 파드가 안 뜨는 사고를 막습니다.
- 예외가 필요하면 AdmissionConfiguration에서 특정 사용자·네임스페이스를 면제할 수 있습니다.

#### 02 SecurityContext

**한 줄로** — 파드나 컨테이너가 **어떤 권한으로 실행될지** 매니페스트에 적는 필드입니다.

**PSA와의 관계**
PSA가 "검문소"라면, SecurityContext는 **검문을 통과하기 위해 채우는 실제 값**입니다. PSA는 기준을 정하고, SecurityContext는 그 기준을 만족시킵니다.

**하드닝 4종 세트** (restricted를 통과하려면 이 4개가 필요합니다)

| 필드 | 하는 일 |
| --- | --- |
| `runAsNonRoot: true` | UID가 0(root)이면 실행을 거부 |
| `allowPrivilegeEscalation: false` | 실행 중에 권한을 더 얻는 것을 차단 |
| `capabilities.drop: [ALL]` | 리눅스 커널 권한을 전부 제거 |
| `seccompProfile.type: RuntimeDefault` | 위험한 시스템콜을 커널이 차단 |

**각각 더 알아둘 것**
- `runAsNonRoot`는 **"root면 거부"라는 검사**일 뿐입니다. 실제로 어떤 UID로 돌릴지는 `runAsUser: 1000` 같은 걸로 따로 지정합니다. 검사만 켜고 이미지가 root면 컨테이너가 아예 시작을 못 합니다(CreateContainerError).
- `allowPrivilegeEscalation: false`는 리눅스의 `no_new_privs`를 켭니다. setuid 같은 방법으로 부모보다 높은 권한을 얻는 걸 막습니다. 단, `privileged: true`가 켜져 있으면 무력화됩니다.
- `capabilities.drop: [ALL]` 후 필요한 것만 `add`로 되살립니다. restricted에서 되살릴 수 있는 건 `NET_BIND_SERVICE`(1024 미만 포트를 여는 권한) 하나뿐입니다.
- `seccompProfile`은 restricted에서 **반드시 명시**해야 합니다. 안 적어도 안 되고, `Unconfined`도 안 됩니다.

**적용 위치가 두 군데입니다**
- 파드 레벨(`spec.securityContext`) : runAsUser, fsGroup 같은 공통 설정
- 컨테이너 레벨(`spec.containers[].securityContext`) : privileged, capabilities, readOnlyRootFilesystem 같은 개별 설정
- **겹치면 컨테이너 레벨이 이깁니다.** 공식 문언: *"they override settings made at the Pod level when there is overlap"*

**⚠️ 자주 틀리는 것**
`readOnlyRootFilesystem`은 좋은 설정이지만 **restricted의 필수 조건이 아닙니다.** "필수"와 "권장"을 구분하는지가 검증 포인트입니다. 무작정 켜면 임시 파일을 쓰는 앱이 깨지므로, `emptyDir`로 쓰기가 필요한 경로만 열어주고 개별 적용합니다.

#### 03 NetworkPolicy

**한 줄로** — 어떤 파드가 어떤 대상과 통신할 수 있는지를 정하는 **파드 단위 방화벽**입니다.

**무슨 문제를 푸나**
쿠버네티스는 기본적으로 **모든 파드가 모든 파드와 통신할 수 있습니다.** 프론트엔드 파드가 DB에 직접 붙을 수도 있습니다. NetworkPolicy로 필요한 통신만 열어줍니다.

**어떻게 동작하나 — 화이트리스트 모델**
1. 기본 상태의 파드는 **비격리**입니다. 전부 열려 있습니다.
2. 어떤 정책이 그 파드를 **선택하는 순간** 격리됩니다.
3. 격리되면 **명시적으로 허용한 트래픽만** 통과합니다.

**⚠️ 자주 틀리는 것 4가지**

**① CNI가 지원해야 동작합니다 — 1순위 원인**
정책을 구현하는 네트워크 플러그인(Calico, Cilium 등)이 없으면 어떻게 될까요? 리소스는 **저장은 되는데 아무 효과가 없습니다.** 에러도 안 납니다.
> 공식 문언: *"without a controller that implements it will have no effect"*

flannel만 쓰는 클러스터에서 "정책 잘 짰는데 왜 안 막히지?" 하는 경우가 대부분 이겁니다.

**② deny 규칙이 없습니다**
여러 정책이 한 파드를 선택하면 **허용의 합집합**이 됩니다. 우선순위도, "이건 막아라"라는 규칙도 없습니다.
→ 차단하려면 **default-deny를 먼저 깔고**(`podSelector: {}` + 허용 규칙 없음) 필요한 것만 여는 방식뿐입니다.

**③ policyTypes를 생략하면 Egress가 안 걸립니다**
- Ingress는 생략해도 항상 설정됩니다.
- **Egress는 egress 규칙이 있을 때만** 설정됩니다.
→ 나가는 트래픽을 막으려면 `policyTypes`에 `Egress`를 **반드시 명시**해야 합니다.

**④ 양쪽이 다 허용해야 합니다**
A가 B에 접속하려면, A의 **egress 허용**과 B의 **ingress 허용**이 **둘 다** 있어야 합니다. 한쪽만 열면 안 됩니다.

**그 외**
- L3/L4(IP·포트)까지만 됩니다. "이 HTTP 경로만 허용" 같은 L7 제어는 서비스 메시 영역입니다.
- default-deny egress를 걸었을 때 **가장 흔한 장애는 DNS 예외 누락**입니다. kube-system의 CoreDNS로 나가는 53번 포트(UDP·TCP 둘 다)를 반드시 열어야 합니다.

#### 04 SA (ServiceAccount)

**한 줄로** — 파드가 쿠버네티스 API 서버에 자기 신원을 증명할 때 쓰는 **기계용 신분증**입니다.

**알아둘 사실 하나** — 쿠버네티스에는 **사람용 User 오브젝트가 아예 없습니다.**
> 공식 문언: *"Normal users cannot be added to a cluster through an API call"*

사람은 인증서나 OIDC 같은 외부 수단으로 인증하고, 워크로드는 SA로 인증합니다. 역할이 갈립니다.

**어떻게 동작하나**
- 네임스페이스마다 `default` SA가 자동으로 만들어집니다.
- 파드가 SA를 지정하지 않으면 이 `default`가 자동으로 붙고, **토큰까지 파드 안에 마운트**됩니다. (`/var/run/secrets/kubernetes.io/serviceaccount`)
- 즉 **아무 설정도 안 하면 모든 파드가 API 토큰을 들고 있습니다.** 이게 기본 리스크입니다.

**그래서 해야 할 것**
- API를 안 쓰는 워크로드는 `automountServiceAccountToken: false`로 토큰 주입을 끕니다. 파드가 털려도 토큰이 없으니 피해가 없습니다.
- SA와 파드 양쪽에 설정할 수 있는데, 겹치면 **파드 spec이 이깁니다.**

**⚠️ 인증과 인가는 다릅니다**
- SA는 **"누구인가"만** 증명합니다.
- **"무엇을 할 수 있는가"는 RoleBinding으로 따로 연결**해야 생깁니다. 연결 전에는 권한이 0입니다.
- 반대로 권한이 없어도 **토큰이 마운트돼 있다는 것 자체가 리스크**입니다. 신분이 노출되니까요.

**검증 방법**
```
kubectl auth can-i get pods --as=system:serviceaccount:<네임스페이스>:<SA이름>
```

#### 05 Role

**한 줄로** — **한 네임스페이스 안에서** "어떤 리소스에 어떤 동작을 허용할지" 모아놓은 권한 묶음입니다.

**규칙의 구성 — 3개가 다 맞아야 허용**
```yaml
rules:
- apiGroups: [""]           # 어느 API 그룹
  resources: ["pods"]        # 어떤 리소스
  verbs: ["get","list"]      # 어떤 동작
```

**⚠️ `""`(빈 문자열)의 의미**
"모든 그룹"이 아니라 **core 그룹**입니다. pods·services·configmaps·secrets 등이 여기 들어갑니다. 흔한 오해입니다.

**verbs 고를 때 주의**
- 읽기: get / list / watch
- 쓰기: create / update / patch / delete
- **`list`는 객체 본문까지 다 보여줍니다.** secrets에 list를 주면 값이 전부 새는 것과 같습니다. get과 별개로 신중히 판단해야 합니다.

**⚠️ RBAC에는 "거부"가 없습니다**
- 명시하지 않은 건 전부 거부입니다(기본 거부).
- 그런데 규칙은 **더하기만** 됩니다. 한 번 열어준 걸 다른 규칙으로 좁힐 수 없습니다.
- → **처음부터 좁게 주는 것이 유일한 방어**입니다.

**그 외**
- Role만 만들면 아무 효과가 없습니다. **RoleBinding으로 연결**해야 권한이 생깁니다.
- Node나 PV처럼 네임스페이스에 속하지 않는 리소스는 Role로 못 다룹니다. ClusterRole 영역입니다.

#### 06 ClusterRole

**한 줄로** — **네임스페이스 경계가 없는** 권한 묶음입니다.

**Role과 뭐가 다른가**
규칙 문법은 **완전히 같습니다.** 차이는 범위뿐입니다. ClusterRole은 이런 것까지 다룰 수 있습니다:
- 네임스페이스에 속하지 않는 리소스 — Node, PV, StorageClass
- 여러 네임스페이스를 가로지르는 권한
- 리소스가 아닌 URL 경로 — `/metrics`, `/healthz` (이건 ClusterRole 전용입니다)

**⚠️ 가장 많이 틀리는 것 — ClusterRole이 무조건 전역인 게 아닙니다**

범위는 **어떤 바인딩으로 붙이느냐**가 결정합니다.

| 붙이는 방법 | 실제 범위 |
| --- | --- |
| ClusterRoleBinding으로 붙임 | 클러스터 전역 |
| **RoleBinding으로 붙임** | **그 네임스페이스로 축소** |

→ 이 성질 덕분에 "공용 권한 템플릿을 하나 정의해두고 여러 네임스페이스에서 재사용"하는 패턴이 가능합니다.

**그 외**
- 한 규칙에는 `resources` 또는 `nonResourceURLs` 중 **하나만** 쓸 수 있습니다.
- 기본 제공 ClusterRole: `cluster-admin`(사실상 root — 부여에 극도로 주의) / `admin` / `edit` / `view`
- 집계(aggregation): 라벨로 작은 ClusterRole들을 자동 합칠 수 있습니다. CRD 권한을 admin/edit/view에 얹을 때 씁니다.

**우리 프로젝트에서 왜 필요한가**
Prometheus와 kube-state-metrics는 ① 전체 네임스페이스의 Pod·Service·Endpoints를 찾아야 하고 ② Node(네임스페이스 없음)를 읽어야 하고 ③ `/metrics` URL에 접근해야 합니다. **Role로는 셋 다 불가능**해서 ClusterRole이 필요합니다.

#### 07 RoleBinding & ClusterRoleBinding

**한 줄로** — 권한 묶음(Role/ClusterRole)을 **대상(SA·User·Group)에 연결하는 전선**입니다.

**구조**
- 권한 내용은 Role 쪽에 있습니다.
- 바인딩은 권한을 **담지 않고 연결만** 합니다.
- "무엇을(Role)"과 "누구에게(Binding)"를 분리한 설계입니다.

**⚠️ 4가지 조합 — 시험 단골**

| 바인딩 | 참조하는 것 | 가능? | 결과 |
| --- | --- | --- | --- |
| RoleBinding | Role | ✅ | 그 네임스페이스 안에서만 |
| RoleBinding | ClusterRole | ✅ | 전역 정의를 **그 ns로 축소** (재사용 패턴) |
| ClusterRoleBinding | ClusterRole | ✅ | 클러스터 전역 |
| ClusterRoleBinding | Role | ❌ | **이것만 불가능** |

**왜 마지막만 안 되나?** 전역 바인딩이 네임스페이스 한정 역할을 가리키는 건 범위가 모순이라서, API가 아예 막습니다.
> API 레퍼런스: *"RoleRef can only reference a ClusterRole"*

**그 외**
- `roleRef`는 **바꿀 수 없습니다.** 다른 Role을 가리키게 하려면 바인딩을 지우고 새로 만들어야 합니다. 실수로 권한 대상이 바뀌는 걸 막는 설계입니다.
- **`default` SA에 권한을 주면 안 됩니다.** SA를 지정하지 않은 모든 파드가 그 권한을 물려받는 사고가 됩니다.

#### 08 Secret

**한 줄로** — 비밀번호·API 키·인증서 같은 **민감한 소량 데이터**를 파드 정의와 분리해서 저장하는 오브젝트입니다.

**목적을 정확히 알기**
Secret의 목적은 **"분리"**이지 **"암호화"가 아닙니다.** 이걸 헷갈리면 보안 설계가 통째로 어긋납니다.

**⚠️ base64는 암호화가 아닙니다**
- `data` 값은 그냥 인코딩입니다. 누구나 디코드합니다.
- 게다가 **기본 설정에서는 etcd에 평문으로 저장**됩니다(공식 문서 명시).
- → 실제 보호는 **RBAC 최소권한 + etcd Encryption at Rest**를 켜야 완성됩니다.

**`data` vs `stringData`**
- `data` : base64로 인코딩해서 넣습니다.
- `stringData` : 평문으로 넣으면 API 서버가 인코딩해줍니다.
- **편의 차이일 뿐 보안 차이는 없습니다.**

**타입 = "어떤 키가 있어야 하는가"의 약속**

| 타입 | 필수 키 | 용도 |
| --- | --- | --- |
| `Opaque` | 자유 | 기본값 |
| `kubernetes.io/dockerconfigjson` | `.dockerconfigjson` | 이미지 pull 인증 |
| `kubernetes.io/tls` | `tls.crt`, `tls.key` | TLS 인증서 |

→ imagePullSecret을 `Opaque`로 만들면 **kubelet이 인식하지 못합니다.**

**파드에 넣는 방법 2가지**
- **환경변수** : 파드가 재시작할 때까지 값이 고정됩니다.
- **볼륨 마운트** : tmpfs(메모리)에 올라가고, Secret을 바꾸면 반영됩니다. 단 **subPath로 마운트하면 갱신이 안 됩니다.**

**그 외** — 크기 제한 1MiB. ConfigMap과 API 구조는 거의 같고, "민감하니까 다르게 취급한다"는 의미가 다릅니다(필요한 노드에만 전달, tmpfs 사용). **자동으로 안전해지는 건 아닙니다.**

#### 09 SealedSecret (Bitnami Sealed Secrets)

**한 줄로** — Secret을 클러스터의 **공개키로 암호화해서 Git에 안전하게 올릴 수 있게** 만드는 CRD입니다.

**무슨 문제를 푸나**
GitOps는 "모든 것을 Git에" 두는 방식인데, Secret만은 올릴 수가 없습니다. base64는 암호화가 아니니까요. SealedSecret이 이 문제를 풉니다.

**어떻게 동작하나 — 비대칭 암호**
1. `kubeseal` 명령이 **공개키로 암호화**합니다. → 공개 저장소에 올려도 안전합니다.
2. 클러스터 안의 컨트롤러만 **개인키(sealing key)를 갖고 있어서** 복호화합니다.
3. 복호화 결과로 **평범한 Secret이 만들어집니다.**

개인키는 클러스터를 절대 벗어나지 않습니다. 봉인한 사람조차 다시 열 수 없습니다.

**봉인 범위 3종**

| 스코프 | 의미 |
| --- | --- |
| `strict` (기본) | 이름 + 네임스페이스까지 고정. 다른 곳에 옮겨 심을 수 없음 |
| `namespace-wide` | 같은 ns 안에서는 이름 변경 가능 |
| `cluster-wide` | 어디든 가능 |

느슨할수록 편하지만 격리가 무너집니다.

**⚠️ 운영의 전부는 sealing key 관리입니다**
- 키는 **기본 30일마다 갱신**되고, 옛 키는 계속 보존됩니다.
- 그래서 백업 대상은 "최신 키 하나"가 아니라 **쌓인 키 전체**입니다.
- **키를 잃으면 Git에 있는 모든 SealedSecret을 영원히 못 엽니다.**
- 백업 키가 있으면 클러스터 없이도 복구할 수 있습니다: `kubeseal --recovery-unseal --recovery-private-key`

**⚠️ etcd 암호화를 대체하지 않습니다**
컨트롤러가 열고 나면 결국 **평범한 Secret이 etcd에 남습니다.**
- SealedSecret : **Git 이동·저장** 구간 보호
- etcd 암호화 : **클러스터 저장** 구간 보호
- → 구간이 다르므로 **둘 다** 필요합니다.

**그 외** — 다른 클러스터에 그대로 복사할 수 없습니다. 그 클러스터의 공개키로 봉인됐기 때문에, 키를 옮기거나 다시 봉인해야 합니다.

#### 10 etcd Encryption at Rest

**한 줄로** — API 서버가 Secret을 **etcd에 쓰기 전에 암호화**하도록 하는 컨트롤플레인 설정입니다.

**무슨 문제를 푸나**
이걸 안 켜면, **etcd 데이터 파일이나 백업 스냅샷 하나만 손에 넣으면** 클러스터의 모든 Secret을 평문으로 읽을 수 있습니다.

**⚠️ 기본값은 암호화 꺼짐입니다**
기본 프로바이더가 `identity`(= 평문)입니다. `EncryptionConfiguration` 파일을 만들고 `--encryption-provider-config`로 API 서버에 넘겨야 켜집니다.

**⚠️ 순서 규칙 — 가장 중요**
- 목록의 **첫 번째 프로바이더만** 새로 쓰는 데이터를 암호화합니다.
- 읽을 때는 목록을 **순서대로 전부 시도**합니다.
- → `identity`가 맨 앞에 있으면 **암호화가 꺼진 것**입니다.

키를 교체하는 순서:
1. 새 키를 목록 **맨 앞에** 추가
2. API 서버 재시작
3. 기존 데이터 전체 재기록
4. 옛 키 제거

**⚠️ 소급 적용이 안 됩니다**
설정을 켜도 **이미 저장된 Secret은 평문 그대로**입니다. 다음 명령으로 전부 다시 써야 실제로 암호화됩니다:
```
kubectl get secrets -A -o json | kubectl replace -f -
```
"설정만 켜면 안전하다"가 대표적인 착각입니다.

**프로바이더 선택**

| 종류 | 설명 |
| --- | --- |
| `aescbc` | 공식 문서에서 padding oracle 취약성으로 **비권장** |
| `aesgcm` | 20만 번 쓸 때마다 키 교체 필요 |
| `secretbox` | 무난 |
| `kms` v2 | **권장** — 키를 클러스터 밖 KMS에 분리 보관 |

**⚠️ 로컬 프로바이더의 한계**
키가 마스터 노드의 설정 파일에 그대로 있습니다. 노드 root를 뺏기면 무력합니다. **진짜 키 분리는 KMS만 가능**합니다.

**⚠️ RBAC을 대체하지 않습니다**
API로 조회하면 API 서버가 복호화해서 돌려줍니다. etcd 암호화는 **디스크·백업** 방어이고, API 접근 방어는 RBAC입니다. 층이 다릅니다.

#### 11 Certificate · Issuer (cert-manager)

**한 줄로** — TLS 인증서를 **자동으로 발급하고 자동으로 갱신**해주는 CRD 짝입니다.

**진짜 가치는 갱신입니다**
최초 발급은 수동으로도 됩니다. 문제는 **만료**입니다. 수동 인증서는 언젠가 반드시 만료 장애를 냅니다. cert-manager는 이걸 자동화합니다.

**두 오브젝트의 역할**
- `Issuer` / `ClusterIssuer` = **발급 기관**
- `Certificate` = **요청서**

**Issuer vs ClusterIssuer**
- `Issuer`는 네임스페이스 소속이라 **같은 ns의 Certificate만** 참조할 수 있습니다. 다른 ns의 Issuer를 참조하려다 실패하는 게 흔한 발급 오류입니다.
- `ClusterIssuer`는 전역이라 여러 ns가 공유합니다.

**Issuer 종류**
- ACME : Let's Encrypt 등 공인 인증서. HTTP-01 또는 DNS-01 챌린지로 도메인 소유를 증명합니다.
- CA / SelfSigned : 사내 PKI, mTLS용
- Vault 등

**발급 과정**
```
Certificate 생성 → 개인키 + CertificateRequest 생성 → Issuer가 서명
→ kubernetes.io/tls 타입 Secret(tls.crt, tls.key)에 저장
```
ACME는 중간에 Order·Challenge 단계가 추가됩니다.

**갱신 동작**
- 기본 수명 90일
- 기본 동작은 **수명의 2/3 지점에 갱신 시작** (= 만료 30일 전)
- `renewBefore`는 **기본값이 없습니다.** 명시하면 그 값이 우선합니다.
- 갱신할 때 Certificate·Secret 오브젝트는 그대로 있고 **Secret 안의 내용물만 교체**됩니다. Ingress는 Secret 이름만 참조하므로 대개 무중단입니다.

**⚠️ `ca.crt`가 두 종류라 헷갈립니다**

| 어디 있는 것 | 무엇 | cert-manager와 관계 |
| --- | --- | --- |
| 파드에 자동 마운트되는 것 | 클러스터 PKI의 CA. API 서버 검증용 | **무관** |
| TLS Secret 안에 있는 것 | cert-manager의 CA가 인증서를 서명한 것 | 관련 |

이 둘을 섞으면 TLS 디버깅이 미궁에 빠집니다.

**그 외** — 9402 포트로 Prometheus 메트릭(인증서 만료 시각, ready 상태)을 노출합니다. **"자동 갱신이 실패한 것"까지 관측으로 잡아야 완성**입니다.

#### 12 Kyverno Policy · ClusterPolicy

**한 줄로** — "리소스가 지켜야 할 규칙"을 **쿠버네티스 YAML 그대로** 선언하는 정책 엔진입니다.

**무슨 문제를 푸나**
"Harbor 레지스트리 이미지만 허용", "latest 태그 금지" 같은 조직 규칙을 강제하고 싶은데, PSA로는 안 됩니다(3레벨 고정이라 세밀 조정 불가). 원래는 webhook 서버를 직접 만들어야 했는데, Kyverno는 **YAML만 쓰면 됩니다.** 정책이 Git·PR 리뷰 대상이 됩니다.

**할 수 있는 4가지**
- `validate` : 규칙 위반 검사
- `mutate` : 값을 자동으로 수정
- `generate` : 리소스를 자동 생성 (예: 새 ns마다 default-deny 정책 자동 생성)
- `verifyImages` : 이미지 서명 검증

**규칙 구조**
- 각 rule = `match`(+선택적 `exclude`) + 위 4종 중 **정확히 하나**
- `ClusterPolicy` = 클러스터 전역 / `Policy` = 네임스페이스 범위

**단계적 도입이 정석**
`failureAction` (v1.13+ rule 단위 필드. 예전 `validationFailureAction`은 폐기 예정)
- `Audit` : 허용하되 PolicyReport에 기록
- `Enforce` : 요청 차단

→ **Audit으로 먼저 관측 → 위반이 없어지면 Enforce로 승격**. 바로 Enforce를 걸면 기존 워크로드가 배포 불가가 됩니다.

**그 외 동작**
- 정책 내용에 맞춰 webhook을 **좁게 자동 등록**합니다. 매칭되는 정책이 없는 요청은 Kyverno까지 오지도 않습니다.
- **mutate가 validate보다 먼저** 실행됩니다(어드미션 순서가 Mutating→Validating). mutate 결과가 validate 규칙과 모순되면 안 됩니다.
- background scan : 새 요청뿐 아니라 **이미 있는 리소스**도 주기적으로 검사해 PolicyReport를 만듭니다.

**PSA와의 관계 — 배타가 아니라 보완**

| | PSA | Kyverno |
| --- | --- | --- |
| 성격 | 내장, 3레벨 고정 | CRD, 임의 조건 |
| 조정 | 세밀 조정 불가 | 자유롭게 |
| 기능 | 검사만 | 검사 + 수정 + 생성 |

→ **PSA는 넓은 벽, Kyverno는 세밀 보완**으로 같이 씁니다.

**⚠️ Kyverno 파드가 죽으면?**
webhook의 `failurePolicy`에 달렸습니다. `Fail`이면 매칭되는 요청이 전부 막힐 수 있습니다. → **Kyverno 자신과 kube-system은 정책 대상에서 제외**하는 게 안전합니다.

#### 13 Admission Webhook

**한 줄로** — API 서버가 리소스를 저장하기 **직전에** 외부 서비스를 호출해 요청을 검사하거나 수정하게 하는 확장 지점입니다.

**왜 알아야 하나**
직접 만들 일은 없습니다. 하지만 **Kyverno·cert-manager·Vault Injector가 전부 이 위에서 동작**하므로, 문제가 생겼을 때 원리를 알아야 고칠 수 있습니다.

**처리 순서**
```
인증 → 인가 → Mutating(수정) → 스키마 검증 → Validating(검사) → etcd 저장
```
- **Mutating이 항상 먼저**입니다. 수정이 끝난 최종 결과를 검사해야 하니까요.
- **Validating은 오브젝트를 바꿀 수 없습니다.** 통과/거부만 합니다.

**동작 방식**
API 서버가 AdmissionReview JSON을 HTTPS로 webhook에 POST → webhook이 허용/거부 또는 수정 내용(JSONPatch)을 응답합니다.

**⚠️ `failurePolicy` — 운영에서 제일 중요**

webhook이 죽거나 응답이 없을 때:

| 값 | 동작 | 위험 |
| --- | --- | --- |
| `Fail` (**기본값**) | 요청 거부 | **클러스터 마비** 가능 |
| `Ignore` | 그냥 통과 | 정책이 안 걸림 |

webhook은 **요청 경로 위의 단일 장애점**입니다. 그래서 kube-system은 제외하고, `namespaceSelector`로 범위를 좁히는 게 필수입니다.

**그 외**
- `timeoutSeconds` 기본 10초(1~30 설정 가능, 짧게 권장)
- `reinvocationPolicy: IfNeeded` (Mutating 전용) : 다른 플러그인이 오브젝트를 또 바꾸면 재호출
- **용어 구분** — Admission Controller는 API 서버 안에 내장된 플러그인들이고, 그중 `MutatingAdmissionWebhook`·`ValidatingAdmissionWebhook` 두 개가 외부 webhook을 호출하는 창구입니다. (`ValidatingAdmissionPolicy`는 CEL 기반 내장 검증으로 **별개 기능**입니다.)

#### 14 Audit Policy (감사 로깅)

**한 줄로** — API 서버를 거치는 모든 요청을 **"누가·언제·무엇을·어디서·결과"**로 기록하는 설정입니다.

**무슨 문제를 푸나**
앱 로그는 컨테이너 안에서 일어난 일만 알려줍니다. **"누가 이 Secret을 읽었나", "누가 이 RBAC을 바꿨나"** 는 감사 로그만 답할 수 있습니다.

**기록 레벨 4단계** — 아래로 갈수록 상세하고 로그량이 폭증합니다.

| 레벨 | 기록 내용 |
| --- | --- |
| `None` | 기록 안 함 |
| `Metadata` | 요청자·시각·리소스·동작 |
| `Request` | + 요청 본문 |
| `RequestResponse` | + 응답 본문 |

**⚠️ 첫 매칭이 이깁니다 — 순서가 곧 정책**
규칙을 위에서부터 평가해서 **처음 일치한 규칙의 레벨**이 적용됩니다.
- 구체적인 예외를 **위에**, 전체 포괄(catch-all)을 **맨 아래**에 둡니다.
- catch-all을 맨 위에 두면 **아래 규칙은 영원히 도달하지 못합니다.**

**⚠️ Secret은 반드시 Metadata로만**
`RequestResponse`로 남기면 응답 본문에 **Secret 값이 그대로 들어갑니다.** 감사 로그 자체가 새로운 유출 경로가 됩니다.

→ 민감 리소스는 최소로, 반복되는 watch는 None으로 — **차등 기록이 설계의 핵심**입니다.

**그 외**
- 4개 스테이지: RequestReceived / ResponseStarted(watch 같은 장시간 요청) / ResponseComplete / Panic. `omitStages`로 중복을 뺍니다.
- **기본은 꺼져 있습니다.** `--audit-policy-file` + 백엔드 플래그(`--audit-log-path` 등)를 명시해야 켜집니다.
- 보관 설정: `-maxage` / `-maxbackup` / `-maxsize`

### 🔵 Tier 2 · 모니터링 (15~22)

#### 15 StatefulSet

**한 줄로** — 파드마다 **바뀌지 않는 이름**과 **파드 전용 볼륨**을 보장하는 컨트롤러입니다.

**언제 쓰나 — 공식 4조건**
아래 중 **하나라도** 필요하면 StatefulSet, 아니면 Deployment입니다.
1. 안정적이고 고유한 네트워크 이름
2. 안정적인 영속 스토리지
3. 순서를 지키는 배포·스케일링
4. 순서를 지키는 롤링 업데이트

**어떻게 동작하나**
- 파드 이름이 `<이름>-<번호>`로 고정됩니다(0부터). 재스케줄돼도 이름이 유지됩니다.
- **`volumeClaimTemplates`** : 템플릿 1개를 적으면 **파드마다 PVC가 자동으로 만들어집니다.**
  - 예: 템플릿 `www` + 파드 `web-0/1/2` → PVC `www-web-0`, `www-web-1`, `www-web-2`
  - 파드가 죽었다 살아나도 **같은 PVC에 다시 붙어서** 데이터가 이어집니다.
  - → Deployment가 "기존 PVC를 공유 참조"하는 것과 **결정적으로 다른 점**입니다.

**Headless Service가 필수입니다**
- `clusterIP: None`인 Service를 **사용자가 직접 만들어서** `serviceName`에 지정해야 합니다.
- 그래야 `web-0.<서비스명>.<ns>.svc.cluster.local` 같은 **파드별 고정 주소**가 생깁니다.

**⚠️ 볼륨은 안 지워집니다**
StatefulSet을 삭제하거나 스케일을 줄여도 **PVC와 PV는 기본적으로 남습니다.** 데이터 안전이 자동 정리보다 우선이라는 설계입니다.
(v1.32에서 정식이 된 `persistentVolumeClaimRetentionPolicy`로 자동 삭제를 켤 수 있지만, 기본값은 보존입니다.)

**순서 보장** — 기본 `OrderedReady`
- 늘릴 때: 0 → 1 → 2 순서로 하나씩
- 줄이거나 업데이트할 때: 역순

**⚠️ StatefulSet ≠ 자동 HA**
StatefulSet이 보장하는 건 **이름·순서·스토리지**뿐입니다. 복제, 정족수, 리더 선출은 **애플리케이션이 알아서** 해야 합니다(MySQL 복제, Raft 등). "StatefulSet 쓰면 HA된다"는 오해입니다.

#### 16 DaemonSet

**한 줄로** — 모든 노드(또는 조건에 맞는 노드)마다 파드를 **정확히 1개씩** 돌리는 컨트롤러입니다.

**무슨 문제를 푸나**
노드 자신의 지표·로그·디바이스는 **그 노드 위에서만** 접근할 수 있습니다. 그래서 노드마다 수집기가 하나씩 있어야 합니다. 목적이 "개수"가 아니라 **"빠짐없이"** 입니다.

**어떻게 동작하나**
- **replica 필드가 없습니다.** 노드 수가 곧 파드 수입니다.
- 노드가 추가되면 자동으로 파드가 생기고, 제거되면 자동으로 사라집니다.
- 일부 노드만 원하면 `nodeSelector`·`nodeAffinity`로 좁힙니다(기본은 전체).

**대표 용도** — node-exporter, 로그 수집기, CNI·CSI 플러그인

**알아둘 동작 2가지**
- **배치는 기본 스케줄러가 합니다.** 컨트롤러가 nodeAffinity를 주입하고 kube-scheduler가 배치합니다. 그래서 리소스 부족·우선순위가 정상 적용됩니다. ("DaemonSet은 스케줄러를 안 탄다"는 옛날 이야기입니다.)
- **톨러레이션이 자동으로 붙습니다.** cordon된 노드나 컨트롤플레인 노드에도 뜰 수 있습니다. 안 띄우려면 셀렉터로 좁혀야 합니다.

**⚠️ Deployment replica를 노드 수만큼 주면 안 되나?**
안 됩니다. 두 가지 이유입니다:
1. 파드가 **같은 노드에 몰릴 수 있습니다.**
2. 노드가 늘어나도 **자동으로 따라 뜨지 않습니다.**

**업데이트 전략** — `RollingUpdate`(기본, 노드별 하나씩) / `OnDelete`(수동 삭제 시 교체)

#### 17 ServiceMonitor · PodMonitor

**한 줄로** — "이 라벨이 붙은 Service(또는 Pod)를 이런 주기로 긁어라"를 선언하는 Prometheus Operator CRD입니다.

**무슨 문제를 푸나**
원래는 `prometheus.yml` 파일을 직접 고치고 Prometheus를 재시작해야 했습니다. CRD를 쓰면 **수집 대상을 쿠버네티스 오브젝트로 관리**할 수 있고, **재시작 없이** 반영됩니다.

**⚠️ 긁는 주체는 CRD가 아닙니다**
CRD는 "이런 걸 긁어달라"는 **의도만** 담습니다. Operator가 이걸 Prometheus 설정으로 번역하고, **실제로 긁는 건 Prometheus**입니다.

**⚠️ 누가 이 CRD를 볼지는 Prometheus가 정합니다**
Prometheus 오브젝트의 `serviceMonitorSelector` / `podMonitorSelector`가 라벨로 CRD를 고릅니다. 여기서 함정이 있습니다:

| 설정 | 의미 |
| --- | --- |
| `{}` (빈 셀렉터) | **전부 매치** |
| null (필드 미지정) | **아무것도 매치 안 함** |

정반대입니다. 주의하세요.

**ServiceMonitor vs PodMonitor**

| | ServiceMonitor | PodMonitor |
| --- | --- | --- |
| 대상 | Service를 골라 → 그 뒤 파드들 | 파드를 직접 |
| 필요한 것 | **Service가 있어야 함** | Service 불필요 |
| 포트 지정 | Service의 **named port** (숫자 불가) | 파드의 포트 |
| 적합한 곳 | 일반 워크로드 | DaemonSet, Job, 사이드카 |

**⚠️ 안 긁힐 때 점검 순서**
90%는 라벨 매칭 문제입니다. 순서대로 확인하세요:
1. Prometheus의 셀렉터 ↔ CRD의 라벨이 맞나?
2. NamespaceSelector에 대상 네임스페이스가 포함됐나?
3. CRD의 selector ↔ Service의 라벨이 맞나?
4. port에 숫자를 적지 않았나? (named port여야 함)
5. 여기까지 다 맞으면 → **NetworkPolicy가 scrape를 막고 있는지** 확인

**활용 패턴** — CRD는 워크로드와 같은 ns에 두고, 다른 ns의 Prometheus가 NamespaceSelector로 가로질러 찾습니다. GitOps에서 "워크로드 + 관측 설정"을 한 폴더에 두는 근거입니다.

#### 18 PrometheusRule

**한 줄로** — Prometheus의 **알림 규칙**과 **기록 규칙**을 쿠버네티스 오브젝트로 선언하는 CRD입니다.

**구조** — 하나의 PrometheusRule 안에 여러 RuleGroup, 그룹 안에 규칙들이 들어갑니다. 그룹마다 평가 주기(`interval`)를 정할 수 있습니다.

**알림 규칙(alerting rule)의 필드**

| 필드 | 의미 |
| --- | --- |
| `alert` | 알람 이름 |
| `expr` | PromQL 조건 |
| `for` | **이 시간 동안 계속 참이어야** 발화 (순간적으로 튀는 오탐 방지) |
| `labels` | severity 등 — Alertmanager 라우팅에 씀 |
| `annotations` | 사람이 읽을 설명 |

**기록 규칙(recording rule)** — `record` + `expr`의 결과를 **새 시계열로 저장**합니다. 알람은 안 울립니다. 자주 쓰거나 무거운 쿼리를 미리 계산해두는 용도입니다. 이름 관례는 `level:metric:operations`입니다.

**⚠️ 역할 분담 — 단골 문제**

| 하는 일 | 담당 |
| --- | --- |
| 규칙 평가하고 발화 | **Prometheus** |
| 중복제거·그룹핑·라우팅·발송 | **Alertmanager** |

Alertmanager는 **규칙을 평가하지 않습니다.** 발화된 알람을 받아서 보낼 뿐입니다.

→ "PrometheusRule 만들면 슬랙 알람 오나요?" 의 답이 **"아니오"** 인 이유입니다. Alertmanager 라우팅 설정과 리시버가 따로 있어야 합니다.

**⚠️ 두 가지 지연을 구분하세요**
- `for` : Prometheus에서 "조건이 이만큼 지속되면 발화"
- `group_wait` / `group_interval` : Alertmanager에서 "발송 타이밍"

**그 외** — Prometheus의 `ruleSelector`가 대상을 고르고, 변경은 재시작 없이 반영됩니다. PromQL이 잘못되면 admission webhook이 생성 시점에 막아줍니다.

#### 19 Probes (liveness · readiness · startup)

**한 줄로** — kubelet이 컨테이너 상태를 주기적으로 검사하는 장치입니다.

**⚠️ 핵심 — 세 프로브는 실패했을 때 하는 행동이 완전히 다릅니다**

| 프로브 | 실패하면 | 목적 |
| --- | --- | --- |
| **liveness** | 컨테이너를 **재시작** | 데드락·행에서 복구 |
| **readiness** | **재시작 안 하고** Service에서 제외 (트래픽만 차단) | 무중단 배포, 과부하 회피 |
| **startup** | (성공 전까지 나머지 둘을 **정지**) | 느리게 시작하는 앱 보호 |

readiness는 회복되면 **자동으로 다시 트래픽을 받습니다.**

**startup이 왜 따로 있나**
느린 앱을 liveness의 `initialDelaySeconds`로 처리하면 어떻게 될까요? 시작이 끝난 뒤에도 그 지연이 계속 적용돼서 **데드락 감지가 늦어집니다.**
startup은 **시작 구간에만** 유예를 주고, 시작이 끝나면 liveness가 정상 주기로 돕니다.
- 허용 시작 시간 = `failureThreshold × periodSeconds`

**검사 방식 4가지**
- `httpGet` : 성공 기준은 **상태코드 200 이상 400 미만**입니다. "200만"이 아닙니다.
- `tcpSocket` : 포트가 열려 있으면 성공
- `exec` : 명령 종료코드가 0이면 성공
- `grpc`

**기본값**

| 항목 | 기본값 |
| --- | --- |
| initialDelaySeconds | 0 |
| periodSeconds | 10 |
| timeoutSeconds | 1 |
| failureThreshold | 3 |
| successThreshold | 1 (liveness·startup은 1 고정) |

**⚠️ 설계 원칙 — liveness는 자기 생존만 검사**
헬스 엔드포인트가 DB 같은 외부 의존성까지 확인하면 어떻게 될까요? **DB가 잠깐 느려지면 멀쩡한 파드들이 전부 연쇄 재시작**됩니다. 외부 의존성은 **readiness로** 확인하세요.

**그 외** — 프로브 요청에는 앱의 인증 헤더가 안 붙습니다. 헬스 엔드포인트는 인증 없이 열어야 합니다.

#### 20 HPA (HorizontalPodAutoscaler) + Metrics API

**한 줄로** — 지표를 보고 **파드 개수를 자동으로 조절**하는 컨트롤러입니다.

**VPA와의 차이** — HPA는 **개수**(수평), VPA는 파드 하나의 **크기**(수직)를 조절합니다.

**계산식**
```
목표 replica = ceil[ 현재 replica × (현재값 / 목표값) ]
```
비율이 1.0에서 ±10%(기본 tolerance 0.1) 안이면 아무것도 하지 않습니다. 개수가 계속 출렁이는 걸 막기 위해서입니다.

**지표는 어디서 오나 — 파이프라인**
```
cAdvisor(kubelet 내장) → kubelet → metrics-server(약 15초 주기) → Metrics API → HPA
```
**⚠️ metrics-server가 없으면 지표가 unknown이 되어 HPA가 동작하지 않습니다.**

**⚠️ Prometheus가 있어도 대체가 안 됩니다**
기본 HPA는 `metrics.k8s.io` API만 읽는데, 이건 metrics-server만 채웁니다. Prometheus 지표로 HPA를 하려면 **prometheus-adapter**를 따로 붙여야 합니다.

**⚠️ requests가 없으면 동작하지 않습니다**
CPU 사용률(%) = **사용량 ÷ requests** 입니다. requests를 안 적으면 분모가 없어서 계산 자체가 안 됩니다.

**늘릴 때와 줄일 때가 다릅니다**
- 늘리기: **즉시** (안정화 윈도우 기본 0초)
- 줄이기: **보수적** (기본 300초 동안 지켜보고 그중 최고 추천값을 채택)
- 갑자기 줄였다가 트래픽이 다시 몰리는 사고를 막기 위해서입니다.

**⚠️ 메모리 기반 HPA가 잘 안 되는 이유**
JVM·Go 런타임·캐시는 부하가 빠져도 **메모리를 OS에 반납하지 않습니다.** 사용률이 계속 높게 유지돼서 **스케일 다운이 안 일어납니다.**
→ 1차 지표는 **CPU**를 쓰고, 메모리는 **limits로 OOM을 막는 용도**로 씁니다.

**적용할 수 없는 대상** — DaemonSet처럼 스케일 개념이 없는 오브젝트. 그리고 HPA와 VPA를 **같은 지표에 동시 적용하면 서로 싸웁니다.**

#### 21 PV (PersistentVolume) & PVC (PersistentVolumeClaim)

**한 줄로** — PV는 **실제 스토리지**, PVC는 **"이만큼 쓰겠다"는 요청서**입니다.

**왜 두 개로 나눴나**
파드는 PV가 아니라 **PVC를 마운트**합니다. 이 한 단계를 두면 **"앱이 무엇을 원하는가"**와 **"스토리지가 어떻게 구현되는가"**를 분리할 수 있습니다. 앱은 스토리지 종류를 몰라도 됩니다.

**⚠️ 스코프가 다릅니다 — 단골 함정**
- **PV** : 클러스터 스코프 (네임스페이스 없음)
- **PVC** : 네임스페이스 스코프

**바인딩은 배타적 1:1**
- 한 PVC는 한 PV에만 묶입니다.
- 묶인 PV는 다른 PVC가 쓸 수 없습니다.
- 요청보다 큰 PV가 배정될 수는 있습니다(최소 요청량 보장).

**⚠️ accessModes — 가장 많이 틀립니다**

| 모드 | 의미 |
| --- | --- |
| `RWO` (ReadWriteOnce) | **노드 단위** 제약 — 같은 노드의 여러 파드는 **동시 접근 가능** |
| `RWOP` (ReadWriteOncePod) | **파드 단위** — 진짜 파드 하나만 |
| `ROX` | 여러 노드에서 읽기 |
| `RWX` | 여러 노드에서 읽기·쓰기 |

**RWO는 "파드 하나"가 아니라 "노드 하나"** 입니다. 공식 문서에 명시돼 있습니다. 진짜 단일 파드로 강제하려면 `RWOP`를 써야 합니다.

**생명주기**
```
Provisioning(정적: 관리자가 미리 / 동적: StorageClass가 자동)
→ Binding → Using → Reclaiming
```
PV 상태: `Available` → `Bound` → `Released` → `Failed`

**Reclaim 정책** — PVC를 지웠을 때 PV를 어떻게 할지

| 정책 | 동작 |
| --- | --- |
| `Retain` | 데이터 보존. PV가 `Released`로 남아 수동 정리 필요 |
| `Delete` | 실제 스토리지까지 삭제 |
| `Recycle` | 폐기된 기능 |

#### 22 StorageClass

**한 줄로** — "이런 성격의 스토리지를 만들어달라"는 **주문서 템플릿**입니다.

**무슨 문제를 푸나**
StorageClass가 없으면 관리자가 PV를 **미리 만들어 둬야** 합니다. StorageClass를 참조하면 PVC를 만드는 순간 **PV가 자동으로 생성**되고 바인딩됩니다.

**동작 구조**
- StorageClass는 **규칙**일 뿐입니다.
- 실제로 볼륨을 만드는 건 **provisioner(CSI 드라이버)** 입니다.
- `parameters`로 복제 수·파일시스템 같은 드라이버별 옵션을 전달합니다.

**⚠️ reclaimPolicy 기본값 함정**

| 생성 방식 | 기본 reclaimPolicy |
| --- | --- |
| **동적 생성** (StorageClass) | **`Delete`** ← PVC 지우면 실제 볼륨까지 삭제 |
| 정적 생성 (관리자가 수동) | `Retain` |

기본값이 반대라 헷갈립니다. **지워지면 안 되는 데이터는 `Retain` 클래스를 따로 만들어 명시**해야 합니다.

**volumeBindingMode — 언제 볼륨을 만들까**

| 값 | 동작 | 문제/장점 |
| --- | --- | --- |
| `Immediate` (기본) | PVC 만들면 바로 프로비저닝 | 볼륨 위치가 먼저 정해져서, 파드가 다른 노드에 뜨면 **못 붙을 수 있음** |
| `WaitForFirstConsumer` | 파드가 스케줄될 때까지 대기 | 파드와 **같은 노드**에 볼륨 생성. 로컬·존 스토리지에 권장 |

**그 외**
- `allowVolumeExpansion: true`면 PVC 용량을 온라인으로 늘릴 수 있습니다.
- `storageclass.kubernetes.io/is-default-class` 애너테이션이 붙은 클래스는 `storageClassName`을 생략했을 때 자동 적용됩니다. **클러스터당 1개만** 두는 게 안전합니다.

### ⚪ Tier 3 · 공통 (23~28)

#### 23 Namespace

**한 줄로** — 클러스터 안을 이름으로 구획하는 오브젝트입니다.

**본질은 폴더가 아니라 "정책을 걸 자리"입니다**
RBAC·ResourceQuota·LimitRange·NetworkPolicy·PSA가 **전부 네임스페이스 단위**로 적용됩니다. 네임스페이스를 나눈다는 건 **정책 경계를 나눈다**는 뜻입니다.

**이름 스코프**
- 오브젝트 이름은 **같은 네임스페이스 안에서만** 유일하면 됩니다.
- Service DNS: `<서비스명>.<네임스페이스>.svc.cluster.local`
- 같은 ns끼리는 짧은 이름(`<서비스명>`)으로 통신됩니다.

**⚠️ 스코프 구분 — 단골 문제**

| 네임스페이스 소속 | 클러스터 스코프 |
| --- | --- |
| Pod, Service, Deployment, PVC, Role, RoleBinding | Node, PV, StorageClass, ClusterRole, Namespace 자체 |

확인 방법: `kubectl api-resources --namespaced=false`

**⚠️ 가장 중요 — 네임스페이스는 보안 경계가 아닙니다**
네임스페이스 자체는 **네트워크·커널·자원을 차단하지 않습니다.**
> 공식 문서: 네임스페이스 간 보안을 **강제하지 않는다**

기본 상태에서는 다른 ns의 파드로 네트워크 접근이 **그냥 됩니다.** 실질적인 격리는 **RBAC + NetworkPolicy + PSA + Quota**를 얹어야 생깁니다.
> 공식 표현: *"궁극의 네임스페이스는 별도의 클러스터"*

**삭제 주의** — 네임스페이스를 지우면 안에 있는 **모든 오브젝트가 연쇄 삭제**되고 되돌릴 수 없습니다.

#### 24 Service

**한 줄로** — 계속 생기고 죽는 파드들 앞에 **고정된 IP와 DNS 이름**을 세워주는 추상화입니다.

**어떻게 동작하나**
1. 라벨 셀렉터로 파드를 고릅니다.
2. 그중 **ready 상태인 파드**의 IP만 EndpointSlice에 올라갑니다.
3. kube-proxy가 그 목록으로 트래픽을 분산합니다.

→ **readiness 프로브와 직결됩니다.** readiness가 실패하면 이 목록에서 빠집니다.

**공식 타입 4가지**

| 타입 | 설명 |
| --- | --- |
| `ClusterIP` (기본) | 클러스터 내부 전용 가상 IP |
| `NodePort` | 모든 노드의 같은 포트를 개방 (기본 범위 30000–32767) |
| `LoadBalancer` | 외부 LB로 노출 (베어메탈은 MetalLB 같은 구현체 필요) |
| `ExternalName` | 외부 DNS 이름으로 CNAME |

**⚠️ 상위 타입은 하위를 포함합니다**
LoadBalancer는 안에 NodePort와 ClusterIP를 **그대로 갖고 있습니다.** "NodePort로 바꾸면 ClusterIP가 없어진다"는 오해입니다.

**⚠️ Headless는 타입이 아닙니다**
`clusterIP: None`이라는 **설정**입니다.
- 가상 IP도 없고 kube-proxy 로드밸런싱도 없습니다.
- DNS가 **파드 IP들을 직접 반환**합니다(A 레코드 여러 개).
- 분산은 명단을 받은 **클라이언트가 알아서** 합니다.
- → "Headless도 로드밸런싱한다"는 틀린 말입니다.

**StatefulSet에 Headless가 필수인 이유**
각 파드가 **개별 고정 주소**(`web-0.svc...`)를 가져야 하기 때문입니다. 가상 IP 하나로 묶어서 분산해버리면 "0번 복제본에만 접속" 같은 요구를 만족시킬 수 없습니다.

#### 25 Deployment

**한 줄로** — 서로 **대체 가능한** 파드를 원하는 개수만큼 유지하고, 무중단으로 업데이트·롤백하는 컨트롤러입니다.

**3계층 구조**
```
Deployment → ReplicaSet → Pod
```
- ReplicaSet은 "N개 유지"만 담당합니다.
- Deployment는 **버전이 바뀔 때마다 새 ReplicaSet을 만들어** 버전 관리를 얹습니다.
- → 실무에서 ReplicaSet을 직접 만들지 않는 이유입니다.

**롤링 업데이트**
`spec.template`이 바뀌면 새 RS를 서서히 키우고 옛 RS를 줄입니다.
- `maxSurge` / `maxUnavailable` 기본 각 25%로 속도와 안전성을 조절합니다.
- 전략: `RollingUpdate`(기본) / `Recreate`(전부 내리고 새로 띄움)

**롤백**
이전 ReplicaSet들이 히스토리로 남아서(`revisionHistoryLimit` 기본 10) `kubectl rollout undo`로 되돌립니다.
**⚠️ 되돌리는 건 스펙(설정)뿐입니다.** 데이터는 무관합니다.

**⚠️ 스토리지 — 단골 문제**
- Deployment는 **PVC를 만들어주지 않습니다.**
- `claimName`으로 **이미 있는 PVC를 참조**만 합니다.
- RWX가 아니면 여러 replica가 나눠 쓸 수 없으므로 **사실상 replica=1**이 됩니다.
- 파드마다 전용 볼륨이 필요하면 → **StatefulSet의 `volumeClaimTemplates`** 입니다.

#### 26 ResourceQuota

**한 줄로** — 네임스페이스 **전체가 합쳐서** 쓸 수 있는 자원 총량과 오브젝트 개수의 상한입니다.

노드가 아니라 **네임스페이스에 거는 예산**입니다.

**제한할 수 있는 것**

| 종류 | 필드 |
| --- | --- |
| 컴퓨트 총량 | `requests.cpu`, `requests.memory`, `limits.cpu`, `limits.memory` |
| 스토리지 | `requests.storage`, `persistentvolumeclaims` |
| 오브젝트 개수 | `pods`, `services` 등 + 일반형 `count/<리소스>` |

**언제 검사하나**
파드를 만들거나 늘릴 때 검사하고, 초과하면 **403 Forbidden**으로 거부합니다.

**⚠️ 소급 적용이 없습니다**
Quota를 낮춰도 **이미 떠 있는 파드는 죽지 않습니다.** 새 요청부터 적용됩니다.

**⚠️ 중요 — Quota를 걸면 파드가 requests/limits를 반드시 적어야 합니다**
CPU/메모리 Quota가 걸린 순간, 그 네임스페이스의 **모든 새 파드는 requests·limits를 명시해야** 합니다. 안 적으면 거부됩니다.
→ 그래서 **LimitRange의 기본값 자동 주입과 짝으로** 씁니다. LimitRange가 없으면 개발자가 매번 다 적어야 합니다.

**그 외** — `scopeSelector`로 대상 파드를 좁힐 수 있습니다(BestEffort, PriorityClass 등).

#### 27 LimitRange

**한 줄로** — 네임스페이스 안에서 **컨테이너·Pod·PVC 하나**가 가질 수 있는 자원의 기본값·최소·최대입니다.

**ResourceQuota와의 관계**
- ResourceQuota = **네임스페이스 전체 예산**
- LimitRange = **1인당 한도**
- 별개이고, **짝으로 씁니다.**

**필드**

| 필드 | 하는 일 |
| --- | --- |
| `defaultRequest` | requests를 안 적으면 이 값을 주입 |
| `default` | limits를 안 적으면 이 값을 주입 |
| `min` / `max` | 허용 범위 |
| `maxLimitRequestRatio` | limit ÷ request 비율 상한 |
| `type` | **필수** — Container / Pod / PersistentVolumeClaim |

**⚠️ 적용 시점은 파드 생성·수정 때뿐입니다**
규칙을 바꿔도 **이미 실행 중인 파드는 영향받지 않습니다.** 재생성될 때 새 규칙이 적용됩니다.

**⚠️ 정합성은 검사하지 않습니다**
`default`(limit)만 있는데 파드가 그보다 큰 request를 적으면 → **request > limit** 모순이 되어 생성에 실패합니다. LimitRange가 이걸 미리 잡아주지 않습니다.

**⚠️ 노드 용량은 안 봅니다**
LimitRange는 **"숫자가 규칙 범위 안인가"만** 검사합니다.
- 실제로 배치 가능한지 → 스케줄러
- 네임스페이스 총량 → ResourceQuota

**그 외** — PVC 요청 크기의 min/max도 강제할 수 있습니다. "실수로 500Gi 요청" 같은 사고를 입구에서 막습니다.

#### 28 PDB (PodDisruptionBudget)

**한 줄로** — 노드 드레인 같은 **계획된 작업** 중에 파드가 동시에 몇 개까지 내려갈 수 있는지 정하는 안전장치입니다.

**무슨 문제를 푸나**
노드를 유지보수하려고 drain하면 그 노드의 파드가 전부 쫓겨납니다. 운 나쁘면 **서비스의 모든 파드가 동시에 내려갑니다.** PDB는 축출 속도를 조절해서 이걸 막습니다.

**지정 방법 2가지 — 동시 지정 불가**
- `minAvailable` : 최소 몇 개는 살아있어야 함
- `maxUnavailable` : 최대 몇 개까지 내려갈 수 있음
- 절대 수 또는 백분율(올림)

**⚠️ Eviction API를 거칠 때만 작동합니다**

| 방법 | PDB 적용? |
| --- | --- |
| `kubectl drain` | ✅ 적용됨 |
| `kubectl delete pod` | ❌ **우회됨** |
| Deployment 삭제 | ❌ 우회됨 |

→ 유지보수는 **반드시 drain으로** 해야 PDB 보호를 받습니다.

**⚠️ 계획된 중단만 막습니다**
하드웨어 고장·커널 패닉 같은 **예기치 못한 중단은 못 막습니다.** (다만 그 손실도 예산에서 차감돼서 이후 축출이 더 보수적이 됩니다.)
진짜 HA는 PDB만으로 안 되고 **복제본 수 + 안티어피니티 + 노드 분산**이 함께 필요합니다.

**⚠️ 너무 빡빡하면 drain이 멈춥니다**
예: replica 3인데 `minAvailable: 3` → **아무 파드도 못 뽑아서 drain이 영원히 대기**합니다.
→ minAvailable은 **정족수 유지에 필요한 만큼만** 잡고, 축출 여유를 **최소 1개**는 남깁니다.
→ 복제본이 1개면 PDB로도 무중단이 불가능합니다.

**그 외**
- 셀렉터가 대상 컨트롤러(Deployment·StatefulSet)의 라벨 셀렉터와 일치해야 합니다.
- `unhealthyPodEvictionPolicy` (v1.31 정식) : 기본 `IfHealthyBudget`. 고장난 앱 때문에 drain이 막히는 걸 원치 않으면 `AlwaysAllow` 권장.

## 1-3. 헷갈리는 세트 비교

**① Role vs ClusterRole**

| 구분 | Role | ClusterRole |
| --- | --- | --- |
| 범위 | 한 네임스페이스 | 전역 (namespace 필드 없음) |
| 다룰 수 있는 것 | ns 안의 리소스만 | + Node·PV·StorageClass + `/metrics` 같은 URL |
| 주 용도 | 일반 워크로드 | 전 ns 탐색·Node 접근이 필요한 소수 (Prometheus 등) |

**② 바인딩 4조합**

| 바인딩 | 참조 | 가능? | 결과 |
| --- | --- | --- | --- |
| RoleBinding | Role | ✅ | 그 ns 안에서만 |
| RoleBinding | ClusterRole | ✅ | 전역 정의를 그 ns로 **축소** |
| ClusterRoleBinding | ClusterRole | ✅ | 클러스터 전역 |
| ClusterRoleBinding | Role | ❌ | **유일한 불가** (범위 모순) |

**③ Deployment vs StatefulSet vs DaemonSet**

| 구분 | Deployment | StatefulSet | DaemonSet |
| --- | --- | --- | --- |
| 파드 성격 | 서로 대체 가능 | 고유 이름 고정 | 노드당 정확히 1 |
| 스토리지 | 기존 PVC 참조(공유) | **파드마다 자동 생성** | 노드 로컬(hostPath 등) |
| 개수 | replicas | replicas + 순서 보장 | **노드 수 = 파드 수** |
| 예 | 웹/API, Grafana | DB, Prometheus, Vault | node-exporter, OTel Agent |

**④ Secret vs SealedSecret vs etcd 암호화**

| 구분 | 보호 구간 | 원리 | 한계 |
| --- | --- | --- | --- |
| Secret | (보호 장치 아님) | base64 인코딩 | 암호화 아님, etcd에 평문 |
| SealedSecret | **Git 이동·저장** | 공개키 봉인 | 복호화 후엔 평범한 Secret |
| etcd 암호화 | **디스크·백업** | API 서버가 쓰기 전 암호화 | API 조회 시엔 복호화됨 → RBAC 별도 필요 |

**⑤ PSA vs SecurityContext vs Kyverno**

| 구분 | 역할 | 적용 단위 | 성격 |
| --- | --- | --- | --- |
| PSA | 기준 검사 | 네임스페이스 라벨 | 내장, 3레벨 고정 |
| SecurityContext | 검사를 통과할 **실제 값** | 파드/컨테이너 | 워크로드가 스스로 선언 |
| Kyverno | 세밀 정책 + 수정·생성 | 전역 또는 ns | CRD, PSA 빈틈 보완 |

**⑤-보충 PSS 3레벨 — 무엇이 어디서 금지되나 (정정 반영)**

| 레벨 | 내용 |
| --- | --- |
| privileged | 제한 없음 (관측 DaemonSet, CNI 등 시스템 워크로드용) |
| baseline | privileged 컨테이너 · host 네임스페이스 · **hostPath** · 과도한 capability 차단. **root 실행은 허용** |
| restricted | baseline 전부 + runAsNonRoot + allowPrivilegeEscalation:false + drop ALL(NET_BIND_SERVICE만 복원 가능) + seccomp 명시 + 볼륨 타입 제한(**PVC는 허용**) |

**⑥ PV vs PVC vs StorageClass**

| 구분 | 정체 | 스코프 |
| --- | --- | --- |
| PV | 실제 스토리지 자원 | 클러스터 |
| PVC | 사용 요청서 (파드가 마운트) | 네임스페이스 |
| StorageClass | 동적 생성 템플릿 | 클러스터 |

**⑦ liveness vs readiness vs startup**

| 구분 | 실패 시 | 목적 | 설계 포인트 |
| --- | --- | --- | --- |
| liveness | 컨테이너 재시작 | 데드락 복구 | **자기 생존만** 검사 |
| readiness | 트래픽만 차단 | 무중단 배포 | 외부 의존성은 여기서 |
| startup | 다른 프로브 정지 | 느린 시작 보호 | 허용 시간 = failureThreshold × periodSeconds |

## 1-4. 우리 프로젝트 결정 8가지

> 선생님이 "왜 그렇게 했나요?"라고 물을 지점들입니다.

**1. PSA는 restricted가 원칙, 완화는 최소로** *(정정 반영)*
- 결정: 대부분 `enforce=restricted`. `dang-db-ns`만 baseline.
- 근거: DB 공식 이미지가 root로 도는데, root 금지는 restricted 전용 요구라 baseline이면 충분합니다.
- 재조정 중: hostPath·hostNetwork는 **baseline에서도 금지**라, node-exporter·OTel Agent는 privileged가 필요합니다. → **그 DaemonSet만 별도 ns로 분리**해서 privileged 범위를 최소화합니다.

**2. Vault는 replica 1 (PoC)**
- 결정: StatefulSet 구조는 제대로 잡되 replica는 1로 고정.
- 근거: Vault의 Raft는 **정족수 3**이 필요한데, 우리는 물리 호스트가 2대입니다. replica 3을 띄워도 호스트 하나가 죽으면 정족수가 깨지는 **가짜 HA**가 됩니다.
- 보완: PoC임을 명시하고, `vault sealed` 알람으로 조기에 감지합니다.

**3. Alertmanager는 replica 3 + PDB minAvailable 2**
- 근거: Alertmanager는 **gossip 방식이라 정족수가 필요 없습니다.** 물리 2호스트에서도 HA가 실제로 유효합니다. (Vault의 Raft와 대비되는 지점입니다.)
- 피어 탐색은 Headless Service DNS로 합니다.

**4. Grafana는 provisioning + SQLite, Deployment**
- 결정: 무상태로 운영. 대시보드·데이터소스는 provisioning 파일로 Git에.
- 근거: **데이터는 Prometheus·Loki에 있고**, 설정은 Git에서 재생성됩니다. 전용 PVC가 필요 없으므로 StatefulSet이 아닙니다.

**5. requests/limits는 실측 기반**
- 결정: 도커에서 실측한 값 + 노드 용량(8Gi/2CPU) 상한.
- 근거: 임의로 정하면 **너무 작으면 OOMKill, 너무 크면 스케줄 불가**라 양쪽 다 위험합니다. 실측이 유일한 근거입니다.
- 강제: LimitRange의 max로 상한을, defaultRequest로 누락을 처리합니다.

**6. CNI는 Calico/Cilium 필수**
- 결정: NetworkPolicy 지원 CNI를 **이관 전제조건**으로 못박음.
- 근거: 미지원 CNI면 default-deny 정책 전부가 **조용히 무효**가 됩니다. 에러도 안 납니다.
- 검증: 적용 후 실제 연결 테스트로 차단을 확인합니다.

**7. 시크릿 3계층**
- 구성: SealedSecret(Git 부트스트랩) + Vault(런타임, PoC) + etcd 암호화(최후 방어)
- 근거: **보호 구간이 각각 다릅니다.** Git 구간 / 런타임 / 디스크·백업. 서로 대체가 안 되므로 직렬로 겹칩니다.

**8. 부하테스트는 K8s 이관 후로**
- 결정: HPA 임계값·Quota는 1차 상한만 정하고, 확정은 이관 후 실측으로.
- 근거: 도커 실측치는 있지만 K8s는 환경 특성이 다릅니다. metrics-server 설치 후 `kubectl top`으로 확정합니다.

## A. 기본 개념 (10문항)

> 2~3문장으로 짧게 답하는 연습을 하세요.

**A1. PSA(Pod Security Admission)가 뭐예요?**

파드가 만들어질 때 보안 설정을 검사해서 통과·거부·경고를 결정하는, 쿠버네티스에 **기본 내장된** 검문소입니다.
- 네임스페이스 라벨을 기준으로 검사합니다.
- 레벨 3개(privileged/baseline/restricted)와 모드 3개(enforce/audit/warn)를 조합해서 씁니다.
- v1.25에서 제거된 PSP를 대체했습니다.

저희는 원칙적으로 `enforce=restricted`를 걸고, DB 네임스페이스만 baseline으로 완화했습니다. 관측용 DaemonSet은 공식문서 재검증 결과 privileged가 필요해서 별도 분리로 재조정 중입니다.

**A2. SecurityContext는 뭐예요?**

파드나 컨테이너가 **어떤 UID·권한·커널 능력으로 실행될지**를 매니페스트에 적는 필드입니다.

PSA와의 관계로 설명하면 이렇습니다: **PSA는 검문소, SecurityContext는 그 검문을 통과할 실제 값**입니다.

저희 팀 표준은 하드닝 4종 세트입니다 — `runAsNonRoot`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`.

**A3. NetworkPolicy는 뭐고, 기본 동작은 어떻게 되나요?**

어떤 파드가 어떤 대상과 통신할 수 있는지를 IP·포트 수준(L3/L4)에서 정하는 방화벽 규칙입니다.

기본 동작이 중요합니다:
- 아무 정책이 없으면 파드는 **비격리 상태**라 전부 통신됩니다.
- 어떤 정책이 그 파드를 **선택하는 순간** 격리되고, 그때부터 **명시적으로 허용한 것만** 통과합니다.

그리고 적용하려면 **Calico나 Cilium 같은 정책 지원 CNI가 필수**입니다. 없으면 정책이 조용히 무시됩니다.

**A4. ServiceAccount는 뭐예요?**

파드가 쿠버네티스 API 서버에 자기 신원을 증명할 때 쓰는 **기계용 신분증**입니다.

알아둘 사실이 하나 있습니다 — 쿠버네티스에는 **사람용 User 오브젝트가 아예 없습니다.** 사람은 인증서나 OIDC 같은 외부 수단으로 인증하고, 워크로드는 SA로 인증합니다.

그리고 SA는 **"누구인가"만** 증명합니다. 권한은 RoleBinding으로 따로 연결해야 하고, 연결 전에는 0입니다.

**A5. Secret에 값을 넣으면 암호화되나요?**

아닙니다.
- `data` 값은 **base64 인코딩**일 뿐이라 누구나 디코드합니다.
- 게다가 기본 설정에서는 **etcd에도 평문으로** 저장됩니다(공식 문서 명시).

실제 보호는 **RBAC 최소권한 + etcd Encryption at Rest**를 명시적으로 켜야 완성됩니다.

**A6. StatefulSet은 뭐고 언제 쓰나요?**

파드마다 **바뀌지 않는 이름**과 **파드 전용 볼륨**을 보장하는 컨트롤러입니다.

공식 문서 기준으로 아래 4가지 중 **하나라도** 필요하면 StatefulSet, 아니면 Deployment입니다:
① 안정적 네트워크 이름 ② 안정적 영속 스토리지 ③ 순서 보장 배포·스케일링 ④ 순서 보장 롤링 업데이트

저희는 Prometheus·Alertmanager·Vault가 여기 해당합니다.

**A7. DaemonSet은 뭐예요?**

모든 노드(또는 조건에 맞는 노드)마다 파드를 **정확히 1개씩** 돌리는 컨트롤러입니다.
- replica 필드가 없고 **노드 수가 곧 파드 수**입니다.
- 노드가 늘거나 줄면 자동으로 따라갑니다.

노드 자체의 지표·로그는 그 노드 위에서만 걷을 수 있어서, node-exporter와 OTel Agent에 씁니다.

**A8. HPA는 어떻게 동작하나요?**

CPU 같은 지표를 보고 **파드 개수를 자동으로 조절**하는 컨트롤러입니다.

기본 지표는 **"사용량 ÷ requests"의 사용률(%)** 이고, 이 숫자는 이 경로로 옵니다:
```
cAdvisor → kubelet → metrics-server → Metrics API → HPA
```

그래서 두 경우에 동작하지 않습니다: **requests를 안 적었을 때**(분모가 없음), **metrics-server가 없을 때**(지표가 unknown).

**A9. Namespace는 보안 경계인가요?**

아닙니다. **소프트 격리**입니다.
- 네임스페이스 자체는 네트워크·커널·자원을 **차단하지 않습니다.**
- 공식 문서도 "네임스페이스 간 보안을 강제하지 않는다"고 명시합니다.

대신 RBAC·NetworkPolicy·PSA·Quota 같은 **정책을 걸 자리**를 제공합니다. 저희는 그 위에 default-deny 등을 얹어서 실질적인 격리를 만들었습니다.

**A10. PDB(PodDisruptionBudget)는 뭐예요?**

노드 드레인 같은 **계획된 중단** 상황에서, 파드가 동시에 몇 개까지 내려갈 수 있는지 정하는 안전장치입니다.
- `minAvailable` 또는 `maxUnavailable` 중 **하나로만** 지정합니다.
- **Eviction API를 거치는 축출에만** 작동합니다.
- 하드웨어 고장 같은 예기치 못한 중단은 막지 못합니다.

## B. 비교·구분 (11문항)

**B1. Role과 ClusterRole의 차이는?**

**범위**가 다릅니다. 규칙 문법(apiGroups·resources·verbs)은 **완전히 같습니다.**
- Role: 특정 네임스페이스 안의 리소스만
- ClusterRole: 네임스페이스 경계 없음 + Node·PV 같은 non-namespaced 리소스 + `/metrics` 같은 URL까지

저희는 "네임스페이스 안에서 끝나는 일에 전역 권한을 주지 않는다"는 원칙으로, Role이 기본이고 ClusterRole은 Prometheus 등 소수만 씁니다.

**B2. RoleBinding과 ClusterRoleBinding의 4가지 조합을 설명해보세요.**

3개는 가능하고 1개만 불가능합니다.

| 조합 | 결과 |
| --- | --- |
| RoleBinding + Role | 그 네임스페이스 권한 |
| RoleBinding + ClusterRole | 전역 정의를 **그 ns로 축소** (재사용 패턴) |
| ClusterRoleBinding + ClusterRole | 클러스터 전역 |
| **ClusterRoleBinding + Role** | **불가능** |

마지막이 안 되는 이유는 전역 바인딩이 네임스페이스 한정 역할을 가리키는 **범위 모순**이라 API가 막기 때문입니다.

여기서 나오는 포인트: **"ClusterRole은 무조건 전역"이 아닙니다.** 전역 여부는 **어떤 바인딩으로 붙이느냐**가 결정합니다.

**B3. Deployment와 StatefulSet은 뭐가 다른가요?**

파드가 서로 **대체 가능하면** Deployment, **고유 신원·순서·전용 스토리지**가 필요하면 StatefulSet입니다.

결정적 차이는 **스토리지**입니다:
- Deployment: 기존 PVC를 **참조(공유)만** 합니다.
- StatefulSet: `volumeClaimTemplates`로 **파드마다 전용 PVC를 자동 생성**하고, 재스케줄돼도 같은 볼륨에 다시 붙습니다.

웹/API는 Deployment, DB나 Prometheus처럼 데이터를 파드 곁에 남겨야 하면 StatefulSet입니다.

**B4. Deployment replica를 노드 수만큼 주면 DaemonSet과 같지 않나요?**

다릅니다. 두 가지 이유입니다:
1. Deployment는 파드가 **같은 노드에 몰릴 수 있습니다.**
2. 노드가 늘어나도 **자동으로 따라 뜨지 않습니다.**

DaemonSet은 "노드당 정확히 1개 + 노드 증감 자동 추종"을 보장합니다. node-exporter처럼 **노드마다 재야 의미가 있는** 워크로드는 DaemonSet이어야 관측 사각지대가 안 생깁니다.

**B5. Secret, SealedSecret, etcd 암호화는 각각 뭘 보호하나요?**

**보호하는 구간**이 다릅니다.

| | 보호 구간 |
| --- | --- |
| SealedSecret | **Git에 올리는 이동·저장** 구간 |
| etcd 암호화 | **클러스터 디스크·백업** 구간 |
| Secret | (보호 장치가 아님) 파드로 값을 전달하는 통로 |

SealedSecret이 컨트롤러에서 복호화되면 결국 **평범한 Secret으로 etcd에 남습니다.** 그래서 서로 대체가 안 되고 **직렬로 겹쳐야** 합니다.

**B6. PSA가 있는데 Kyverno는 왜 또 필요한가요?**

PSA는 **3레벨 고정 프로파일**이라 단순하고 예측 가능한 대신 **세밀 조정이 안 됩니다.**

Kyverno는 이런 게 가능합니다:
- "Harbor 레지스트리 이미지만 허용", "latest 태그 금지" 같은 **임의 조건 검사**
- 값을 자동 수정(mutate), 리소스 자동 생성(generate)

배타 관계가 아닙니다. **PSA가 넓은 벽, Kyverno가 세밀 보완**으로 같이 씁니다. 저희는 PSA를 완화한 네임스페이스를 Kyverno로 다시 조입니다.

**B7. PV, PVC, StorageClass의 관계를 설명해보세요.**

- **PVC** = "이만큼 이렇게 쓰겠다"는 요청서
- **PV** = 클러스터에 실제로 있는 스토리지
- **StorageClass** = PVC 요청에 맞춰 PV를 자동으로 찍어내는 공장 설정

파드는 **PV가 아니라 PVC를 마운트**하고, PVC와 PV는 **배타적 1:1**로 묶입니다.

스코프도 다릅니다 — **PVC만 네임스페이스 소속**이고, PV와 StorageClass는 클러스터 스코프입니다.

**B8. liveness, readiness, startup 프로브의 차이는?**

**실패했을 때의 행동**이 다릅니다.

| 프로브 | 실패하면 | 목적 |
| --- | --- | --- |
| liveness | 컨테이너 **재시작** | 데드락 복구 |
| readiness | 재시작 없이 **트래픽만 차단** (회복 시 자동 복귀) | 무중단 배포 |
| startup | 성공 전까지 **나머지 둘을 정지** | 느린 시작 보호 |

운영 원칙은 **"liveness는 자기 생존만 검사, DB 같은 외부 의존성은 readiness로"** 입니다.

**B9. ClusterIP와 Headless Service의 차이는?**

- **ClusterIP**: 대표 가상 IP를 하나 만들고 kube-proxy가 뒤의 파드들로 분산합니다.
- **Headless**(`clusterIP: None` — 별도 타입이 아니라 **설정**입니다): 가상 IP도 분산도 없이 **DNS가 파드 IP 명단을 직접 반환**합니다.

**"하나의 대표 vs 명단 전체"** 의 차이입니다.

그래서 각 파드를 개별적으로 지목해야 하는 **StatefulSet에는 Headless가 필수**입니다.

**B10. ResourceQuota와 LimitRange의 차이는?**

- **ResourceQuota**: 네임스페이스 **전체 합계**의 상한 (예: "requests 합 최대 16Gi")
- **LimitRange**: **개별** 컨테이너·파드·PVC 하나의 기본값·최소·최대 (예: "한 파드 최대 2Gi")

둘은 짝으로 씁니다. 이유가 있습니다:
> CPU/메모리 Quota가 걸리는 순간 **모든 새 파드가 requests/limits를 명시해야** 합니다. 안 적으면 거부됩니다. 이때 **LimitRange의 기본값 자동 주입**이 누락된 파드를 구제합니다.

**B11. ServiceMonitor와 PodMonitor의 차이는?**

- **ServiceMonitor**: Service를 라벨로 골라 그 뒤의 파드들을 긁습니다. **Service가 있어야 하고, Service의 named port**를 써야 합니다(숫자 불가).
- **PodMonitor**: Service 없이 파드를 직접 라벨로 긁습니다.

기본은 ServiceMonitor를 쓰고, Service를 두지 않는 DaemonSet 계열에는 PodMonitor가 자연스럽습니다.

주의할 점: **실제로 긁는 주체는 CRD가 아니라 Prometheus**입니다. CRD는 "이걸 긁어달라"는 선언일 뿐입니다.

## C. 프로젝트 결정 근거 (8문항) — 가장 중요

**C1. 관측 네임스페이스는 PSA를 어떻게 잡았나요?**

먼저 사실관계입니다:
- node-exporter는 `/proc`·`/sys`를, OTel Agent는 `/var/log`를 **hostPath로** 읽어야 합니다. hostNetwork·hostPID도 씁니다.
- 그런데 공식 Pod Security Standards상 **이것들은 baseline에서도 금지**입니다.
- 즉 이 DaemonSet들에는 **privileged 레벨이 필요**합니다.

솔직히 말씀드리면, 처음엔 baseline으로 잡았습니다. 공식문서를 재검증하면서 이 사실을 확인했고, 지금은 **privileged가 필요한 DaemonSet만 별도 네임스페이스로 분리**해서 privileged 범위를 최소화하는 방향으로 재조정 중입니다.

`dang-db-ns`는 사정이 다릅니다. DB 공식 이미지가 root로 도는 것은 **restricted 전용 요구(runAsNonRoot) 위반일 뿐**이라 baseline으로 충분합니다.

어느 경우든 SecurityContext 하드닝, Kyverno validate, NetworkPolicy 격리는 **동일하게 유지**합니다.

> **꼬리질문 대비 — "baseline이면 뭐까지 허용되나요?"**
> baseline은 privileged 컨테이너·host 네임스페이스·hostPath 같은 **명백한 권한 상승 경로만** 차단합니다. runAsNonRoot·drop ALL·seccomp 명시는 요구하지 않습니다(그건 restricted 전용). 그 빈틈은 저희가 SecurityContext와 Kyverno로 자발적으로 메웁니다.

**C2. 왜 Vault는 replica 1인데 Alertmanager는 3이죠?**

두 시스템의 **합의 방식**이 다르기 때문입니다.

- **Vault는 Raft** — **정족수(3노드 중 2)** 가 필요합니다. 그런데 저희는 물리 호스트가 2대입니다. replica 3을 띄워도 호스트 하나가 죽으면 **정족수가 깨지는 가짜 HA**가 됩니다.
- **Alertmanager는 gossip** — **정족수가 필요 없습니다.** 물리 2호스트에서도 HA가 실제로 유효합니다.

그래서 Vault는 StatefulSet 구조만 제대로 잡고 **replica 1 PoC로 명시**했고, Alertmanager는 **replica 3 + PDB minAvailable 2**로 운영합니다.

> **꼬리질문 대비 — "그럼 Vault가 죽으면 어떻게 되나요?"**
> 런타임 동적 발급만 멈춥니다. 정적 시크릿은 SealedSecret 계층이 담당하므로 부트스트랩은 무사합니다. `vault sealed` PrometheusRule 알람으로 조기에 감지합니다.

**C3. Prometheus는 왜 StatefulSet이죠?**

TSDB와 WAL을 **로컬 디스크에 쓰는** 상태 저장 워크로드이기 때문입니다.

StatefulSet을 쓰면:
- `volumeClaimTemplates`로 `prometheus-0` 전용 PVC가 자동 생성·고정됩니다.
- 파드가 재시작해도 **같은 PVC에 다시 붙어서 WAL을 이어받습니다.**
- → 수집 공백과 데이터 유실을 막습니다.

공식 4조건 중 **"안정적 영속 스토리지 + 안정적 신원"** 에 해당하는 전형적인 사례입니다.

> **꼬리질문 대비 — "StatefulSet을 지우면 데이터도 날아가나요?"**
> 아니요. 기본값으로는 PVC·PV가 삭제되지 않고 남아서, 재배포하면 다시 붙습니다. (v1.32 정식 기능인 retentionPolicy로 자동 삭제를 켤 수는 있지만 기본은 보존입니다.)

**C4. Grafana는 왜 Deployment죠? 대시보드는 어디 저장돼요?**

Grafana를 **의도적으로 무상태로** 설계했기 때문입니다.

- 지표·로그 데이터 자체는 **Prometheus·Loki 같은 각 수집기에** 있습니다.
- 대시보드·데이터소스 설정은 **provisioning 파일로 Git에** 코드로 두었습니다.

그래서 파드가 죽어도 **GitOps 재프로비저닝으로 동일하게 복원**되고, 전용 PVC가 필요 없으므로 StatefulSet이 아닌 Deployment가 맞습니다.

> **꼬리질문 대비 — "UI에서 수정한 대시보드는요?"**
> provisioning이 원본이므로 **UI 수정은 휘발 전제**입니다. 변경은 Git을 거치는 게 운영 원칙입니다. 알람도 인프라 알람은 PrometheusRule(GitOps)로 표준화하는 방향입니다.

**C5. requests/limits 값은 어떻게 정했나요?**

**도커 환경에서 실측한 값**을 기반으로 하고, **워커 노드 용량(8Gi/2CPU)** 을 상한으로 잡았습니다.

임의로 정하면 안 되는 이유가 있습니다:
- 너무 작으면 → **OOMKill**
- 너무 크면 → **스케줄 불가·자원 낭비**
- 양쪽 다 위험해서 **실측이 유일한 근거**라고 판단했습니다.

그리고 LimitRange의 `max`가 이 상한을 admission에서 강제하고, `defaultRequest`가 누락을 자동으로 메웁니다. 최종 확정치는 **K8s 이관 후 부하테스트로 재검증**하는 전제입니다.

> **꼬리질문 대비 — "부하테스트는 왜 아직 안 했나요?"**
> 도커 수치는 이미 확보했습니다. K8s는 환경 특성이 달라서 **이관 완료 후 실환경에서 해야 의미가 있어** 일정상 이월했습니다.

**C6. 시크릿 관리는 어떻게 설계했어요?**

**3계층 직렬 방어**입니다.

| 계층 | 담당 구간 | 대상 예 |
| --- | --- | --- |
| ① SealedSecret | Git 부트스트랩 | DB 초기 비밀번호, Harbor 자격증명 |
| ② Vault | 런타임 동적 발급 | (물리 한계로 replica 1 PoC) |
| ③ etcd 암호화 | 최종 저장 | 전부 |

핵심은 이겁니다: **어느 계층을 거치든 최종 형태는 K8s Secret으로 etcd에 남습니다.** 그래서 ③이 없으면 **etcd 스냅샷 하나가 곧 전체 유출**입니다.

> **꼬리질문 대비 — "SealedSecret이 있는데 etcd 암호화가 왜 또 필요하죠?"**
> SealedSecret은 **Git 구간만** 보호합니다. 컨트롤러가 복호화하고 나면 평문 Secret이 etcd에 남습니다. 보호 구간이 달라서 서로 대체가 안 됩니다.

**C7. CNI를 왜 Calico/Cilium으로 전제했나요?**

NetworkPolicy가 저희 보안 설계의 축인데, **정책 지원 CNI가 없으면 NetworkPolicy가 무효**가 되기 때문입니다.

무서운 건 이 부분입니다:
> 미지원 CNI(flannel 단독 등)에서는 정책 리소스가 **저장은 되지만 오류 없이 조용히 무시**됩니다.

그러면 default-deny 3계층(fe→be→db)이 통째로 무효가 되는데 **아무도 모릅니다.** 치명적이라 CNI 선정을 **이관 전제조건으로 못박았습니다.**

그래서 체크리스트에 "default-deny 적용 후 **파드 간 연결 테스트로 실제 차단 확인**"을 넣었습니다.

> **꼬리질문 대비 — "적용됐는지 어떻게 검증해요?"**
> 리소스가 존재하는 것과 동작하는 것은 다릅니다. 정책 적용 후 실제 연결 테스트(수동 워크스루)로 차단 여부를 확인합니다.

**C8. 알람 규칙은 왜 PrometheusRule CRD로 관리하나요?**

알람을 **UI 수기 설정이 아니라 Git(ArgoCD) 코드**로 두면 리뷰·버전 관리·롤백이 가능해지기 때문입니다.

부가 이점도 있습니다:
- Operator가 **재시작 없이** 반영해 줍니다.
- 잘못된 PromQL은 **admission webhook이 생성 시점에 차단**합니다.

대상은 `up==0`, 메모리 limit 90%, TLS 만료 임박, Vault sealed 같은 **인프라·플랫폼 알람**이고, 대시보드에 밀착된 알람만 Grafana Alerting에 남기는 소유권 구분을 진행 중입니다.

> **꼬리질문 대비 — "PrometheusRule만 만들면 슬랙 알람이 오나요?"**
> 아니요. CRD는 **발화까지만** 책임집니다. 발송되려면 Alertmanager 라우팅·리시버 + default-deny 위에 슬랙 egress 허용 + webhook 시크릿까지 갖춰져야 합니다.

## D. 실무 함정 (6문항)

**D1. enforce=restricted 네임스페이스에 위반 Deployment를 apply하면 어떻게 되나요?**

**apply 자체는 성공합니다.**

이유는 PSA의 `enforce`가 **최종 파드에만** 적용되기 때문입니다.
1. Deployment 오브젝트는 저장됩니다.
2. 그 밑에서 만들어지는 파드만 거부됩니다.
3. 결과적으로 **replica 0으로 조용히 실패**합니다.

> 공식 문서: "enforce는 워크로드 리소스가 아니라 결과 파드에만 적용된다"

가장 잘 걸리는 함정이라, 저희는 **warn·audit 모드를 같은 레벨로 함께** 걸었습니다. 이 둘은 워크로드 리소스에도 적용돼서 apply 시점에 경고가 보입니다.

> **꼬리질문 대비 — "그 조용한 실패는 어떻게 탐지해요?"**
> kube-state-metrics의 **spec replica 대비 available replica 불일치** 지표와, ReplicaSet의 **FailedCreate 이벤트**로 잡습니다.

**D2. 메모리 limit 초과와 CPU limit 초과는 어떻게 다르게 동작하나요?**

자원의 성격이 달라서 결과가 다릅니다.

| 자원 | 성격 | 초과하면 |
| --- | --- | --- |
| 메모리 | 비압축성 | **OOMKill — 컨테이너가 죽습니다** |
| CPU | 압축성 | **throttle — 느려질 뿐 안 죽습니다** |

그래서 **메모리 limit은 실측 대비 여유를 둬야** 하고, CPU limit은 상대적으로 관대해도 됩니다.

> **꼬리질문 대비 — "그럼 메모리 기반 HPA는 왜 잘 안 써요?"**
> JVM·캐시 계열은 부하가 빠져도 **메모리를 반납하지 않아서** 스케일 다운이 안 됩니다. 1차 지표는 CPU를 쓰고, 메모리는 limits로 OOM 방어만 합니다.

**D3. RWO PVC를 쓰는 파드가 여러 개 뜨면 어떻게 되나요?**

**RWO는 파드 단위가 아니라 노드 단위 제약**입니다.
- 같은 노드에 스케줄된 파드들은 하나의 RWO PVC에 **동시 접근할 수 있습니다.**
- 다른 노드의 파드만 못 붙습니다.

진짜 단일 파드로 강제하려면 **`RWOP`(ReadWriteOncePod)** 를 써야 합니다.

그래서 Deployment가 RWO PVC를 참조하면, replica가 **다른 노드로 갈리는 순간 깨지므로** 사실상 replica 1로 봐야 합니다.

> **꼬리질문 대비 — "PVC를 지우면 데이터도 지워지나요?"**
> `reclaimPolicy`에 달렸습니다. `Retain`이면 PV가 Released로 남아 수동 정리가 필요하고, `Delete`(동적 프로비저닝의 기본값)일 때만 실제 볼륨까지 삭제됩니다.

**D4. NetworkPolicy를 잘 짰는데 트래픽이 안 막힙니다. 원인이 뭘까요?**

**1순위는 CNI가 NetworkPolicy를 지원하지 않는 경우**입니다. flannel 단독 같은 환경에서는 정책 리소스가 저장은 되지만 **오류 없이 조용히 무시**됩니다.

**2순위는 `policyTypes` 누락**입니다. `Egress`를 명시하지 않으면, egress 규칙이 없는 한 **나가는 트래픽은 그대로 열려 있습니다.**

그래서 저희는 CNI를 전제조건으로 두고, 적용 후 **실제 연결 테스트로 검증**합니다.

> **꼬리질문 대비 — "default-deny egress를 걸었더니 전부 장애가 났어요. 왜죠?"**
> **DNS 예외를 빠뜨린 것**입니다. kube-system의 CoreDNS로 나가는 53번 포트(UDP·TCP)를 허용해야 합니다. default-deny egress 도입 시 **가장 흔한 장애 원인**이라 예외 1순위입니다.

**D5. kubectl drain이 끝나지 않고 무한 대기합니다. 왜죠?**

**PDB의 축출 여유가 0인 경우**가 대표적입니다.

예를 들어 replica 3에 `minAvailable: 3`이면 → 어떤 파드도 축출할 수 없어서 **drain이 영원히 블록**됩니다.

`minAvailable`은 **정족수 유지에 필요한 수까지만** 잡고, 축출 여유를 최소 1개는 남겨야 합니다. 저희 Alertmanager가 **replica 3 + minAvailable 2**인 이유입니다.

> **꼬리질문 대비 — "그럼 kubectl delete pod로 지우면 되지 않나요?"**
> 지워지긴 합니다. 하지만 **Eviction API를 우회해서 PDB 보호가 무력화**됩니다. 유지보수는 반드시 축출 경로(drain)로 하는 게 원칙입니다.

**D6. ServiceMonitor를 만들었는데 Prometheus targets에 안 뜹니다. 어디부터 보나요?**

**90%는 라벨 매칭 문제**라 순서대로 봅니다.

1. Prometheus의 `serviceMonitorSelector` ↔ CRD 라벨이 맞나?
2. `NamespaceSelector`에 대상 네임스페이스가 포함됐나?
3. ServiceMonitor의 `selector` ↔ Service 라벨이 맞나?
4. `port`에 숫자를 적지 않았나? (Service의 **named port**여야 함)

여기까지 다 맞는데도 안 되면 → **NetworkPolicy가 scrape 트래픽을 막는지** 확인합니다. default-deny 환경에서는 메트릭 포트 ingress 허용이 있어야 실제로 긁힙니다.

> **꼬리질문 대비 — "셀렉터를 빈 값({})으로 두면요?"**
> **빈 셀렉터는 전부 매치, null(필드 미지정)은 아무것도 매치 안 함** — 정반대 동작이라 주의해야 합니다.

## 어떤 문제가 나올까

**C(결정 근거)가 가장 많이 나올 것으로 봅니다.**
검증 포인트가 "외웠는가"가 아니라 **"이해하고 결정했는가"** 이기 때문입니다. 저희 구성(PSA 레벨 배치, Vault 1 vs Alertmanager 3, StatefulSet 선택, 실측 기반 수치)의 **"왜"** 를 물을 확률이 높습니다.
- 특히 **C1은 정정된 내용으로** 답해야 합니다.

**B(비교·구분)는 고전 문제입니다.**
단골: RBAC 4조합(특히 ClusterRoleBinding+Role 불가), PV/PVC 방향, base64 ≠ 암호화

**D(실무 함정)는 "그거 없으면 / 틀리면 어떻게 되는데요?" 패턴입니다.**
각 오브젝트의 **부재·오설정 시나리오**를 답할 수 있어야 꼬리질문에서 안 무너집니다.

## 마지막 점검 — 이것만은 틀리지 마세요

| # | 함정 | 정답 |
| --- | --- | --- |
| 1 | hostPath는 baseline에서 되나? | ❌ **baseline에서도 금지.** privileged 필요 |
| 2 | enforce=restricted면 위반 Deployment가 apply 실패하나? | ❌ **apply는 성공.** 파드만 거부 → replica 0 |
| 3 | ClusterRoleBinding + Role 가능한가? | ❌ **유일하게 불가** |
| 4 | Secret은 암호화되나? | ❌ **base64 인코딩.** etcd 암호화 별도 필요 |
| 5 | RWO는 파드 하나만? | ❌ **노드 단위.** 파드 단위는 RWOP |
| 6 | NetworkPolicy만 만들면 차단되나? | ❌ **지원 CNI 필수.** 없으면 조용히 무시 |
| 7 | Headless는 Service 타입인가? | ❌ **타입 아님.** `clusterIP: None` 설정 |
| 8 | PrometheusRule 만들면 슬랙 알람 오나? | ❌ **발화까지만.** 발송은 Alertmanager |
| 9 | metrics-server 없이 HPA 되나? | ❌ **지표 unknown → 동작 불가** |
| 10 | Namespace가 보안 경계인가? | ❌ **소프트 격리.** 정책을 얹어야 격리됨 |
