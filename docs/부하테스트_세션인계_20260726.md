## 0. 지금 무엇을 하고 있나 (한 문단 요약)

**Docker Compose 단계인 현재 production 환경에서 부하테스트를 해서, "컨테이너 1개가 감당하는
최대 처리량과 그때의 CPU/메모리"를 실측한다.** 그 결과가 **나중에 k8s로 이관할 때
레플리카 수와 requests/limits를 정하는 근거**가 된다.

발단은 팀 슬랙 논의였다:
- 김성애(팀장): "쿠버 마이그레이션인데 그거 결과치대로 나중에 레플리카 주는 거 생각해야되니까"
- 최윤경(부팀장): "몇 명까지 버틸 수 있나 테스트해서 그 최댓값을 구한 다음, 그 값에서 n번
  부하테스트를 돌리면서 그라파나에서 컨테이너별 메모랑 CPU 얼마나 먹는지 확인하면 될거야"

### ⚠️ 이 단계에서 다루지 않는 것 (사용자 명시)

**아직 k8s로 이관하지 않았다.** 따라서 아래는 지금 참고 대상이 아니다:
- k8s 시방서(`k8s_DangDang_시방서 (2)-*.csv`)의 requests/limits/HPA/ResourceQuota
- 워커 노드 용량, LimitRange, 네임스페이스 설계

이전 세션에서 이쪽으로 한 번 빠졌다가 사용자가 바로잡았다. **부하테스트는 Docker 단계에서 한다.**

## 1. 확정된 결정

### 도구: k6 (Grafana k6)

6개 도구(k6 / Locust / nGrinder / JMeter / Gatling / Artillery)를 7개 기준으로 비교해 선정.

| 기준 | k6가 통과하는 이유 |
| --- | --- |
| 유지보수 활성도 | Grafana Labs 활발 |
| open model (RPS 램핑) | `ramping-arrival-rate` executor 내장 → knee point 정확 측정 |
| Prometheus 연동 | **내장** (`experimental-prometheus-rw`, k6 v0.42.0+, xk6 빌드 불필요) |
| git 리뷰 | JS 파일 |
| 생성기 오버헤드 | Go 고루틴 기반, 낮음 |
| k8s 재사용 | k6-operator |
| 학습비용 | 낮음 |

**결정적 근거**: 우리 Prometheus에 remote-write 수신기가 **이미 켜져 있다**
→ [infra/monitoring/docker-compose.yml:25](../infra/monitoring/docker-compose.yml#L25) `--web.enable-remote-write-receiver`
→ **추가 인프라 0으로 k6 결과가 그라파나에 꽂힌다.**

**nGrinder는 배제.** naver/ngrinder 저장소가 **2025-09-24 아카이브(read-only)** 되어 더 이상
유지보수되지 않는다(마지막 릴리스 3.5.9-p1). 보안 패치 없음 + Prometheus 연동 없음.
출처: https://github.com/naver/ngrinder

**chaos 계열(Chaos Mesh/Litmus)은 다른 범주** — 부하 생성이 아니라 장애 주입.
k8s 이관 후 "레플리카가 실제로 장애를 흡수하나" 검증용. 지금은 대상 아님.

### 실행 명령 (확정)

```bash
K6_PROMETHEUS_RW_SERVER_URL=http://100.110.81.51:9090/api/v1/write \
K6_PROMETHEUS_RW_TREND_STATS="p(95),p(99),avg,max" \
k6 run -o experimental-prometheus-rw script.js
```

> `K6_PROMETHEUS_RW_TREND_STATS` 축소와 요청별 `name` 태그는 **필수**.
> Prometheus가 `mem_limit 512m` / `retention.size 2GB`로 작아서 카디널리티 폭발에 약하다.
> **k6 버전은 도커 이미지 태그로 고정할 것** — `experimental-` 접두어라 버전 간 breaking
> change가 가능하고, n회 반복 비교 중 버전이 바뀌면 회차 간 비교가 무효가 된다.

`x-hardening` 앵커를 9개 서비스 전부가 `<<: *hardening`으로 상속:

## 4. 🔑 가장 중요한 발견 — 병목은 CPU가 아니라 메모리다

트래픽이 거의 없는 지금도 **login-service가 메모리 한도의 97.6%를 쓰고 있다.**
반면 CPU는 가장 높은 ingredients도 37.6%로 여유가 넉넉하다.

### 부하테스트 설계에 주는 의미

윤경님이 말한 "버티지 못하는 순간"의 **형태가 응답 지연이 아니라 OOMKill(컨테이너 강제 종료)** 이 된다.

- ❌ CPU 포화로 p95가 서서히 나빠지는 완만한 knee point
- ✅ 메모리가 256MiB를 치는 순간 컨테이너가 죽고 재시작 → **에러율이 절벽처럼 튐**

k6로 부하를 올리면 **login / ai / diet 세 개는 거의 확실히 OOMKill된다.**
그 자체가 유효한 측정 결과지만, 준비 없이 production에서 터뜨리면 사고다.

### 그래서 부하테스트 단계 설계

```
0단계  OOMKill 이력 확인 + Grafana 알람 silence 설정        ← 부하 걸기 전 필수
1단계  Smoke (1 VU, 1분) — 스크립트 검증
2단계  메모리 여유 있는 서비스부터 (main / admin / recipe / ingredients)
       → CPU knee point를 정상적으로 측정 가능
3단계  메모리 한계 서비스 (login / ai / diet)
       → mem_limit을 512m로 임시 상향한 뒤 측정
       → "제한이 없을 때 실제로 얼마나 먹는지"를 알아야 k8s limits 근거가 생김
4단계  전체 시나리오 부하 (로그인 → 목록 → 상세)
```

**3단계가 핵심.** 지금 256MiB에 눌린 상태로 재면 "256MiB까지 쓰더라"는 동어반복만 나온다.
제한을 풀고 재야 진짜 필요량이 나오고, 그게 k8s `limits.memory`의 근거가 된다.

### 방법론 보완점 (윤경님 원안 대비)

1. **"버틴다"를 SLO로 못 박을 것** — k6 thresholds에 코드로:
   `http_req_duration: ['p(95)<500']`, `http_req_failed: ['rate<0.01']`
2. **포화점에서 리소스를 재면 안 됨** — CPU 100% 찍힌 값은 "필요량"이 아니라 "한계치".
   측정 지점은 **SLO를 지키는 최대 부하(knee point)**.
3. **VU가 아니라 RPS로 올릴 것** — VU 방식(closed model)은 서버가 느려지면 부하도 같이 줄어
   한계를 과소 측정한다. `ramping-arrival-rate`(open model) 사용.
4. **n회 반복 시** 첫 1~2분(워밍업)은 버리고, 평균이 아니라 **회차별 p95 편차**를 볼 것.

- 워커 노드 가용 CPU 10 vs 시방서 필요량 17.95 CPU → **현 설계로는 배포 불가**
  (마스터 4 CPU / 워커 2 CPU 배치가 역전. 재배치하면 총량 변화 없이 해결)
- 시방서 Deployments.csv의 백엔드 서비스명(quote/news/mypage/search)이 **실제와 불일치**.
  `@NameSpace.csv`와 cAdvisor 실측이 일치하므로 그쪽이 정답
- `dang-pipeline` 네임스페이스가 Deployments/HPA/LimitRange/ResourceQuota 어디에도 없음
- kafka 메모리 requests 1Gi < 실측 1.07GiB (유일하게 **부족**한 항목)

## 8. 재현용 명령어

```bash
# 컨테이너별 CPU (7일 p95)
curl -s -G 'http://100.110.81.51:9090/api/v1/query' \
  --data-urlencode 'query=quantile_over_time(0.95, sum by (name) (rate(container_cpu_usage_seconds_total{job="cadvisor-production-vm"}[5m]))[7d:5m])'

# 컨테이너별 메모리 (7일 최대) — working_set이 OOMKill 판정 기준
curl -s -G 'http://100.110.81.51:9090/api/v1/query' \
  --data-urlencode 'query=max_over_time(sum by (name) (container_memory_working_set_bytes{job="cadvisor-production-vm"})[7d:5m])'

# 컨테이너별 적용된 mem_limit
curl -s -G 'http://100.110.81.51:9090/api/v1/query' \
  --data-urlencode 'query=max by (name) (container_spec_memory_limit_bytes{job="cadvisor-production-vm",name!=""})'
```

> 주의: `container_spec_memory_limit_bytes`를 `/ on(name)`으로 나누면 **stale series(옛 컨테이너 ID)
> 때문에 duplicate series 오류**가 난다. `max by (name)`으로 각각 뽑아 손으로 나눌 것.

## 9. 부하테스트 스크립트 뼈대 (아직 미작성 — Q1 확정 후 작성)

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  scenarios: {
    breakpoint: {
      executor: 'ramping-arrival-rate',   // open model: 초당 요청 수 기준
      startRate: 10, timeUnit: '1s',
      preAllocatedVUs: 50, maxVUs: 500,
      stages: [
        { target: 50,  duration: '2m' },
        { target: 100, duration: '2m' },
        { target: 200, duration: '2m' },
        { target: 400, duration: '2m' },
      ],
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<500'],   // SLO를 코드에 명시
    http_req_failed:   ['rate<0.01'],
  },
};

export default function () {
  // name 태그로 URL 그룹핑 — 카디널리티 폭발 방지 (R3)
  const res = http.get('http://10.10.10.30:8080/...', { tags: { name: 'xxx' } });
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}
```

**레플리카 산정 공식 (부하테스트 후 적용)**
```
레플리카 1개의 SLO 처리량 = R (knee point RPS)
목표 RPS = T  →  replicas = ceil(T / R) × 1.3   (30% 여유)

requests.cpu    = knee point 평균 CPU
limits.cpu      = 피크 CPU × 1.5~2.0   (CPU limit은 좁히면 CFS 스로틀링으로 p95가 튐)
requests.memory = knee point 평균 메모리
limits.memory   = 피크 메모리 × 1.3~1.5  (초과 시 OOMKill이라 여유 필요)
HPA target      = 60~70%, CPU 기준만 (메모리 기반 HPA는 scale-down이 안 일어남)
```
