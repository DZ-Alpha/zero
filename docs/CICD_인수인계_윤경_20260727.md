# CI/CD 인수인계 — 김지훈 → 이윤경

> 작성 2026-07-27 · K8s 이관에 맞춰 CI/CD 담당 변경
> **읽는 순서**: 1장(현황) → 2장(뭐가 바뀌나) → **3장(USB로 옮길 것)** → 4장(구축 순서) → 6장(함정)

---

## 0. 세 줄 요약

1. 지금 CI/CD는 **GitHub Actions + harbor VM에 설치한 self-hosted 러너**로 돌아갑니다. Jenkins는 안 씁니다.
2. 이번엔 **외부 호스트의 VirtualBox VM**에 러너·SonarQube·Trivy를 **컨테이너 없이 직접 설치**합니다.
3. **USB로 가져갈 가치가 있는 건 3개뿐**입니다 — Harbor CA 인증서, SonarQube DB 덤프, 자격증명 목록. 나머지는 Git에 있거나 새로 만드는 게 낫습니다.

## 1. 지금 무엇이 돌고 있나

### 1-1. 전체 그림

```
개발자 push → GitHub
                ↓
     ┌──────────┴──────────┐
     │                     │
 cloud 러너            self-hosted 러너
 (ubuntu-latest)       (harbor VM 안)
 빌드·테스트·Sonar      이미지 빌드·Trivy·Harbor push·배포
                          ↓
                    Harbor 레지스트리 → production VM
```

- **워크플로우 4개**: `build-test.yml`(본체, **2,084줄 / job 18개**), `lint.yml`, `infra-drift-check.yml`, `monitoring-watchdog.yml`
- **러너 배분**: cloud `ubuntu-latest` 10개 job / **self-hosted 11개 job**
- self-hosted를 쓰는 이유: **Harbor가 사내망에만 있어서** 외부 러너에서 push가 안 됩니다

### 1-2. 파이프라인 단계

| 순서 | 단계 | 도구 | 통과 못 하면 |
| --- | --- | --- | --- |
| 1 | 변경 감지 | `dorny/paths-filter` | — (바뀐 것만 진행) |
| 2 | 빌드·테스트 | Node / Python | 중단 |
| 3 | **코드 품질** | SonarQube **Quality Gate** | **중단** |
| 4 | 이미지 빌드 | docker buildx | 중단 |
| 5 | **취약점 스캔** | **Trivy** (`CRITICAL,HIGH` → `exit-code 1`) | **중단** |
| 6 | 레지스트리 push | Harbor | 중단 |
| 7 | 배포 | SSH + docker compose | 헬스체크 실패 시 **자동 롤백** |
| 8 | 알림 | Slack | — |

### 1-3. GitHub Secrets (9개) — 값은 GitHub에 있으니 옮길 필요 없음

| 이름 | 용도 | K8s 단계에서 |
| --- | --- | --- |
| `HARBOR_ROBOT_USER` / `HARBOR_ROBOT_TOKEN` | Harbor 로그인 | **계속 필요** |
| `SONAR_TOKEN` | SonarQube 인증 | **새 서버용으로 재발급** |
| `SLACK_WEBHOOK_URL` | 알림 | 계속 필요 |
| `PROD_VM_SSH_PASSWORD` / `DB_VM_SSH_PASSWORD` | 배포 SSH | **불필요해짐** (kubectl로 대체) |
| `PUBLIC_APP_URL` / `ADMIN_PUBLIC_APP_URL` / `BACKEND_GATEWAY_URL` | 빌드 시 주입 | 값만 갱신 |

> ⚠️ **실제 비밀번호·토큰 값은 이 문서에 없습니다.** `harbor.credentials.local.md`(gitignore됨)에 있고, **직접 만나서 전달**하는 게 원칙입니다. 슬랙·메일로 보내지 마세요.

## 2. 무엇이 바뀌나

| | 도커 단계 (지금) | K8s 단계 (앞으로) |
| --- | --- | --- |
| **CI/CD 위치** | harbor VM (Proxmox) | **외부 호스트의 VirtualBox VM** |
| **설치 방식** | 컨테이너(docker compose) | **직접 설치** (systemd 서비스) |
| **배포 대상** | production VM 1대 | **K8s 클러스터** (마스터 1 + 워커 5) |
| **배포 방법** | SSH → `docker compose up -d` | `kubectl apply` 또는 **ArgoCD** |
| **롤백** | 직전 이미지 태그로 재배포 | `kubectl rollout undo` (내장) |
| **헬스체크** | 배포 후 `curl /health` 스크립트 | **readiness probe** (플랫폼이 함) |
| **네트워크** | 같은 Proxmox 안 | **외부 → 사내망**, 경로 확보 필요 ⚠️ |

### 이 변경에서 가장 신경 쓸 것

**① 네트워크 도달성이 최대 난관입니다**

지금은 러너가 harbor VM 안에 있어서 Harbor·production이 **바로 옆**에 있습니다. 새 CI/CD VM은 **밖**에 있습니다.

확보해야 할 경로:
```
CI/CD VM → Harbor (harbor.hizero.local:443)     이미지 push
CI/CD VM → K8s API 서버 (마스터:6443)            kubectl 배포
CI/CD VM → GitHub (443)                          워크플로우 수신
```

**VirtualBox 네트워크 모드가 핵심입니다.** 기본값인 **NAT로 두면 밖에서 이 VM에 접근이 안 됩니다.** 브리지 어댑터로 바꿔서 VM이 사내망 IP를 직접 받게 해야 합니다.

**② 컨테이너 → 직접 설치로 바뀌면서 생기는 일**

컨테이너는 "이미지만 받으면 끝"이었는데, 직접 설치는 **OS 의존성을 직접 챙겨야** 합니다. 특히 SonarQube가 까다롭습니다(4장 참조).

## 3. USB로 옮길 수 있는 것 / 없는 것 ★

### ✅ 실제로 전달하는 파일 — **1개**

| # | 무엇 | 전달 | 왜 필요 |
| --- | --- | --- | --- |
| **1** | **Harbor CA 인증서** (`harbor-ca.crt`, 2,041 bytes) | USB 또는 메신저 (**공개 인증서라 무방**) | 새 VM이 `harbor.hizero.local`을 **TLS로 신뢰**하려면 필수. 없으면 `docker login`이 인증서 오류로 실패합니다. **7/19에 이것 때문에 하루를 썼습니다** |

**검증값** — 받은 뒤 대조하세요:
```bash
openssl x509 -in harbor-ca.crt -noout -fingerprint -sha256
# 64:CF:0A:D3:48:EE:D5:6C:E2:BD:E3:CB:AC:6C:C9:ED:31:8D:86:F2:CC:5E:89:DC:BD:D7:08:6E:AD:78:BF:90
```

> ⚠️ harbor VM의 `/data/cert/` 에는 **`ca.key`(CA 개인키)가 같이** 있습니다. 유출되면 우리 도메인 인증서를 누구나 위조할 수 있습니다.
> 그래서 개인키가 없는 `/etc/docker/certs.d/harbor.hizero.local/ca.crt` 에서 추출했습니다. **직접 뽑을 일이 있으면 이 경로를 쓰세요.**

### 🔑 파일이 아니라 **새로 발급**하는 것 (2개)

자격증명은 **이전(transfer)이 아니라 회전(rotate)** 이 원칙입니다. 담당이 바뀌면 이전 담당자도 계속 접근 가능한 상태가 되고, 사고 시 추적이 안 되기 때문입니다.

| 무엇 | 방법 |
| --- | --- |
| **Harbor robot 계정** | Harbor UI에서 **새로 발급** → 새 값을 GitHub Secrets(`HARBOR_ROBOT_USER`/`HARBOR_ROBOT_TOKEN`)에 등록. 기존 robot 계정은 전환 완료 후 **비활성화** |
| **SonarQube 토큰** | 새 SonarQube 기동 후 발급 → `SONAR_TOKEN` 갱신 |

> 전달 과정 자체가 없어지므로 **가장 안전하고 가장 빠릅니다.** (robot 계정 발급 30초)

### 📅 나중에 하나 더 생깁니다 — kubeconfig

클러스터 구축 후 **배포용 kubeconfig**가 필요합니다. 이건 **자격증명 파일**입니다.

- ❌ 메신저 금지 · ❌ 이메일 금지
- ✅ USB · Tailscale 직접 전송 · 사내망 `scp`
- ⚠️ `cluster-admin`이 아니라 **배포에 필요한 권한만** 담긴 것을 받으세요 (5장 참조)

### ❌ 옮기지 않기로 한 것

| 무엇 | 왜 |
| --- | --- |
| **SonarQube DB 덤프** | 새로 스캔하면 **현재 상태는 그대로** 나옵니다. 잃는 건 과거 추세뿐이라 이번 일정에선 이득이 없습니다. 게다가 덤프에는 **비밀번호 해시와 코드 조각**이 들어 있어 취급이 까다롭습니다. 품질 게이트 설정만 **스크린샷 1장**으로 넘깁니다 |
| **Trivy 취약점 DB 캐시** | **매일 갱신**되어 옮겨도 하루면 낡습니다. 첫 스캔 때 자동으로 받습니다(수 분) |
| **Docker 이미지 레이어 캐시** | 경로·스토리지 드라이버가 달라 **재사용이 안 됩니다** |
| **SSH 개인키** | 담당이 바뀌면 **키도 바뀌는 게 원칙**입니다. 새로 만들고 공개키를 등록하세요 |

### ❌ 옮길 수 없는 것 — 새로 해야 합니다

| 무엇 | 왜 |
| --- | --- |
| **GitHub Actions 러너 등록** | 등록 토큰이 **그 호스트에 묶여** 있습니다. 새 VM에서 **재등록 필수**입니다. 기존 러너는 GitHub 설정에서 지워주세요 (안 지우면 offline 러너가 남아 job이 걸립니다) |
| **Harbor robot 계정 토큰** | 토큰은 **발급 시 한 번만** 보입니다. 저장해둔 값이 없으면 **새로 발급**해야 합니다 |
| **systemd 서비스 설정** | 도커 단계엔 없었습니다. 새로 작성해야 합니다 |

### 📦 USB가 필요 없는 것 — 이미 Git에 있습니다

`.github/workflows/*.yml` · `sonar-project.properties` · `.trivyignore` · `infra/` 아래 compose 파일 · 문서·런북

> **저장소만 clone하면 됩니다.** 이게 CI/CD를 코드로 관리한 이득입니다.

## 4. 새 환경 구축 순서

### 4-1. VM 사양 권장

| 항목 | 권장 | 이유 |
| --- | --- | --- |
| CPU | 4코어 이상 | 이미지 빌드가 CPU를 많이 씁니다 |
| 메모리 | **8GB 이상** | SonarQube만 2GB+, Elasticsearch가 내장돼 있습니다 |
| 디스크 | **100GB 이상** | 이미지 레이어가 빠르게 쌓입니다. 도커 단계에서 **디스크 고갈로 파이프라인이 멈출 뻔했습니다** |
| 네트워크 | **브리지 어댑터** | NAT면 외부에서 접근 불가 |
| OS | Ubuntu 22.04 / 24.04 LTS | 기존과 동일하게 |

### 4-2. 설치 순서 (의존성 순서대로)

**① 기본 패키지**
```bash
sudo apt update && sudo apt install -y curl git jq unzip ca-certificates
```
> `jq`와 `unzip`은 워크플로우가 실제로 씁니다. 도커 단계에서 **unzip이 없어 파이프라인이 실패**한 적이 있습니다.

**② Docker** (이미지 빌드용 — CI/CD 자체는 컨테이너로 안 돌리지만 빌드에는 필요)
```bash
# 공식 설치 스크립트 사용 후
sudo usermod -aG docker $USER    # 재로그인 필요
```

**③ Harbor CA 신뢰 등록** ← USB에서 가져온 파일
```bash
sudo mkdir -p /etc/docker/certs.d/harbor.hizero.local
sudo cp ca.crt /etc/docker/certs.d/harbor.hizero.local/
sudo cp ca.crt /usr/local/share/ca-certificates/harbor-ca.crt
sudo update-ca-certificates
sudo systemctl restart docker
```
**검증**: `docker login harbor.hizero.local` 이 성공해야 다음으로 갑니다.

**④ DNS 해석** — `harbor.hizero.local`이 안 풀리면 `/etc/hosts`에 추가
```
192.168.0.53   harbor.hizero.local
```

**⑤ GitHub Actions 러너 설치**
> GitHub 저장소 → Settings → Actions → Runners → New self-hosted runner 에서 **그때 발급되는 명령**을 그대로 씁니다. 토큰은 유효기간이 짧으니 미리 받아두지 마세요.

설치 후 **systemd 서비스로 등록**하는 게 중요합니다:
```bash
sudo ./svc.sh install
sudo ./svc.sh start
```
> 이걸 안 하면 **터미널을 닫는 순간 러너가 죽습니다.**

**⑥ Trivy** (바이너리 직접 설치)
```bash
# 워크플로우가 참조하는 경로 구조를 맞춰야 합니다
mkdir -p ~/.trivy-bin ~/.trivy-cache
```
> ⚠️ **워크플로우 수정 필요**: 현재 경로가 `/home/bruce/.trivy-bin/${{ runner.name }}`로 **하드코딩**돼 있습니다(`build-test.yml` 708·1343·1491줄). 새 VM의 사용자명이 `bruce`가 아니면 **여기를 고쳐야** 합니다.

**⑦ SonarQube 직접 설치** ← 여기가 가장 까다롭습니다

컨테이너로 할 땐 안 보이던 것들이 나옵니다:

| # | 요구사항 | 안 하면 |
| --- | --- | --- |
| 1 | **Java 17 이상** | 기동 실패 |
| 2 | **PostgreSQL 별도 설치** | 내장 DB는 운영 불가 |
| 3 | `vm.max_map_count=524288` 커널 파라미터 | **Elasticsearch가 기동 안 됩니다** |
| 4 | `fs.file-max=131072` | 동일 |
| 5 | **root로 실행 금지** | Elasticsearch가 거부합니다. 전용 계정 필요 |

```bash
# ③④ 설정 (재부팅해도 유지)
echo "vm.max_map_count=524288" | sudo tee -a /etc/sysctl.conf
echo "fs.file-max=131072" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

**⑧ SonarQube DB 복원** ← USB에서 가져온 덤프
```bash
psql -U sonar -d sonar < sonarqube_backup.sql
```
> 복원 후 SonarQube를 기동하면 기존 프로젝트와 품질 게이트가 살아납니다.

**⑨ kubectl 설치 + kubeconfig 배치**
```bash
mkdir -p ~/.kube && cp <받은 config> ~/.kube/config
kubectl get nodes    # 이게 되면 배포 준비 완료
```
> kubeconfig는 성애님/지훈에게 요청하세요. **관리자 권한 전체를 받지 말고**, 배포에 필요한 권한만 있는 ServiceAccount 기반 kubeconfig를 받는 게 맞습니다 (아래 5장).

## 5. 워크플로우에서 바꿔야 할 곳

| # | 위치 | 지금 | 바꿀 것 |
| --- | --- | --- | --- |
| 1 | `build-test.yml` 708·1343·1491 | `/home/bruce/.trivy-bin/...` | 새 VM 사용자 경로로 |
| 2 | `backend-deploy-production` job | SSH + `docker compose up -d` | `kubectl set image` 또는 ArgoCD 동기화 |
| 3 | `Health check` step | `curl /health` | **삭제** — readiness probe가 대신합니다 |
| 4 | `Rollback` step | 직전 태그로 재배포 | `kubectl rollout undo` |
| 5 | `bgateway-cutover` job | compose 재생성 | K8s 배포로 통합 |
| 6 | `infra-drift-check.yml` | compose 파일 비교 | **GitOps면 불필요해집니다** |
| 7 | Secrets | `PROD_VM_SSH_PASSWORD` 등 | 삭제하고 kubeconfig로 |

> **⚠️ 배포 job을 바꾸기 전에 반드시 확인**: 지금 배포는 **변경된 서비스만** 교체합니다(`--no-deps`). K8s로 옮길 때 이 "변경분만" 로직을 유지해야 합니다. 안 그러면 커밋 하나에 9개 서비스가 전부 재배포됩니다.

### 배포용 권한은 최소로 받으세요

`cluster-admin` kubeconfig를 받으면 편하지만, **CI/CD가 뚫리면 클러스터 전체가 뚫립니다.**
필요한 건 이 정도입니다:
```
Deployment  : get, list, patch, update
Pod         : get, list          (상태 확인용)
ReplicaSet  : get, list          (rollout 확인용)
```
지훈에게 이 권한만 있는 ServiceAccount와 kubeconfig를 요청하세요.

## 6. 알려진 함정 — 실제로 겪은 것들

전부 도커 단계에서 **실제로 발생했고 해결한** 것들입니다. 같은 데서 막히지 마세요.

| # | 증상 | 원인 | 해결 |
| --- | --- | --- | --- |
| **1** | Harbor push가 인증 실패 | **`echo`로 넘긴 비밀번호 끝의 개행** | `--password-stdin` 사용 (`printf '%s'` 조합) |
| **2** | Harbor 접속이 인증서 오류 | CA 신뢰 등록 안 됨 | 4장 ③번. **디렉터리 존재가 아니라 파일 내용까지** 확인 |
| **3** | 서비스를 추가했는데 **에러 없이 빌드에서 빠짐** | paths-filter에 배선 누락 | 지금은 **누락 시 파이프라인이 일부러 실패**하는 가드가 있습니다. 그 에러 메시지를 그대로 따르세요 |
| **4** | 러너 2대 동시 실행 시 Trivy 충돌 | 설치 경로가 같음 | 경로에 `${{ runner.name }}` 포함 (이미 반영) |
| **5** | SonarQube 2회차 분석이 오탐 | CE 버전은 브랜치 분석이 없어 프로젝트가 섞임 | 브랜치별 임시 프로젝트를 **분석 전 초기화** |
| **6** | 디스크 고갈로 파이프라인 정지 직전 | 로컬 이미지 누적 | `runner-cleanup` job이 정리합니다. **새 VM에서도 반드시 유지** |
| **7** | 일회성 job을 돌렸는데 배포까지 됨 | `deploy_target` 기본값이 `both` | 수동 실행 시 **`deploy_target=none`** 을 반드시 지정 |
| **8** | 머지됐는데 배포가 안 됨 | 배포 감지 경로에 `infra/` 누락 | 배포 경로를 바꿀 땐 **paths-filter도 같이** 확인 |
