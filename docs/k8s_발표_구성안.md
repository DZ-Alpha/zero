# K8s 발표 구성안 — 스토리라인 + 시연 1개

> 김지훈 · **보안 / 모니터링** · 작성 2026-07-27
> 전제: 발표 8/04, 구축 7/27~7/31, 검증 8/02
> ⚠️ **담당 범위**: K8s 단계에서는 **CI/CD를 맡지 않습니다.** 도커 단계와 달리 보안·모니터링에만 집중합니다.
> → 파이프라인·ArgoCD·이미지 빌드는 **타 담당의 발표 파트**이므로, 이 구성안은 그 영역을 **전제조건으로만** 다룹니다.
> **이 문서의 진짜 목적**: 발표 구성이 아니라 **"구축하면서 무엇을 남겨야 하는가"** 를 지금 확정하는 것

---

## 0. 왜 스토리라인인가 — 도커 때와의 차이

도커 발표는 **끝난 뒤에 커밋 307건을 역복원**해서 서사를 만들었습니다. 남은 흔적 안에서 이야기를 찾은 것입니다.

K8s는 아직 시작 전입니다. **스토리를 먼저 정하고, 그 스토리가 요구하는 증거를 구축하면서 수집**할 수 있습니다.

> ⚠️ **가장 흔한 실패**: 구축을 다 끝내고 8/2에 PPT를 만들려고 보면, **정작 필요한 순간의 화면이 없습니다.**
> 정책이 차단되던 순간, 파드가 거부되던 순간, 알람이 울리던 순간은 **그때 찍지 않으면 재현 비용이 큽니다.**
> → 그래서 6장의 **촬영 체크리스트**가 이 문서의 핵심입니다.

## 1. 관통선 — 이 발표가 하는 한 가지 주장

> ### "도커에서 **손으로 만들어야 했던 안전장치**가, K8s에서는 **플랫폼이 보장하는 구조**가 됩니다."

이게 관통선입니다. 개념 설명이 아니라 **이전(移轉)의 서사**입니다. 이 문장이 좋은 이유:

- 도커 파트 발표와 **자연스럽게 이어집니다** (같은 사람이 같은 문제를 계속 푼 것)
- 개념(PSA·RBAC·NetworkPolicy)이 **"왜 필요한가"** 안에서 나옵니다 — 용어 나열이 아니라
- "K8s를 왜 쓰나"라는 질문에 **미리 답한 상태로** 시작합니다

### 대응표 — 1장 슬라이드로 쓸 것

**보안·모니터링 항목만 골랐습니다.** (CI/CD 항목은 타 담당 파트라 제외)

| 도커에서 손으로 만든 것 | K8s에서 대체되는 것 |
| --- | --- |
| compose 앵커로 하드닝 설정을 **9개 서비스에 복붙** | **PSA + SecurityContext** — 위반하면 파드가 아예 안 뜸 |
| 백엔드 포트를 **loopback에 묶어** 우회 차단 | **NetworkPolicy** — L3/L4 정책으로 선언 |
| 컨테이너마다 `mem_limit`·로그 로테이션 **수동 지정** | **LimitRange + ResourceQuota** — admission이 강제 |
| 자격증명을 **gitignore 파일로 분리**해 보관 | **SealedSecret + etcd 암호화** — 봉인해서 Git에 두고 저장도 암호화 |
| 배포 후 `curl /health` 확인 스크립트 | **readiness probe** — 통과 전엔 트래픽이 안 들어감 |
| Grafana JSON 프로비저닝으로 알람 관리 | **PrometheusRule CRD** — admission이 잘못된 PromQL을 생성 시점에 차단 |

> 발표 문장: *"도커에서는 이 여섯 가지를 제가 설정과 스크립트로 일일이 만들었습니다. K8s에서는 플랫폼이 강제합니다. **그래서 제 일은 만드는 것에서 올바르게 선언하는 것으로 바뀝니다.**"*

> **담당 전환 한 줄 처리**: *"도커 단계에서는 CI/CD와 관측을 함께 맡았고, K8s에서는 **보안과 모니터링에 집중**했습니다."*
> 굳이 길게 설명하지 않습니다. 한 줄이면 충분하고, 오히려 **범위가 명확해서 깊이가 생겼다**는 인상을 줍니다.

## 2. 슬라이드 구성 (본편 20~22장 / 15분 기준)

시간이 다르면 3장과 4장의 분량으로 조절합니다. **1·5장은 줄이지 않습니다.**

### 1막 · 왜 옮기는가 (2장, 1.5분)

| # | 슬라이드 | 담을 것 |
| --- | --- | --- |
| 1 | **도커에서 손으로 만든 것들** | 위 대응표 6줄. 도커 발표를 안 본 사람도 이해되게 |
| 2 | **그래서 무엇을 옮기나** | 이관 범위 한 장 — **보안 5겹 + 관측 스택**. 담당이 보안·모니터링임을 명시하고, **파이프라인은 타 담당**임을 그림에서 회색 처리 |

### 2막 · 경계를 5겹으로 그었다 (7장, 5분) ★개념이 들어가는 자리

**각 겹마다 같은 4줄 틀을 씁니다.** 반복 구조라 청중이 예측하며 따라옵니다.

> **무엇을 막나 → 왜 이 레벨로 정했나 → 우리 클러스터 적용값 → ⚠️ 흔한 오해**

| # | 겹 | 핵심 개념 | 여기서만 말할 것 |
| --- | --- | --- | --- |
| 3 | 전체 지도 | 5겹 개요 | 한 장에 5겹이 겹쳐 보이는 그림 |
| 4 | **1겹 Namespace** | 소프트 격리 | ⚠️ **"네임스페이스는 보안 경계가 아닙니다."** 공식 문서도 격리를 강제하지 않는다고 명시. **정책을 걸 자리**를 주는 것 |
| 5 | **2겹 PSA** | 무엇으로 실행되는가 | 3레벨×3모드. **restricted를 원칙**으로, DB는 baseline, 관측 DaemonSet은 privileged — **hostPath가 baseline에서도 금지**라 불가피 |
| 6 | **3겹 RBAC** | 무엇을 조작하는가 | SA는 **신원만** 증명, 권한은 RoleBinding으로 별도. K8s에 **사람용 User 오브젝트가 없다**는 사실 |
| 7 | **4겹 NetworkPolicy** | 무엇과 통신하는가 | 기본은 **비격리(전부 허용)**. 정책이 선택하는 순간 격리. **default-deny 3계층** + DNS 예외 |
| 8 | **5겹 Secret** | 무엇을 아는가 | **base64는 암호화가 아님.** SealedSecret(Git 구간) / Vault(런타임) / etcd 암호화(저장) — **보호 구간이 달라 대체 불가** |
| 9 | **적용 결과 한 장** | — | 네임스페이스별 PSA 레벨·Quota·정책 수를 표로. **"선언했다"의 증거** |

### 3막 · 함정 3개 (3장, 2.5분) ★가장 기억에 남는 구간

도커 발표에서 가장 반응이 좋았던 게 *"조용한 실패"* 였습니다. 같은 축을 K8s에서 이어갑니다.

| # | 함정 | 왜 무서운가 | 어떻게 막았나 |
| --- | --- | --- | --- |
| 10 | **enforce는 apply를 막지 않는다** | 위반 Deployment도 **apply는 성공**. 파드만 거부돼 **replica 0으로 조용히 실패** | `warn`·`audit`을 같은 레벨로 병행 → apply 시점에 경고. KSM의 **replica 불일치 지표**로 탐지 |
| 11 | **CNI가 없으면 정책이 무효** | 미지원 CNI에서 NetworkPolicy는 **오류 없이 조용히 무시**. default-deny 3계층이 통째로 무효인데 아무도 모름 | CNI를 **이관 전제조건으로 못박음** + 적용 후 **실제 연결 테스트로 차단 확인** |
| 12 | **default-deny egress의 DNS** | DNS(53)를 안 열면 **이름 해석부터 실패**해 전 서비스 장애. 가장 흔한 사고 | 예외 1순위로 CoreDNS 53(UDP/TCP) 명시 |

> 이 3장은 **"공부해서 아는 것"이 아니라 "설계에 반영한 것"** 으로 말합니다.
> *"이 세 가지는 저희가 실제로 대응한 것들입니다."*

### 4막 · 관측을 옮겼다 (4장, 3분)

| # | 슬라이드 | 담을 것 |
| --- | --- | --- |
| 13 | **무엇을 어떤 워크로드로 띄웠나** | Deployment / StatefulSet / DaemonSet **선택 근거** — 공식 4조건. Prometheus는 왜 STS, Grafana는 왜 Deployment |
| 14 | **왜 노드마다 1개여야 하나** | DaemonSet — replica를 노드 수만큼 줘도 **같은 노드에 몰릴 수 있고 노드 증가를 못 따라감** |

## 3. 시연 — 「파드 하나가 일하기까지」 (2분 45초)

### 판단 기준 (이걸로 골랐습니다)

| # | 기준 | 왜 |
| --- | --- | --- |
| 1 | **눈에 보이게 실패해야** | 보안은 작동할 때 안 보입니다. **막히는 것**을 보여주는 것 말고 증명 수단이 없습니다 |
| 2 | **같은 명령, 다른 결과** | 명령을 바꾸면 "다른 걸 친 것 아니냐"가 됩니다. **변수는 정책 하나**여야 합니다 |
| 3 | **인프라 의존이 적어야** | CNI·HPA·외부망에 걸리면 당일에 죽습니다 |
| 4 | **의외성** | 청중이 이미 믿는 걸 보여주면 기억에 안 남습니다 |
| 5 | **부분 실패해도 완주** | 폴백으로 **갈아타는** 것보다, 일부만 빼고 **끝까지 가는** 게 낫습니다 |

### ✅ 최종안 — 하나의 파드, 세 개의 관문

> **컨셉**: 파드 **하나**를 띄워서 일을 시킵니다. 그 앞에 관문이 세 개 있습니다.
> **각 관문마다 「거부 → 정책 부여 → 허용」이 반복**되고, 명령은 매번 **똑같은 것**을 칩니다.

#### 🚪 1관문 · 실행 권한 — "이 컨테이너로 살아도 되는가" (60초)

```bash
# 하드닝 안 된 워크로드를 restricted 네임스페이스에 배포
k apply -f demo-bad.yaml
#> deployment.apps/demo created                    ← 성공했습니다?

k get deploy demo
#> NAME   READY   UP-TO-DATE   AVAILABLE
#> demo   0/1     0            0                   ← ★ 파드가 없습니다

k describe rs -l app=demo | tail -6
#> Error creating: pods "demo-xxxxx" is forbidden:
#>   violates PodSecurity "restricted:latest":
#>   privileged, hostPath volumes, allowPrivilegeEscalation != false,
#>   unrestricted capabilities, runAsNonRoot != true, seccompProfile
```

> 🎙 **"apply는 성공했는데 파드가 0개입니다. 에러도 안 났습니다.**
> 이게 K8s에서 **가장 흔하고 가장 위험한 실패**입니다. 배포됐다고 믿는데 서비스는 안 뜬 상태입니다.
> 이유는 `enforce`가 **Deployment가 아니라 최종 파드에만** 적용되기 때문입니다.
> 그리고 지금 막힌 `privileged`와 `hostPath`는 **컨테이너 탈출에 쓰이는 바로 그 경로**입니다."

```bash
k apply -f demo-good.yaml          # SecurityContext 4종 추가
k get deploy demo
#> demo   1/1     1            1                   ← 통과
```

#### 🚪 2관문 · 조작 권한 — "무엇을 만질 수 있는가" (60초)

**같은 명령 4번. 답만 달라집니다.**

```bash
k auth can-i list pods --as=system:serviceaccount:dang-be-ns:demo-sa -n dang-be-ns
#> no                        ← 파드는 떴는데 아무것도 못 합니다

k apply -f demo-rbac.yaml    # Role(pods: get,list) + RoleBinding

k auth can-i list pods   --as=...:demo-sa -n dang-be-ns
#> yes                       ← 준 것만 생깁니다

k auth can-i delete pods --as=...:demo-sa -n dang-be-ns
#> no                        ← ★ 읽기만 줬으니 삭제는 안 됩니다 (최소권한)

k auth can-i list pods   --as=...:demo-sa -n dang-db-ns
#> no                        ← ★ Role은 그 네임스페이스 안에서만 (경계)
```

> 🎙 **"ServiceAccount는 '누구인가'만 증명합니다. 권한은 0입니다.**
> Role을 붙여야 생기고, **준 것만** 생깁니다. 읽기는 되지만 삭제는 안 되고, 이 네임스페이스에서만 됩니다.
> RBAC은 **더하기만 있고 빼기가 없어서**, 안 준 것이 곧 차단입니다."

**이 4줄이 최소권한·네임스페이스 경계·additive 원칙을 한 번에 증명합니다.**

---

#### 🚪 3관문 · 통신 권한 — "누구와 말할 수 있는가" (40초)

```bash
k exec deploy/demo -- curl -s --max-time 3 -o /dev/null -w '%{http_code}\n' \
  http://dang-be-main-svc:3002/health
#> curl: (28) Operation timed out                  ← default-deny가 막습니다

k apply -f demo-netpol.yaml     # demo → be 만 허용

k exec deploy/demo -- curl ... (동일 명령)
#> 200                                             ← 통과
```

> 🎙 **"파드가 뜨고 권한도 받았지만, 아직 아무와도 통신할 수 없습니다.**
> NetworkPolicy는 기본이 전부 허용인데, 정책이 그 파드를 **선택하는 순간 격리**됩니다.
> 그때부터는 **명시적으로 허용한 것만** 통과합니다."

#### 🏁 마무리 (15초)

> 🎙 **"파드 하나가 일하려면 실행 권한, 조작 권한, 통신 권한을 각각 따로 받아야 합니다.**
> 셋 다 **기본값이 '안 됨'** 이고, 저희는 필요한 것만 명시적으로 열었습니다.

### 왜 이게 최선인가

| 기준 | 이 시연의 답 |
| --- | --- |
| **1. 보이게 실패** | 3관문 전부 **거부 화면이 먼저** 나옵니다 |
| **2. 같은 명령** | 2관문은 **문자 그대로 같은 명령**이 no→yes로 바뀝니다. 3관문도 같은 curl. **변수는 정책뿐**입니다 |
| **3. 의존성** | 1·2관문은 **CNI·네트워크·외부 의존이 0**. 적합성 있는 클러스터면 무조건 됩니다 |
| **4. 의외성** | *"apply 성공인데 파드가 0개"* — 여기서 반응이 나옵니다. K8s를 아는 사람일수록 더 반응합니다 |
| **5. 부분 실패 대응** | **3관문만 빼면 1분 50초로 완주**합니다. 폴백으로 갈아탈 필요가 없습니다 ★ |
| **커버 범위** | Namespace · PSA · SecurityContext · SA · Role · RoleBinding · NetworkPolicy — **오브젝트 7종** |
| **서사 연결** | 1관문이 도커 발표의 *"조용한 실패"* 주제를 그대로 이어받습니다 |

### ❌ 뺀 후보와 이유

| 후보 | 왜 뺐나 |
| --- | --- |
| NetworkPolicy 단독 | **CNI 하나에 전부 걸립니다.** 그리고 "네트워크가 막힌다"는 청중이 이미 믿는 사실이라 의외성이 없습니다 |
| PSA 단독 | 반전은 가장 강하지만 **오브젝트 1종**뿐이라 설계 전체를 못 보여줍니다 |
| 파드 kill → 자동 복구 | 아는 사람에겐 당연하고, 모르는 사람에겐 그냥 재시작으로 보입니다 |
| HPA 스케일아웃 | 스케일 지연이 수십 초라 **대기 시간이 길고 실패 확률이 높습니다** |
| 탈취된 파드 공격 시나리오 | 드라마는 크지만 **거부만 있고 허용 대비가 없어** 최소권한 설계를 못 보여줍니다. → 1관문에서 `privileged`·`hostPath`가 막히는 것으로 **같은 메시지를 이미 전달**합니다 |
| Grafana 대시보드 투어 | 시연이 아니라 스크린샷이면 충분합니다 |
| 시연 2개 | 하나가 실패하면 **나머지도 신뢰를 잃습니다** |

### 🛠 준비물 (7/29 리허설까지)

| 파일 | 내용 |
| --- | --- |

## 4. 개념을 스토리에 녹이는 방법

개념 슬라이드가 **강의처럼 되지 않게** 하는 세 가지 규칙입니다.

**규칙 1 — 개념은 반드시 "우리 결정" 뒤에 붙인다**

| ❌ 이렇게 말하지 않기 | ✅ 이렇게 말하기 |
| --- | --- |
| "PSA에는 3개 레벨이 있습니다. privileged, baseline, restricted…" | "저희는 **restricted를 기본**으로 잡았습니다. 그런데 관측 DaemonSet은 노드의 `/proc`을 읽어야 해서 **baseline에서도 금지**되는 hostPath가 필요합니다. 그래서 그것만 별도 네임스페이스로 분리했습니다." |

**뒷 문장이 개념 설명을 이미 다 하고 있습니다.** 3레벨을 나열하지 않아도 청중은 레벨이 여러 개고 강도가 다르다는 걸 압니다.

**규칙 2 — 오해를 먼저 깨고 시작한다**

각 겹의 ⚠️ 줄은 **"이렇게 알기 쉬운데 사실은 다르다"** 형식입니다.
- "네임스페이스는 보안 경계 같지만 소프트 격리입니다"
- "Secret은 암호화 같지만 base64입니다"
- "NetworkPolicy는 만들면 되는 것 같지만 CNI가 없으면 무시됩니다"

**오해를 짚으면 그 개념은 기억에 남습니다.** 그냥 정의를 말하면 안 남습니다.

**규칙 3 — 숫자를 붙인다**

"NetworkPolicy를 적용했습니다"(X) → "**네임스페이스 8개 전부에 default-deny를 걸고, 허용 규칙 N개를 명시했습니다**"(O)

## 5. 도커 발표와의 관계

담당 범위는 좁아졌지만 **문제를 대하는 방식은 그대로**라는 게 이 발표의 힘입니다. 같은 사람이 같은 원칙을 계속 적용한 것으로 읽히게 만듭니다.

| 도커 발표의 주제 | K8s 발표에서 이어받는 자리 | CI/CD 담당이 아니어도 유효한가 |
| --- | --- | --- |
| "게이트를 먼저 세웠다" | 2막 — 워크로드보다 **경계를 먼저** 세움 | ✅ 게이트가 파이프라인에서 **admission으로 옮겨간 것**뿐 |
| "배포보다 관측을 먼저" | 4막 — 관측 스택 이관 | ✅ 관측은 계속 담당 |
| "조용한 실패가 제일 무섭다" | **3막 전체** — PSA enforce, CNI 무효, DNS 누락 | ✅ 오히려 **보안 영역에 더 많음** |
| "안 되는 건 안 된다고 남긴다" | 6막 — 아직 안 한 것 | ✅ 태도의 문제 |

> 도입에서 한 문장으로 연결하면 됩니다:
> *"도커 발표에서 가장 강조했던 게 '조용한 실패'였는데, **K8s 보안에도 정확히 같은 함정이 세 개** 있었습니다."*

**범위 축소를 약점으로 만들지 않는 법**: 도커에선 CI/CD까지 맡느라 보안이 *"파이프라인에 붙인 스캔"* 수준이었지만, K8s에선 **경계를 5겹으로 설계**할 수 있었다 — **범위가 좁아진 만큼 깊어졌다**는 프레임으로 갑니다.
