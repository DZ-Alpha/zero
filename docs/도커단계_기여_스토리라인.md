## 1장. 코드를 짜기 전에 유출부터 막았다 (7/08~7/10)

파이프라인을 만들기 전에 **gitleaks pre-commit 훅**부터 넣었습니다. 그리고 팀원이 각자 설치하게 스크립트로 만들어 배포했습니다.

> `feat(secops): add gitleaks pre-commit hook config and team setup script`

이유는 단순합니다. **시크릿은 한 번 올라가면 지워도 히스토리에 남습니다.** 커밋 시점에 막는 것 말고는 완전한 회수 방법이 없습니다.

같은 날 **lint 워크플로우**(shellcheck + yamllint)를 올렸습니다. 인프라를 셸 스크립트와 YAML로 다룰 거라, 그 두 개가 문법 오류로 깨지면 배포 자체가 안 됩니다. **다루게 될 언어의 검사부터 세운 것**입니다.

> **여기서 정한 기준**: 게이트는 나중에 붙이는 게 아니라 처음에 세운다.

**한 일**: 자격증명을 즉시 회전하고, 실제 비밀번호는 **gitignore된 로컬 파일**로 분리했습니다. 그리고 팀 규칙으로 **"추적되는 파일에 평문 비밀번호 금지"** 를 못박았습니다.

같은 날 파이프라인을 **끝에서 끝까지 한 번 통과**시키고 기록으로 남겼습니다.

## 3장. 배포를 자동화하기 전에 눈을 먼저 만들었다 (7/13~7/16) ★

순서를 이렇게 잡은 이유가 있습니다. **자동 배포를 먼저 켜면, 뭐가 깨졌는지 모르는 채로 빨라지기만 합니다.**

### 무엇을 어떻게 볼지 나눴다

| 보는 대상 | 도구 | 왜 나눴나 |
| --- | --- | --- |
| 호스트 자원 | node-exporter | VM 4대의 CPU·메모리·디스크 |
| 컨테이너 자원 | cAdvisor | 컨테이너별 사용량 — 나중에 **K8s requests/limits의 유일한 실측 근거**가 됨 |
| 서비스 외형 | blackbox-exporter | 사용자가 실제로 겪는 상태 |
| 미들웨어 | kafka-exporter | 큐 적체는 호스트 지표에 안 잡힘 |

메트릭은 **Prometheus**, 로그는 **Loki**, 트레이스는 **Tempo**, 시각화는 **Grafana**로 확정했습니다.

### 대시보드를 UI에서 손으로 만들지 않기로 했다

먼저 **as-code로 백업**(#13)하고, 이어서 **프로비저닝으로 전환**(#37)했습니다. UI에서 만들면 누가 언제 왜 바꿨는지 남지 않기 때문입니다.

가는 길에 두 번 걸렸습니다 — Loki 설정에 없는 필드를 넣어 **크래시 루프**가 났고(#31), 대시보드 JSON이 **이중 UTF-8 인코딩**으로 한글이 깨졌습니다(#42). 둘 다 원인을 찾아 고쳤습니다.

### 알람을 만들고, 알람마다 대응 절차를 썼다

TLS 만료 알람(#24), Harbor **본문 검사** probe(#23) — 200만 보면 껍데기만 살아있는 걸 못 잡아서 응답 본문까지 확인하게 했습니다. 로그 로테이션 + Loki retention(#29)으로 디스크도 막았습니다.

그리고 여기가 핵심인데, **9개 알람 룰 전부에 대해 v1 룬북을 작성**했습니다.

> `docs(ops): add v1 infra runbook covering all 9 alert rules (#26)`

**울리기만 하고 뭘 해야 할지 모르는 알람은 소음입니다.** 새벽에 울렸을 때 볼 문서가 없으면 그 알람은 결국 꺼집니다.

### 기준을 남의 것으로 세웠다

이미지 보안 문서를 **NIST SP 800-190**과 **OWASP** 기준으로 작성했습니다. 자체 기준으로 "안전하다"고 하면 근거가 없기 때문입니다.

> `docs(secops): expand Docker image security doc with NIST SP 800-190 + full OWASP review`

- **브랜치 보호가 깨져 있던 것** — job 이름이 바뀌면 필수 체크가 사라집니다. `backend-checks` **집계 job**을 만들어 이름을 고정했습니다.
- **실패 알림 사각지대** — `notify-on-failure`가 자기 `needs`에 없는 job의 실패를 놓치고 있었습니다.

그리고 모든 GitHub Action을 **SHA로 핀 고정**했습니다(#36). 태그는 옮겨질 수 있어서, 태그만 믿으면 **공급망 공격에 그대로 노출**됩니다.

## 5장. 하루 전쟁 — Harbor TLS·인증 (7/19)

**production VM이 Harbor에서 이미지를 못 받았습니다.** 이날 하루에만 진단·수정 커밋이 20건 넘게 쌓였습니다.

원인을 하나씩 지워나갔습니다.

| 의심 | 확인 방법 | 결과 |
| --- | --- | --- |
| DNS 미해석 | production `/etc/hosts` 확인 | 일부 원인 |
| CA 신뢰 실패 | `ca.crt` **디렉터리 존재가 아니라 파일 내용**까지 확인 | 원인 |
| robot 계정 권한 | harbor VM 자체에서 **대조 실험** | 정상 → 권한 아님 |
| 방화벽/프록시 | DB VM에서 토큰 엔드포인트 직접 curl | 정상 |
| 시계 오차 | clock skew 확인 | 정상 |
| **`echo`의 개행** | `--password-stdin`으로 교체 | **진짜 원인** |

`echo`로 넘긴 비밀번호의 **끝 개행이 인증을 깨뜨리고 있었습니다.** 같은 인용부호 중첩 버그를 세 번 잘못 짚고 **네 번째에 실제 원인**을 찾았습니다.

> `fix(cicd): fix the 4th (real) instance of the same quote-nesting bug`
> `fix(cicd): use --password-stdin for all SSH-wrapped Harbor logins`

**해결로 끝내지 않고 재발을 막았습니다** — CA 인증서를 production VM에 **자동 배포**하도록 파이프라인에 넣었습니다. 손으로 넣으면 VM이 늘 때마다 또 터집니다.

이날 부산물이 하나 더 나왔습니다. 일회성 진단 job을 돌렸는데 **`deploy_target` 기본값이 `both`라 배포까지 딸려 돌았습니다.** `none` 옵션을 추가하고, 주석으로 사고 경위를 남겼습니다.

> **여기서 배운 것**: 진단은 "무엇이 문제인가"가 아니라 **"무엇이 문제가 아닌가"를 하나씩 지우는 것**이다. 그리고 진단용 도구가 운영을 건드리면 안 된다.

SRE 블랙박스 모니터링 원칙은 **"사용자가 겪는 증상"** 을 재라고 합니다. 내부 서비스 하나가 흔들려도 사용자 화면이 멀쩡하면 그건 P0가 아닙니다. **알람 개수를 늘리는 게 관측 품질이 아니라는 것**을 이때 정리했습니다.

> `scope: registry 캐시 철회(buildx 빌더가 DNS 미해석 - 빌더 재구성 필요, 재정비로)`

되는 것처럼 보이게 두는 것보다 **안 되는 것을 안 된다고 기록하는 게** 낫다고 판단했습니다.

**④ 감시자를 감시하게 했다**
모니터링 스택이 통째로 죽으면 **알람도 같이 죽습니다.** 자기 자신은 자기가 감시할 수 없습니다.
그래서 모니터링 VM **바깥**(harbor VM 러너)에서 15분마다 프로브를 쏘고, **Grafana를 거치지 않고 Slack에 직접** 알리는 워치독을 별도로 만들었습니다.

## 7장. 스캔한 이미지를 그대로 배포하게 만들었다 (7/22~7/23)

문제를 발견했습니다. **같은 커밋을 PR에서 한 번, main에서 또 한 번 빌드**하고 있었습니다.

그러면 이렇게 됩니다:
1. PR에서 빌드한 이미지 A를 Trivy가 스캔 → 통과
2. main에서 **다시 빌드**한 이미지 B를 배포
3. **A와 B는 같다는 보장이 없습니다**

즉 *"취약점 스캔을 통과한 이미지"* 와 *"실제 배포된 이미지"* 가 다를 수 있는 구조였습니다.

**한 일 — build-once 패턴**: PR에서 **1회만 빌드**해 staging에 올리고, main에서는 **digest를 그대로 승격**합니다. 재빌드가 없으니 스캔한 바로 그 이미지가 배포됩니다.

frontend에 먼저 적용해 검증하고 → backend 9종 매트릭스로 확산 → frontend-admin까지 넣었습니다. 승격 무결성 검증이 `imagetools`의 **index 래핑** 때문에 오판하던 것도 교정했습니다.

같은 기간 CVE 대응도 했습니다.

| 대상 | 조치 |
| --- | --- |
| `next` 16.2.10 → 16.2.11 | HIGH 4건 |
| `sharp` 0.34.5 → 0.35.3 | 임시 억제 해제 후 정식 수정 |
| `cryptography` 48.0.1 | HIGH 2건 |
| `perl-base` CRITICAL | **Debian 수정판 없음** → diet-service는 패키지 제거로 해결, 나머지는 `.trivyignore`에 **사유 기록 후 리스크 수용** |

무조건 억제하지 않고, **고칠 수 있으면 고치고 못 고치면 이유를 남기는 것**을 원칙으로 했습니다.

## 8장. 잠갔다 — 도커 단계 마지막 날 (7/24)

**① 사람이 손으로 고친 설정이 조용히 갈라지는 것**
일부 스택(cAdvisor·SonarQube·monitoring)은 VM에서 사람이 직접 `docker compose`로 띄웁니다. **Git과 실제가 달라져도 아무도 모릅니다.**
→ **일 1회 드리프트 자동 감지**를 만들었고, 하루 안에 **세 번 개선**했습니다.

| 차수 | 문제 | 조치 |
| --- | --- | --- |
| 1차 | 러너가 있는 harbor VM만 검사 → 정작 드리프트 난 cAdvisor는 3개 VM에 있어 2곳이 깜깜 | production·DB VM까지 **확장** |
| 2차 | 전부 같은 톤으로 보고돼 뭘 조치할지 불명확 | **조치필요 / 참고** 분리 + diff 출력 |
| 3차 | 인라인 주석 차이까지 드리프트로 **오탐** | 텍스트 비교 → **compose 정규화 비교** |

**② 조용히 실패하던 것들**
paths-filter에 서비스를 등록하지 않으면 **에러 없이 그냥 빌드에서 빠집니다.** 배포됐다고 믿는데 안 된 상태입니다.
→ **세 곳(paths-filter / SERVICES / PORTS)에 다 배선되지 않으면 파이프라인을 일부러 실패시키는 가드**를 넣었습니다. 조용한 실패를 시끄러운 실패로 바꾼 것입니다.

같은 계열로 `infra/` 경로가 프론트 배포 감지에서 빠져 **머지됐는데 배포가 안 되던 것**, b-gateway 라우트 검증이 `/b/admin`의 **401을 실패로 오판**하던 것(인증 필요는 정상)도 고쳤습니다.

**③ 관측 도구가 관측 대상을 죽일 뻔한 것**
cAdvisor의 디스크 사용량 스캔(`du`)이 폭주해 **production VM 디스크가 포화되기 직전**이었습니다.
→ 해당 스캔을 차단했습니다. 이후 SonarQube를 포함한 모든 스택에 **로그 로테이션 + 리소스 상한 + 헬스체크**를 강제했습니다.

**④ 런타임 하드닝**
- 백엔드 서비스 포트를 **loopback 바인딩** — 외부에서 직접 못 붙고 **b-gateway를 거쳐야만** 접근됩니다
- b-gateway에 동일 수준 적용 — `cap_drop` · `no-new-privileges` · `pids_limit`
- 하드닝 앵커를 **9개 서비스가 실제로 쓰고 있는지 검증**해서 정리

**⑤ 러너가 멈추기 직전이었던 것**
self-hosted 러너에 로컬 이미지가 누적돼 **디스크 고갈로 파이프라인이 정지 직전**이었습니다. 자동 정리를 넣었습니다.

## WBS와 다르게 한 3가지

WBS에 적힌 것과 실제 구현이 다른 부분이 세 군데 있습니다. **못 한 것이 아니라 제약을 확인하고 다르게 결정한 것**입니다.

### ① 배포 방식 — 블루/그린 대신 「변경분 교체 + 헬스체크 게이트 + 자동 롤백」

**WBS**: 무중단 블루/그린
**실제**: `--no-deps`로 변경된 서비스만 순차 교체 → `/health` 확인 → **실패 시 직전 이미지 태그로 자동 롤백**

**왜 다르게 했나**: 블루/그린은 **같은 스택을 두 벌 동시에 띄울 자원**이 필요합니다. 단일 production VM에는 그만한 여유가 없습니다.
그래서 **목적(순단 최소화 + 실패 시 즉시 복구)은 그대로 두고 방식만 자원에 맞췄습니다.** 배포 전에 현재 태그를 기록해두고, 헬스체크가 실패하면 그 태그로 되돌립니다.
b-gateway만은 **별도 컷오버 job**으로 분리하고 **라우트 검증**을 붙였습니다. 게이트웨이는 잘못 바뀌면 전 서비스가 한 번에 죽기 때문입니다.

**K8s에서는**: Deployment 롤링 업데이트 + readiness 프로브로 **자연스럽게 이관**됩니다. readiness가 통과해야 트래픽이 들어가므로, 도커에서 손으로 만든 헬스체크 게이트가 플랫폼 기능으로 대체됩니다.

### ② 알림 경로 — Alertmanager 대신 Grafana Alerting

**WBS**: Alertmanager → Slack
**실제**: Grafana Alerting → Slack (알람 룰 12종 + severity 라우팅)

**왜 다르게 했나**: 시각화용 Grafana가 이미 떠 있었습니다. **컴포넌트를 하나 더 늘려 얻는 이득이 도커 단계에서는 없었습니다.** 룰·연락처·라우팅 정책을 모두 JSON으로 코드화해서 Git 관리 요건은 동일하게 충족했습니다.

**K8s에서는**: 인프라 알람을 **PrometheusRule CRD + Alertmanager로 이관**합니다. 이유가 생깁니다 — 알람을 Git 코드로 두면 ArgoCD로 배포되고, **admission webhook이 잘못된 PromQL을 생성 시점에 차단**해줍니다. Grafana Alerting은 대시보드에 밀착된 알람만 남깁니다.

### ③ 모듈별 파이프라인 — 파일 분리 대신 paths-filter 논리 분리

**WBS**: 크롤링·레시피수집 등 배포 단위별 파이프라인 분리
**실제**: 하나의 워크플로우 안에서 **9개 서비스 매트릭스 + `dorny/paths-filter`로 변경분만** 빌드·배포

**왜 다르게 했나**: WBS가 지적한 진짜 문제는 *"일괄배포 시 한 곳 실패가 전체를 막는 것"* 입니다. 이건 **워크플로우 파일을 쪼개지 않아도 해결됩니다** — 변경된 서비스만 job이 돌고, 서로 독립적으로 실패합니다.
반대로 파일을 9벌로 쪼개면 **하드닝·게이트·알림을 9곳에 중복 유지보수**해야 하고, 한 곳만 빠뜨리면 그게 곧 보안 구멍이 됩니다.
대신 **누락되면 파이프라인이 실패하는 가드**를 넣어, 논리 분리의 유일한 약점(배선 누락)을 막았습니다.

## 발표 대본 (그대로 읽어도 되는 문장)

> "도커 단계 17일 동안 제가 맡은 건 **CI/CD 파이프라인과 관측 체계**였습니다. 만든 것을 나열하기보다 **어떤 순서로, 왜 그렇게 했는지**를 말씀드리겠습니다.
>
> **첫째, 게이트를 먼저 세웠습니다.** 코드를 짜기 전에 gitleaks 훅과 린트 워크플로우를 넣었습니다. 시크릿은 한 번 올라가면 지워도 히스토리에 남기 때문입니다. 그런데도 초반에 SonarQube 비밀번호가 유출됐고, 자격증명을 회전하면서 **'추적되는 파일에 평문 금지'** 를 팀 규칙으로 정했습니다. 도구만으로는 부족하다는 걸 그때 배웠습니다.
>
> **둘째, 자동 배포보다 관측을 먼저 만들었습니다.** 순서를 바꾸면 뭐가 깨졌는지 모르는 채로 빨라지기만 합니다. 호스트·컨테이너·외형·미들웨어를 각각 다른 익스포터로 나눠 봤고, 대시보드와 알람은 UI가 아니라 **코드로 관리**했습니다. 그리고 **알람 9개 전부에 대응 룬북을 썼습니다.** 울리기만 하고 뭘 해야 할지 모르는 알람은 결국 꺼지기 때문입니다.
>
> **셋째, 그 다음에 손을 뗐습니다.** main에 머지되면 자동 배포되게 하되, **SonarQube 품질 게이트를 통과해야만** 넘어가게 묶었습니다. 액션은 전부 SHA로 고정했습니다. 태그는 옮겨질 수 있어서 공급망 공격에 노출되기 때문입니다.
>
> **가장 어려웠던 건 7월 19일**입니다. production VM이 Harbor에서 이미지를 못 받았습니다. DNS, CA 신뢰, robot 권한, 방화벽, 시계 오차를 하나씩 지워나갔고, 결국 원인은 **비밀번호를 `echo`로 넘길 때 붙는 개행**이었습니다. `--password-stdin`으로 바꿔 해결했고, **재발을 막으려고 CA 인증서 배포 자체를 파이프라인에 자동화**했습니다. 진단은 무엇이 문제인지 찾는 게 아니라 **무엇이 문제가 아닌지를 지워나가는 일**이라는 걸 그날 배웠습니다.
>
> **그 다음 이틀은 뭘 뺀 기간입니다.** 로그 수집 경로에서 중간 단계를 제거했고, 백엔드 개별 probe는 붙였다가 하루 만에 되돌렸습니다. SRE 블랙박스 원칙상 재야 할 건 **사용자가 겪는 증상**이지 내부 서비스 하나가 아니기 때문입니다. 빌드 캐시도 도입했다가 빌더 DNS 문제로 철회하고 그 사실을 기록했습니다. **되는 것처럼 보이게 두는 것보다 안 된다고 남기는 게 낫다**고 판단했습니다.
>
> 그리고 관측 스택 자체가 죽으면 알람도 같이 죽는다는 걸 깨닫고, **모니터링 VM 바깥에서 15분마다 확인해 Grafana를 거치지 않고 Slack으로 직접 알리는 워치독**을 따로 만들었습니다.
>
> **구조적으로 가장 중요한 수정은 build-once입니다.** 같은 커밋을 PR에서 한 번, main에서 또 한 번 빌드하고 있었는데, 그러면 **스캔을 통과한 이미지와 실제 배포된 이미지가 다를 수 있습니다.** PR에서 한 번만 빌드해 staging에 올리고 main에서는 digest를 그대로 승격하도록 바꿔서, 스캔한 바로 그 이미지가 배포되게 했습니다.
>
> **마지막 날엔 잠갔습니다.** 사람이 손으로 띄운 스택이 Git과 갈라지는 걸 잡으려고 드리프트 감지를 만들었고, 하루 안에 세 번 개선했습니다. 파이프라인에 서비스 배선이 빠지면 **에러 없이 그냥 빠지던 문제**는, 누락 시 일부러 실패시키는 가드로 바꿨습니다. 그리고 백엔드 포트를 loopback에 묶어 **게이트웨이를 거쳐야만** 접근되게 하고, `cap_drop`·`no-new-privileges`·`pids_limit`을 적용했습니다.
>
> **WBS와 다르게 한 게 세 가지 있습니다.**
> 배포는 블루/그린 대신 **변경분 교체 + 헬스체크 + 자동 롤백**으로 했습니다. 블루/그린은 스택을 두 벌 띄울 자원이 필요한데 단일 VM엔 없었습니다. 목적은 유지하고 방식만 자원에 맞춘 것이고, K8s에선 롤링 업데이트와 readiness로 자연히 이관됩니다.
> 알림은 Alertmanager 대신 **Grafana Alerting**으로 했습니다. Grafana가 이미 있어 컴포넌트를 늘릴 이유가 없었고, 룰은 전부 코드로 관리했습니다. K8s에선 PrometheusRule과 Alertmanager로 옮깁니다.
> 모듈별 파이프라인은 파일을 쪼개는 대신 **paths-filter로 논리 분리**했습니다. '한 곳 실패가 전체를 막는 문제'는 이걸로 해결되고, 파일을 9벌로 쪼개면 게이트를 9곳에 중복 관리해야 해서 오히려 구멍이 생깁니다.
>
> **정리하면, 도커 단계에서 만든 건 파이프라인과 대시보드가 아니라 기준과 검증 방법입니다.** 게이트를 먼저 세우고, 관측을 먼저 만들고, 조용한 실패를 시끄러운 실패로 바꾸고, 안 되는 건 안 된다고 남겼습니다. **그 기준을 K8s로 옮기는 것이 지금 하는 일입니다.**"
